# Evidence levels and bands

This is pairtime's published definition of evidence levels and bands, for {{.Covers}}. This server runs scoring {{.Running}}. Reviewers, programs and Hack Club's Quality and Integrity team all read this same text, and every review page links to it.{{if .Others}} Other versions: {{.Others}}.{{end}}

Every credited second has an evidence level, A, B or C, and in a submission every credited minute also has a band. {{if .Builtin}}The definition below is section 6.4 of {{.Design}}, word for word.{{else}}The definition below is section 6.4 of pairtime's design as it read for scoring {{.From}}, word for word. The design this server was built from may say something else.{{end}} [Terms](#terms) at the end explains its words, and references in parentheses, such as (D6) or (EV 6.7), point to that design and the documents it cites.

## Levels

**Levels, per credited second.** A second credited by an anchor's window takes that anchor's level. A second credited from the reading bucket takes the level of the human anchor that qualifies the drain (the nearest one within `READ_HORIZON_S`). But a second drained from output that a plugin or the bridge reported is level C whatever anchor qualifies the drain, since nothing but the side door backs it. One drained from the `R_TURN_BASE_S` that a `pairtime track` call, a plugin or bridge prompt or a queued message that a plugin reported starts its turn with takes no better level than that act. Either carries the side door's label, `via_plugin`, `via_bridge` or `via_track` (5.2). A lookup takes the lower level of the two credited seconds that bracket it, and carries a bracket's side-door label. A second credited in a slot whose focus is unknown is level C whatever its anchor's level, and so is every second credited from an anchor whose evidence test names focus and passed only because the window in front was unknown; both carry `focus_unknown` (SM 2.5).

| Level | All of these hold |
|---|---|
| A | The second is witnessed, or offline within D6's conditions. Presence comes from OS input. The client saw which window was in front in the second's slot and, for an act whose evidence test names focus, at the act. The anchor is keyboard-backed: `input_keys` is true in its evidence window, from the macOS key-down idle time or from the opt-in typing module with injected input excluded, and not from the typing module on a VM-labeled machine (D17). The anchor's `via` is `hook`, `log`, `shell`, `git` or `editor`, or it is a `track`, `plugin` or `bridge` anchor with keyboard input in the host window in the 10 s before it |
| B | Witnessed, or offline within D6's conditions. Presence from OS input, with keyboard-specific input unavailable (`input_any` only). The client saw which window was in front, as for A. The anchor's `via` is `hook`, `log`, `shell`, `git` or `editor` |
| C | Anything else: backfilled or lookback minutes, `track`, `plugin` and `bridge` anchors without keyboard corroboration, `editor_unverified` anchors, relayed anchors (SM 2.2 rule 9) and the reading they qualify, seconds credited where the client couldn't see which window was in front (SM 2.5), and offline minutes beyond the cap or without the forge push |

A side-door event that a pairtime log reader matches gets no level of its own: the log record's anchor counts instead, at that record's level, and the side-door event is a cross-check (5.2).

A relayed anchor is a message the person sent through an agent app, read from the app's own store with `via` `app`. Its typing time and its session's reading count whatever this device saw of the person, unless the machine was asleep, and always at level C (SM 2.2 rule 9, 2.4).

Labels ride along with levels and never change them: `via_track`, `via_plugin`, `via_bridge`, `typing_module`, `vm`, `focus_unknown`, `editor_typing` (v1.5 at the earliest), and `via_relay`, an origin label that every relayed anchor carries.

## Bands

**Bands, per credited minute of a submission**, computed from public inputs only, so the teen's copy of the review page shows them too (EV 6.7, D9):

| Band | Rule |
|---|---|
| Corroborated | Witnessed, not offline. Level A, or level B in a row that also has editor acts passing CC10. The anchor was seen by two records written by different code paths: hook and transcript, hook and OTel, or an editor heartbeat that passed the peer-process check plus a commit whose diffstat covers the file. The row passes CC6, CC7 and CC9 |
| Witnessed | Witnessed, level A or B, and misses a corroborated condition |
| Offline | Offline, within D6's conditions, level A or B |
| Backfilled | Level C, or late beyond D6's conditions. Shown with the handbook-third cap applied. Relayed minutes sit here because they are level C, though their witness label is the live one |

Held minutes (D7) sit outside the bands and aren't credited until a reviewer clears them.

## Program policy presets

**Program policy presets.** A program may set a preset, and the justification text names it. A preset may pre-approve only rows that are entirely corroborated and level A, with no flags and `captured_s` at most `PREAPPROVE_ROW_MAX_S` = 3,600 s. No preset pre-approves level-B, offline or backfilled minutes (JT must-fix 10; JT, Evidence-first, on the preset). Must-view rows and one random clean row are still opened before "approve remaining rows" unlocks.

## Terms

- **Anchor.** A human act that passes its evidence test, such as a typed prompt, an edit or a commit. It opens a lead window before it and a trail window after it, and credits seconds in them while the person is present and focused on its project (SM 2.3). A relayed anchor, a message the person sent through an agent app, is the exception: its typing time and its session's reading count whatever this device saw of the person, unless the machine was asleep, and always at level C (SM 2.2 rule 9, 2.4). Where pairtime can't see which window is in front, it still credits them, at level C (SM 2.5).
- **Reading bucket.** Each harness session's estimate of how long reading the agent's output could take. Present, focused seconds drain it (SM 2.4).
- **Lookup.** A short stretch in a browser or chat app between two stretches of project work (SM 2.5).
- **`input_keys` and `input_any`.** What the operating system reports about input in a window of time: keyboard input in particular, or only that there was some input.
- **`via`.** How a record arrived: `hook`, `log` (a harness transcript), `otel`, `os`, `git`, `shell`, `editor`, `editor_unverified`, `bridge`, `track`, `plugin` or `app` (a message read from an agent app's own store). The agent sets it from the path the record came in by, so a sender can't choose its own.
- **Witnessed, offline and backfilled.** A record's witness label, from how late the server received it (DESIGN 7.4). Witnessed means received within `WITNESS_LAG_S` = 900 s. Offline means late, but sealed on a continuous chain while the ledger held upload-failure notes, then flushed in one catch-up. Backfilled is everything else that arrived late, and all lookback.
- **D6's conditions.** Offline minutes count at their computed level up to `OFFLINE_CAP_S` = 10,800 s per submission, whatever the flush delay, and only if a commit in their interval reached the forge within `OFFLINE_PUSH_S` = 86,400 s of reconnecting. They are banded below witnessed and never pre-approved.
- **Held minutes (D7).** Minutes the server can't reproduce when it re-scores a submission, or whose chain doesn't verify. They aren't credited until a reviewer clears them.
- **The VM rule (D17).** On a machine labeled VM, minutes that are level A only because of the typing module drop to level B. The label never lowers credit.
- **CC6, CC7, CC9 and CC10.** Consistency checks (DESIGN 7.3). CC6 compares the server's re-score of a submission with the buckets it received live. CC7 checks that the revealed records reproduce every batch root, with no gaps. CC9 checks three things about a session: it stays in one project, every agent turn has a prompt or an automated origin in the same session, and its parent class, the kind of program its AI tool was started from (such as a terminal, an editor or a script), doesn't change partway through. CC10 checks that editor anchors arrive while an editor window of that project has focus.
