# Erratum: the project map, and a session across its repo's first commit

Date 2026-11-24. Raised by finding 18 of #69, the review of the git adapter in #47, and carried as WP-AG4's open item. Status: decided 2026-11-24 by the orchestrator for the owner (D-ag4-project-map). There is no project-binding record and no new event kind. A repo that gets its roots within a day of its folder's last use keeps its folder's key, so a session that crosses its repo's first commit keeps one project however soon the commit follows `git init`. `state.json` is the only copy of most of the project map, and after a lost map the agent takes back from `commits/` which key holds each root commit made on the computer (Decision, below). No scoring rule changes.

## Input

- DESIGN 3.5's `state.json` row says "Rebuildable from the ledger and the harness logs", and WP-AG4's Build asks the agent to rebuild the project map from the ledger when `state.json` is missing. `internal/agent/state` sets aside a `state.json` the release can't read and starts afresh on that promise.
- The git adapter's project map (`git.ProjectMap`) holds each repo's common git directory, key, kind, roots and aliases. A known repo keeps its key when a merged-in history adds roots or a rewrite replaces one (`reroot`, `holdsAny`). The resolver keys a folder outside git, a repo with no commit yet and a shallow clone by the folder. A first commit or an unshallow it sees moves the repo to its root-commit key, with the folder key as an alias (`Resolver.identify`, `Rekey`). A repo it first sights with roots takes the key of a known project that holds them, or its roots' own key.
- The resolver trusts a folder's answer for a minute (`DefaultRecheck`), and the agent looks at a session's folder again only once its answer is that old (`trackFresh`). A folder outside git isn't watched (`Watcher.Track`), and the first scan of a repo only notes where its reflog ends (`Scanner.Scan`).
- No ledger record holds a path. A `git.change` body keeps its `sha` and `parents`, which carry no local tag (`TestLocalFields`), so a commit with no parents made on the computer, a repo's first commit or an amend of it, puts a project key and a root commit in the ledger. `commits/` keeps the same pair in each commit record for 180 days. The roots of a repo first seen with its history, as after a clone, are in no record. DESIGN 6.5 reveals full bodies of other projects' records under its rules (a), (d) and (f).
- `pkg/score` takes a session's project from its first record and a turn's from its prompt. It keys reading buckets by the session's project and drains a bucket only in slots that resolve to that project (SM 2.4, 3.2). The agent sets each session's `focus_project` from its latest record.
- CC9 checks that one session stays in one project. CC3 counts a commit's lines against its project's records since the previous commit, or since the project's first record (DESIGN 7.3).
- The server keeps each device key's project id for the account's lifetime, so a key used again joins its old project (`rollup_projects`, migration 0005).

## What the rules give

- A new project built with an agent often gets `git init` and its first commit in its first session, and often within a minute of each other: an agent's one Bash call (`git init && git add -A && git commit -m init`), a scaffolder that commits for itself, or a person typing the commands. Then the resolver never sees the repo without commits. Its next look finds a repo with roots no project holds, which takes its root-commit key, and the watcher's first scan only notes where the reflog ends, so the first commit gets no `git.change` and no commit record.
- Either way, the session's records before the commit carry the folder key, and its records from a minute or so after carry the root-commit key. Its reading bucket stays under the folder key while its slots resolve to the root-commit key, so the bucket never drains again and the rest of the session earns no reading credit. CC9 fails the session. Where the first commit is recorded, CC3 finds no edit under its key before it, so a first commit of more than 200 lines comes out `unexplained_lines`. DESIGN 6.5 (a) reveals records by their header project, so it doesn't put the session's records from before the commit in a submission of the root-commit key's project, and the server can't link the folder key to the repo, since the folder key never has roots.
- A lost `state.json` loses the keys the map kept across grown or rewritten roots, and the aliases. A record holding the map's folders would show a private repo's folder to the reviewer of another project (DESIGN 6.5 (a), (f)). A record of opaque keys alone could link keys, but the scorer, CC9 and 6.5 would each need a rule to read it.
- A restore onto a new install has no `state.json` and a new `K_dev` (ledger-v1 3), so every project gets a new key there whatever any record says. Registration links those keys by their roots, as it links two computers' keys.

## Decision

Decided 2026-11-24 by the orchestrator for the owner.

1. No project-binding record and no new event kind. The project map stays in `state.json`, and a release that changes `state.json`'s format carries it over. Its folders exist nowhere else, and it keeps a folder outside git only as its folder key, never its path.
2. A repo keeps its folder's key when it gets its roots. A repo that gets them, at a first commit or an unshallow the resolver sees, or that the resolver first sights with roots at a main worktree it gave a folder key, keeps that folder's key, or the random key of point 5 the folder uses instead, if the resolver last gave the folder that key in the 24 hours before and the key holds no roots yet. It keeps it whether or not a known project holds those roots, and the roots join the key, as a rewritten root or a merged-in history already leaves a repo's key alone. The map records each folder key the resolver gives, to a folder outside git, an unborn repo or a shallow clone, with when it last gave it, and forgets it a day later unless the folder uses a random key. The 24 hours keep a folder key that sat unused from going to an unrelated repo made later at the same path, and keep the list short. Past the 24 hours the resolver does what it does today: the repo takes the key of the known project that holds its roots, or its roots' own key, and a repo the map held without roots keeps its folder key as an alias.
3. When a repo the resolver first sights with roots keeps its folder's key under point 2, the watcher's first scan of that repo records the reflog's entries dated after the resolver last gave the key, as a repo first seen before its first commit has that commit recorded, instead of only noting where the reflog ends. So the first commit has its `git.change` and commit record under the session's key.
4. So every record of a session in the folder carries one key across its repo's first commit: its own records, the commit's `git.change` and commit record, the folder's editor heartbeats and shell commands, and the `focus_project` of its window. That holds across an agent restart between `git init` and the commit, or between the commit and the agent's next look at the folder, since the map keeps when the folder key was last given. `pkg/score`, CC9 and DESIGN 6.5 need no rule for a key that changes, and no scoring version moves. SM 1.1 and 3.2 say that a repo can keep its folder's key, and DESIGN 5.8 says when.
5. A key names one project on the device. When the key a folder outside git, an unborn repo or a shallow clone is about to get is the key or an alias of a repo the map holds with roots, or a key the map records as holding a root, and git positively finds none of those roots there, the folder gets a random key of the folder-key form instead. Git finds them positively absent when it says the folder is in no repo and no `.git` is at or above it, or when the folder is in a repo that isn't shallow and `cat-file` finds none of the roots. A folder git refuses, a git that is missing or times out, and a shallow clone keep the key, as `holdsAny` keeps an identity when it can't tell. The map keeps the random key under the folder's folder key, so the folder keeps it across restarts and through its own `git init` and first commit, and it is never the gone repo's key or one the gone repo had before. The entry of the repo that was at the folder leaves the map with its path, and its roots keep their key. A key that never held roots can't be shown gone, so a folder made again where a folder outside git was keeps its key, as it always has. Today the next repo made where a repo with a folder-key alias was takes the alias, and this ends that.
6. Two repos the map holds can list the same roots under different keys, as when a repo first seen without its roots gets a known project's history by a pull or an unshallow. The map records which key each root went to first, and a restarted resolver gives each root to that key, so a fresh clone joins the same project after a restart as before it. Registration links the two keys on the server.
7. Registration (DESIGN 4.3) sends a key's root commits each time the project map gives the key roots it didn't have: a repo's first sighting with commits, the first commit or unshallow of one first seen without them, a rewritten root and a merged-in history. The server links the keys of the account that share a root into one project id (WP-SV10). The client half goes with the uploader (WP-AG5), after SV10's endpoint.
8. A lost map is rebuilt in part. When `state.json` holds no project map that reads, the agent, before the resolver answers its first folder, reads the commit records in `commits/` oldest first and gives each root commit, a record with no parents, to the key of the first record that names it, which then counts as a key holding that root for point 5. So a repo whose root commit `commits/` still holds keeps its key, and a folder where such a repo is gone gets a random key. Any other repo takes from the next start the key its present roots give, or its folder's while it has none, and registration links that key to the old one. This computer's views list those as two projects, and a session running across that start has records under both, which CC9 flags. Only a `state.json` the release can't read, or one the teen deletes, loses the map.

DESIGN 3.5 now states points 1 and 8, DESIGN 4.4 the map's retention, DESIGN 5.8 points 2 to 6 and 8, DESIGN 4.3 point 7, SM 1.1 and 3.2 that a repo can keep its folder's key, ledger-v1 3 the random key's form, and PLAN the resolver, watcher and agent changes (WP-AG4) and registration (WP-SV10).

## Accepted costs

- A folder used for a long time outside git and then made a repo brings its whole history into the repo's project, which a submission can then count and reveal (DESIGN 6.5 (a), 7.5 step 4). A repo's time before its next commit already has no cap (SM 4.3 item 3 caps only the credited time after the last commit in a window), so a teen who means to pad a project gains nothing that working in a clone from the start doesn't give. pairtime gives a folder's time to the folder's project (SM 3.2), and this keeps that true across `git init`. What bounds that time elsewhere bounds it here: D13 starts a window at most 180 days before the freeze, SM 4.3's half rate halves a project's credit after two credited hours without a progress event and the first commit restores only the day before it, `few_commits` flags a project of many hours and few commits, and the challenge draws from the window's own prompts. A bound on how old the folder's history may be would bring back the split session in every folder older than the bound.
- A folder key can still come back where nothing points elsewhere: for a folder outside git deleted and made again, and, after a lost map, for a folder where a repo is gone whose root commit `commits/` no longer holds or never held, as with a clone. Such a key joins the old project on the server, roots and all, because the server keeps a key's project id for the account's lifetime. Refusing the new roots at registration wouldn't part the minutes the key carries, so the server doesn't try.
- A repo first seen without its roots that gets a known project's history stays a project of its own on this computer, as point 6 says, and only registration joins the two on the server.

## Why the alternatives lost

- A project-binding record. Its body can't hold the map's folders. It could hold root commits, which `git.change` already holds for repos born on the computer, but for a clone it would put the roots of a repo the teen never committed to in bodies DESIGN 6.5 (a), (d) and (f) can show another project's reviewer, and each first copy would go in the 180-day sweep. Linking keys through it needs an SM rule and a scoring version, a 6.5 rule that reveals the old key's records, a CC9 exception, rtype `0x14` with a vectors chain of its own, `tools/ledger_ref.py`, and ingest's acceptance before any client sends one. `commits/` gives back the part that matters with none of that.
- Pinning each session to the key of its first record in the agent. The commit's `git.change`, editor heartbeats and shell commands in the same folder would still take the root-commit key, so the commit's anchor, its resets of SM 4.2's counts, its restores (SM 4.3) and an IDE session's editor slots would land in a project other than the session's.
- Letting the key change and having `pkg/score` move a session's bucket to its latest record's project. That needs an SM rule, a scoring version, a CC9 exception and a 6.5 reveal rule, and the time before the first commit would still be a project of its own on the server.
