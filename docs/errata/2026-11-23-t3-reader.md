# Erratum: what T3 Code's store leaves open for its reader, and what the code does until it's decided

Date 2026-11-23. Raised by the PR that builds T3 Code's reader (WP-ADE1, PR 3), from the open questions its spec left, what a read of T3's source couldn't settle, and the readings the PR's code chose. Status: waiting for the orchestrator. Until an item is decided, the code does what the item says, and the oracles stay as they are (DESIGN 6.6).

## Input

- D-relayed (docs/errata/2026-11-22-relayed-prompts.md): SM 2.2's "Relayed prompts" bullets and rule 9, DESIGN 3.3's `apps` row, DESIGN 5.1's T3 Code row and app-table paragraph, and DESIGN 5.9's doctor line. This PR builds them as T3 Code's reader (internal/adapters/t3code), the agent's apps component (internal/agent/apps.go), two entries of the app table (internal/platform/appclass.json) and doctor's `app.t3_code` line (internal/agent/doctor/apps.go).
- T3 Code's source at d8f3feff (pingdotgg/t3code, 2026-11-12). Every T3 path below is in that tree.

## Expected

Each case below follows from SM and DESIGN, so a reviewer can say what the reader, the agent and doctor should do with it and check that they do.

## What the rules leave open, and what the code does

1. **A guest's message that lost its guest mark.** The owner can promote a guest's queued message to a steer: the server refuses that only for a delegated task's results and notifications (apps/server/src/orchestration-v2/Orchestrator.ts:10795-10804). A steer that the provider declines, or that lands after its turn ended, goes out again without `guestMessageId` (apps/server/src/orchestration-v2/EffectWorker.ts:311-335), and that dispatch strips `context.guest` (Orchestrator.ts:14497-14508). The row is then a message of its own run from `user` and `web`, whose text opens "Message from guest <name>, sent by the owner:", with no mark. Whether T3's interface offers Steer on a guest's message wasn't checked.
   DESIGN 5.1 puts the guest test in the first query's `WHERE` clause "so the reader never reads a guest's message". The reader's guest test (internal/adapters/t3code/sql.go, `notGuest` and `isGuest`) also takes a row whose text opens with "Message from guest " for a guest's. The test runs inside sqlite3, so none of the text leaves it. An owner who starts a message with those words is taken for a guest, so the message earns nothing and its prompt keeps no text.

2. **A declined steer's follow-up.** T3 marks a follow-up with `steerFollowUpOfRunId`, on the command alone, never in the stored row (packages/contracts/src/orchestrationV2.ts:3290), and its own test of a message a person sent leaves such a follow-up out (Orchestrator.ts:7037-7041). The follow-up keeps the steer's message id and gets `createdAt = updatedAt = now` (EffectWorker.ts:287-353).
   A reader that saw the steer first, as a row with no run of its own, sees its stamp and its run change and counts it edited, so it earns nothing. A reader that first sees it after the follow-up, as when the agent was down during the steer, or the steer and its decline fell between two reads 10 s apart, takes it for a fresh message of its own run. It records it stamped at the follow-up, late by up to the length of the turn it tried to steer, and the stamp places the message's lead at the wrong time.

3. **Deliveries that wait with no bound.** A new thread launched with a worktree and setup scripts delivers its first message only after the setup has run (`defer_start`, Orchestrator.ts:7634; apps/server/src/orchestration-v2/ThreadLaunchService.ts:1110-1126), and a held queue waits for the next message a client sends (Orchestrator.ts:7034-7059). T3 stamps a message when its server takes it in, so neither wait shows in the stamp.
   SM 2.2 pairs a record only with a prompt delivered at most `RELAY_MATCH_S` (600 s) after the stamp, and D-relayed lists "a message queued longer than `RELAY_MATCH_S` earns nothing" as a known limit. The code does that. So the first message of a new worktree thread earns nothing when its setup takes longer than 10 minutes, though the wait is T3's setup and not a queue.

4. **Steers, and a guest's steer.** Neither T3's source nor this PR says whether Claude Code fires `UserPromptSubmit` for a steer that T3 pushes into a running query. T3 sends it as an SDK user message with a fresh uuid whose echo it tracks (apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts:12794-12837). A steered message's row names the running target run, whose own message is another one. D-relayed's question 3, the steer capture, is still open.
   The reader writes no record for a row without a run of its own, so a steer earns nothing, as SM 2.2 says. A guest's message steered into a run is reported to the agent as steered and marks no prompt, because only a run the guest's message started tells the reader which prompt carries it. If Claude Code does fire the hook for a steer, two things follow. The prompt that carries a steered guest's words isn't marked `guest` and keeps its text, which the privacy notice's T3 Code paragraph doesn't allow for. And a steer that reaches a run whose own prompt the agent never asked about can claim the run's record, since the reader pairs a run with the first prompt of its session at or after the run's start.

5. **JSON1 in older sqlite3.** The reader's SQL needs sqlite3's JSON functions, which are built in from sqlite3 3.38. Ubuntu 20.04 ships 3.31.1. Debian's and Ubuntu's older builds usually turn JSON1 on at compile time, but no one has checked one. The schema probe refuses a store the tool can't read with JSON functions, and doctor's line then says "pairtime doesn't read T3 Code's store, because this sqlite3 has no JSON functions".

6. **The folder test.** T3 runs a thread in its `worktreePath`, or else in its project's `workspace_root` (apps/server/src/orchestration-v2/RuntimePolicy.ts:162-186). T3's worktrees sit outside the repository, under the T3 home (apps/server/src/config.ts:162), `existing_worktree` launches keep the client's string as sent (ThreadLaunchService.ts:499-502), and `workspace_root` is resolved without following symlinks (apps/server/src/workspace/WorkspacePaths.ts:133-138). On macOS and Windows its case can differ from the disk's.
   The agent answers the folder test for T3's string, the thread's folder before the project's root, with its git adapter, as for a hook call's folder (internal/agent/adapters.go, `appFolder`). A folder the adapter hasn't seen yet is held while the adapter finds its project. One in no repository, or kept out by a `.pairtime-ignore`, is out, and any other is tracked under its project's key. A T3 worktree outside its repository is tracked, since git names its repository. The adapter reads the folder as T3 spelled it, so a `.pairtime-ignore` that only another spelling of the path reaches, through a symlink, is missed.

7. **A stamp later than the read.** SM 2.2 bounds only how late the reader may read a row: at most `RELAY_SEEN_LAG_S` after its stamp. T3's server and pairtime's agent run on one machine, under one clock, so a stamp later than the moment the reader reads the row comes from a row written by hand or a clock that was stepped. The reader passes it, as the rule's wording does, and its record's `t` comes before its `sent_at`.

8. **The pairing's slack.** The reader pairs a run with the first prompt the agent asked about of one of the run's Claude Code sessions, from 2 s before the run's start to 2 s after its end, and, for a message's own run, from the message's stamp to `RELAY_MATCH_S` after it. Each run takes one prompt, in the order the runs started. The agent remembers each prompt it asked about for `RELAY_MATCH_S` plus a minute, so a record read after its prompt can still name it. SM states the stamp's window. It doesn't state the 2 s on either side of the run, which the reader allows for the moments between T3 taking a run's times and Claude Code's hook firing.

9. **What counts as typed.** The spec strips T3's machine strings before the reader measures a message: a leading `Ultrathink:` line, the 121-character attachment-only placeholder, and context-reference tokens with their envelope. The reader also counts a quote of the agent's text, which T3 writes as `[Assistant quote](t3-citation://...)` (packages/shared/src/assistantCitations.ts:11-24), as the comment the person wrote with it, and not the quoted words.

10. **Prompts the agent doesn't ask about.** DESIGN 5.1 has the agent ask the reader "before it keeps the text of any prompt from a session T3's server started". The agent asks about a prompt that a hook or a log reader saw, once per turn, in a session that a walked hook call or a `session.start` record of the agent's current run showed to be an agent app's. It doesn't keep those marks across restarts. So three kinds of prompt from T3's sessions keep their text even when a guest's run delivered them: one that reached the agent only through the spool, with no walk, while the agent was down or slow; one that lookback reads from before pairtime; and, after a restart, a transcript copy read before any hook call of its session. Each still earns nothing, since no record witnesses it, and the draw never picks it. The privacy notice says so in words a reader can follow: pairtime keeps that prompt like any other when it "can't tell that a prompt came from T3 Code, as with one sent while pairtime's agent wasn't running".

11. **A relay record's class.** The ledger writer computes a `relay.message`'s `pc` when it writes the record, with `asked` from the session the record is bound to: a record bound to no session is never an answer. The scorer's class of the relayed turn reads the prompt's side as well. They can differ when the record comes after its prompt and an output asked a question in between, when the prompt has `answers_question`, or when `typed_len_est` is shorter than `len_chars`. ledger-v1 10.7 says `pc` is the class "as the writer computed it".

12. **A claude typed into T3 Code's own terminal.** T3 has terminals of its own, in its window and its web client, whose ptys T3's server opens (apps/server/src/terminal/NodePtyAdapter.ts). A claude typed into one runs under an interactive shell whose parent is T3's server.
   SM 2.2 rule 4 skips the shell, so the session's nearest non-shell ancestor is the server, `parent_class` `agent_app`, and "every other prompt of such a session is `headless`, whatever window hosts it". No T3 message witnesses those prompts, since they aren't messages. The classifier gives `agent_app` (internal/platform/classify_test.go), so a person who types into T3's terminal at this computer earns nothing for it. Before this PR the table didn't know T3, and its window hosted no session, so that typing earned nothing then either.

13. **T3 Code's desktop app runs its server.** The desktop app runs its server as its own executable, `process.execPath` with `ELECTRON_RUN_AS_NODE=1` (apps/desktop/src/backend/DesktopBackendConfiguration.ts:528-541), and so does the `t3` command it installs (apps/desktop/src/app/DesktopCliShim.ts:133-140). On Linux, Electron's helper processes have its name too. T3's own installs run the server as the `t3` executable they put in `<T3 home>/runtime/versions/<version>` (scripts/npm-launcher/t3.mjs:183-196), and a server run from T3's source runs as `node`.
   So the desktop app's entry in appclass.json (`t3code` on Linux, its product names `T3 Code`, `T3 Code (Beta)` and `T3 Code (Nightly)` on macOS and Windows) has `app_class` `agent_app` and the new role `app_server`, not `desktop`. With `desktop`, every session the desktop's own server starts would get `parent_class` `unknown`, and no T3 message could witness it. The `t3` entry has `app_class` `other`, since the server owns no window. A server run as `node` from T3's source stays `script_runtime`. The app table now names `t3 serve`, so the process scan that docs/errata/2026-11-23-agent-app-context.md leaves to the orchestrator's choice could count it.

14. **Doctor's two T3 Code warnings.** DESIGN 5.1 has doctor say "when a T3 Claude instance has a Claude home of its own" and "when T3 is installed but no session T3 started has reached pairtime in a day".
   For the first, doctor reads T3's settings.json beside each store it finds (`t3code.ClaudeHomes`): each enabled Claude instance's "CLAUDE_CONFIG_DIR path", else the `CLAUDE_CONFIG_DIR` its environment sets, and the `providers.claudeAgent` entry that older T3 versions wrote (apps/server/src/provider/Drivers/ClaudeHome.ts, apps/server/src/serverSettings.ts). It warns of a home whose settings.json holds none of pairtime's hooks and passes over Claude Code's default home, whose hooks doctor's hook line checks. It can't see a `CLAUDE_CONFIG_DIR` that T3's server gets from its own environment.
   For the second, the agent keeps in state.json when it last heard of a session whose walk or `session.start` names an agent app's server. Doctor warns when no such session has reached the agent in the last day and either T3 runs or the reader read messages today that paired with nothing. While T3 isn't running and the reader read nothing today, it says nothing, since no session could have reached pairtime.

15. **Hooks under T3's SDK, not seen live.** That a T3 run's session id is the hook's `session_id` comes from T3's source, `sessionId` and `resume` (ClaudeAdapterV2.ts:1998-2000), and not from a live hook record. T3 passes no `settingSources` to the Claude Agent SDK's query (ClaudeAdapterV2.ts:2043-2111). Its comment that "a user's settings.json env beats the process env in Claude Code" (ClaudeAdapterV2.ts:1970) holds only if the SDK it pins, `@anthropic-ai/claude-agent-sdk` `^0.3.321`, loads the user's settings, hooks included, when that option is left out. This PR didn't check the SDK. If it doesn't load them, no T3 session reaches pairtime, nothing pairs, and doctor's second warning says so.

16. **A store that looks open after T3 stopped.** The reader takes T3 to be running while its store's `-wal` and `-shm` files exist (DESIGN 3.3's `apps` row), and D-relayed-context makes presence's project context live on the same test (docs/errata/2026-11-23-agent-app-context.md). A read-only `sqlite3` that opens the store while those files are missing makes both, and leaves them when it exits, since a read-only connection can't checkpoint. That was checked with sqlite3 3.45.1 on a fixture store. So a T3 that stops while one of the reader's runs has the store open, or a T3 killed before it closed its store, leaves both files behind. From then on the store looks open: the reader reads it every 10 s, and presence samples once a minute with no other context, until T3 next starts and stops cleanly.
   The reader now checks the two files before each run of `sqlite3`, not only at the start of a read (internal/adapters/t3code/reader.go, `query`). That leaves a T3 that stops during a run, or that was killed. The URI parameter `readonly_shm=1`, which SQLite doesn't document, keeps a read from making the `-shm` file, but it still makes an empty `-wal`.

17. **The tests a record of `cron` or `cross_session` takes, and the provider.** The spec names a run of its own, the age test and the `updated_at` test for a record of `declared` `none`. The reader applies all three to `cron` and `cross_session` records too, and records no message of a thread whose run goes to a provider other than Claude Code (a provider thread's `driver` other than `claudeAgent`; doctor's counts call these `OtherHarness`). A `cron` or `cross_session` record that is never written leaves its prompt to rule 4, which takes it as `headless` rather than `scheduled` or `subagent`, so the prompt earns nothing either way and only its label differs. A row held while the agent's git adapter resolves its folder (item 6) takes the age test when the reader decides it, not when the reader first read its stamp.

A VACUUM may renumber the message rows' rowids, as T3 assumes (apps/server/src/persistence/Migrations/069_ThreadMessageSearch.ts:14), but no one has run one on a real store. The reader keeps its cursor check and its resync, so this needs no decision. Item 2 of D-relayed's questions, T3's MCP Apps, wasn't checked again here and stays open there.

## For the orchestrator

1. Item 1: keep the reader's test of a guest's opening words, which reads the text inside sqlite3 alone, or drop it and accept that a guest's message without its mark is recorded as the owner's.
2. Item 2: whether a declined steer's follow-up that the reader first sees after the follow-up may earn credit at its late stamp. Leaving it out needs a mark that T3 doesn't store, which only T3 can add.
3. Item 3: whether the first message of a `defer_start` run should count `RELAY_MATCH_S` from the run's start, which the reader already reads, rather than from the stamp. That changes SM 2.2 and the scorer's pairing check.
4. Item 4: schedule the steer capture. If steers fire `UserPromptSubmit`, say whether the agent marks `guest` every prompt of a session that arrives after a guest's message was steered into the session's running run, until that run ends.
5. Item 5: have a CI job run the reader's tests with the sqlite3 of Ubuntu 20.04 and Debian 11. If one lacks JSON1, doctor's line there should say how to get one that has it.
6. Item 6: confirm the thread's folder before the project's root, and say whether the agent should resolve symlinks in T3's string before its git adapter reads it.
7. Item 7: whether the reader refuses a row stamped later than the moment it reads it, beyond a small allowance such as 2 s.
8. Item 8: confirm the 2 s around a run's start and end.
9. Item 9: confirm that a quote counts as the person's comment alone.
10. Item 10: close the gaps in code, or keep the notice's exception. Closing them means keeping the sessions' marks in state.json, and asking the reader about spooled and lookback prompts too for the guest mark alone, which needs a reader call that claims no run, since a spooled copy that claimed one would take the witness from its turn's log copy. Even then the notice keeps an exception for prompts from before the reader's first read, which lookback reads: the reader starts at the newest row, so it knows no earlier guest's run.
11. Item 11: say which class a relayed turn rests on, the record's committed `pc` or the scorer's own, and what CC6 and CC8 compare.
12. Item 12: whether an interactive shell with a terminal between a harness and an agent app's server makes the session `terminal_app`, so that SM 2.2 rules 6 and 7 credit typing into T3's own terminal while its window is in front. Typing in that terminal from another device shows no input here, so rules 6 and 7 still give it nothing.
13. Items 13 and 14: confirm the desktop app's role and doctor's readings.
14. Item 15: check one live T3 message's hook record against its run's `nativeThreadId`, which the steer capture can do in the same run.
15. Item 16: whether "T3 runs" should rest on T3's server process, which the app table now names (item 13), rather than on its store's files, for the reader's cadence and for D-relayed-context's project context. A process scan tells a running T3 from files that a stop during a read or a killed T3 left.
16. Item 17: confirm the reader's tests for `cron` and `cross_session` records, the provider test, and when a held row's age is measured.
