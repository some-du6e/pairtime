# Erratum: what T3 Code's store leaves open for its reader, and what the reader does about it

Date 2026-11-23. Raised by the PR that builds T3 Code's reader (WP-ADE1, PR 3, #222), from the open questions its spec left, what a read of T3's source couldn't settle, and the readings the PR's code chose. Status: decided 2026-11-23 by the orchestrator for Karim, in issue #225, with the rulings on the review of #222. Items 1 and 2 corrected the same day from that review. Applied to SM 1.2, 2.2, 2.3 and 8.1, DESIGN 3.3, 4.1, 5.1, 5.9, 7.3 and 7.5, docs/spec/ledger-v1.md 10.7, testdata/fixtures/README.md, PLAN's WP-SC7, D-relayed (docs/errata/2026-11-22-relayed-prompts.md) and D-relayed-context (docs/errata/2026-11-23-agent-app-context.md) by #222, the PR that raised it, under the oracle-change label.

## Input

- D-relayed (docs/errata/2026-11-22-relayed-prompts.md): SM 2.2's "Relayed prompts" bullets and rule 9, DESIGN 3.3's `apps` row, DESIGN 5.1's T3 Code row and app-table paragraph, and DESIGN 5.9's doctor line. This PR builds them as T3 Code's reader (internal/adapters/t3code), the agent's apps component (internal/agent/apps.go), two entries of the app table (internal/platform/appclass.json) and doctor's `app.t3_code` line (internal/agent/doctor/apps.go).

## Expected

## What the rules left open, and what the code did

As #222 first had it, at ff30842, the head the review in #225 read. Items 1 and 2 are corrected from that review. The Decision below says what changes.

1. **A guest's message that lost its guest mark.** T3's client sends a guest's message as `queue_after_active` (packages/client-runtime/src/operations/commands.ts:545), so while a turn runs the message waits in the queue. Guest rows can't be edited, but the owner can send one, which promotes it to a steer (apps/web/src/components/chat/QueuedRunsControl.tsx:186, `queued-message.promote-to-steer`), and the server refuses that only for a delegated task's results and notifications (apps/server/src/orchestration-v2/Orchestrator.ts:10795-10804). A steer that the provider declines, or that lands after its turn ended, goes out again without `guestMessageId` (apps/server/src/orchestration-v2/EffectWorker.ts:311-335), and that dispatch strips `context.guest` (Orchestrator.ts:14497-14508). The projection upserts the row by its message id (apps/server/src/orchestration-v2/ProjectionStore.ts:2789), so it keeps its rowid. The row is then a message of its own run from `user` and `web`, whose text opens "Message from guest <name>, sent by the owner:", with no mark.
   DESIGN 5.1 puts the guest test in the first query's `WHERE` clause "so the reader never reads a guest's message". The reader's guest test (internal/adapters/t3code/sql.go) also took a row whose text opens with "Message from guest " for a guest's, inside sqlite3, so none of the text left it. This item first said that the test catches the case above. Corrected after the review in #225: it does only when the reader first reads the row after T3 sent it again, and the reader has usually read a guest's row before then. When the owner promoted a queued guest row, the row named another run, so the reader marked its watch changed and dropped it. A guest row first read as a steer, or before its run was visible, was never watched. The row the follow-up reuses is behind the reader's cursor, so the reader never read it again: Pair answered that it knew the prompt and that no guest's run had delivered it, and the guest's name and words went into the vault. The SQL also tested the text from its first character, where the reader's measure strips white space and an `Ultrathink:` line first. An owner who starts a message with those words is taken for a guest, so the message earns nothing and its prompt keeps no text. Decision 1 changes this.

2. **A declined steer's follow-up.** T3 marks a follow-up with `steerFollowUpOfRunId`, on the command alone, never in the stored row (packages/contracts/src/orchestrationV2.ts:3290), and its own test of a message a person sent leaves such a follow-up out (Orchestrator.ts:7037-7041). The follow-up keeps the steer's message id and its row, and gets `createdAt = updatedAt = now` (EffectWorker.ts:287-353).
   A reader that saw the steer first, as a row with no run of its own, records nothing for it and doesn't watch it, and the row is behind its cursor, so it never reads the row again: the follow-up earns nothing. This item first said that such a reader sees the row's stamp and run change and counts it edited. Corrected after the review in #225: that holds only for a row the reader recorded and watches, and it never watches an owner's steer. A reader that first sees it after the follow-up, as when the agent was down during the steer, or the steer and its decline fell between two reads 10 s apart, takes it for a fresh message of its own run. It records it stamped at the follow-up, late by up to the length of the turn it tried to steer, and the stamp places the message's lead at the wrong time. Rules 6 and 7 test that late stamp as the message's (decision 2).

3. **Deliveries that wait with no bound.** A new thread launched with a worktree and setup scripts delivers its first message only after the setup has run (`defer_start`, Orchestrator.ts:7634; apps/server/src/orchestration-v2/ThreadLaunchService.ts:1110-1126), and a held queue waits for the next message a client sends (Orchestrator.ts:7034-7059). T3 stamps a message when its server takes it in, so neither wait shows in the stamp.
   SM 2.2 pairs a record only with a prompt delivered at most `RELAY_MATCH_S` (600 s) after the stamp, and D-relayed lists "a message queued longer than `RELAY_MATCH_S` earns nothing" as a known limit. The code does that. So the first message of a new worktree thread earns nothing when its setup takes longer than 10 minutes, though the wait is T3's setup and not a queue.

4. **Steers, and a guest's steer.** Neither T3's source nor this PR says whether Claude Code fires `UserPromptSubmit` for a steer that T3 pushes into a running query. T3 sends it as an SDK user message with a fresh uuid whose echo it tracks (apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts:12794-12837). A steered message's row names the running target run, whose own message is another one. D-relayed's question 3, the steer capture, is still open.
   The reader writes no record for a row without a run of its own, so a steer earns nothing, as SM 2.2 says. A guest's message steered into a run is reported to the agent as steered and marks no prompt, because only a run the guest's message started tells the reader which prompt carries it. If Claude Code does fire the hook for a steer, two things follow. The prompt that carries a steered guest's words isn't marked `guest` and keeps its text, which the privacy notice's T3 Code paragraph doesn't allow for. And a steer that reaches a run whose own prompt the agent never asked about can claim the run's record, since the reader pairs a run with the first prompt of its session at or after the run's start.

5. **JSON1 in older sqlite3.** The reader's SQL needs sqlite3's JSON functions, which are built in from sqlite3 3.38. Ubuntu 20.04 ships 3.31.1. Debian's and Ubuntu's older builds usually turn JSON1 on at compile time, but no one has checked one. The schema probe refuses a store the tool can't read with JSON functions, and doctor's line then says "pairtime doesn't read T3 Code's store, because this sqlite3 has no JSON functions".

6. **The folder test.** T3 runs a thread in its `worktreePath`, or else in its project's `workspace_root` (apps/server/src/orchestration-v2/RuntimePolicy.ts:162-186). T3's worktrees sit outside the repository, under the T3 home (apps/server/src/config.ts:162), `existing_worktree` launches keep the client's string as sent (ThreadLaunchService.ts:499-502), and `workspace_root` is resolved without following symlinks (apps/server/src/workspace/WorkspacePaths.ts:133-138). On macOS and Windows its case can differ from the disk's.
   The agent answers the folder test for T3's string, the thread's folder before the project's root, with its git adapter, as for a hook call's folder (internal/agent/adapters.go, `appFolder`). A folder the adapter hasn't seen yet is held while the adapter finds its project. One in no repository, or kept out by a `.pairtime-ignore`, is out, and any other is tracked under its project's key. A T3 worktree outside its repository is tracked, since git names its repository. The adapter reads the folder as T3 spelled it, so a `.pairtime-ignore` that only another spelling of the path reaches, through a symlink, is missed.

7. **A stamp later than the read.** SM 2.2 bounds only how late the reader may read a row: at most `RELAY_SEEN_LAG_S` after its stamp. T3's server and pairtime's agent run on one machine, under one clock, so a stamp later than the moment the reader reads the row comes from a row written by hand or a clock that was stepped. The reader passes it, as the rule's wording does, and its record's `t` comes before its `sent_at`.

8. **The pairing's slack.** The reader pairs a run with the first prompt the agent asked about of one of the run's Claude Code sessions, from 2 s before the run's start to 2 s after its end, and, for a message's own run, from the message's stamp to `RELAY_MATCH_S` after it. Each run takes one prompt, in the order the runs started. The agent remembers each prompt it asked about for `RELAY_MATCH_S` plus a minute, so a record read after its prompt can still name it. SM states the stamp's window. It doesn't state the 2 s on either side of the run, which the reader allows for the moments between T3 taking a run's times and Claude Code's hook firing.

9. **What counts as typed.** The spec strips T3's machine strings before the reader measures a message: a leading `Ultrathink:` line, the 121-character attachment-only placeholder, and context-reference tokens with their envelope. The reader also counts a quote of the agent's text, which T3 writes as `[Assistant quote](t3-citation://...)` (packages/shared/src/assistantCitations.ts:11-24), as the comment the person wrote with it, and not the quoted words.

10. **Prompts the agent doesn't ask about.** DESIGN 5.1 has the agent ask the reader "before it keeps the text of any prompt from a session T3's server started". The agent asks about a prompt that a hook or a log reader saw, once per turn, in a session that a walked hook call or a `session.start` record of the agent's current run showed to be an agent app's. It doesn't keep those marks across restarts. So three kinds of prompt from T3's sessions keep their text even when a guest's run delivered them: one that reached the agent only through the spool, with no walk, while the agent was down or slow; one that lookback reads from before pairtime; and, after a restart, a transcript copy read before any hook call of its session. Each still earns nothing, since no record witnesses it, and the draw never picks it. The privacy notice says so in words a reader can follow: pairtime keeps that prompt like any other when it "can't tell that a prompt came from T3 Code, as with one sent while pairtime's agent wasn't running".

11. **A relay record's class.** The ledger writer computes a `relay.message`'s `pc` when it writes the record, with `asked` from the session the record is bound to: a record bound to no session is never an answer. The scorer's class of the relayed turn reads the prompt's side as well. They can differ when the record comes after its prompt and an output asked a question in between, when the prompt has `answers_question`, or when `typed_len_est` is shorter than `len_chars`. ledger-v1 10.7 says `pc` is the class "as the writer computed it".

12. **A claude typed into T3 Code's own terminal.** T3 has terminals of its own, in its window and its web client, whose ptys T3's server opens (apps/server/src/terminal/NodePtyAdapter.ts). A claude typed into one runs under an interactive shell whose parent is T3's server.
   SM 2.2 rule 4 skips the shell, so the session's nearest non-shell ancestor is the server, `parent_class` `agent_app`, and "every other prompt of such a session is `headless`, whatever window hosts it". No T3 message witnesses those prompts, since they aren't messages. The classifier gives `agent_app` (internal/platform/classify_test.go), so a person who types into T3's terminal at this computer earns nothing for it. Before this PR the table didn't know T3, and its window hosted no session, so that typing earned nothing then either.

13. **T3 Code's desktop app runs its server.** The desktop app runs its server as its own executable, `process.execPath` with `ELECTRON_RUN_AS_NODE=1` (apps/desktop/src/backend/DesktopBackendConfiguration.ts:528-541), and so does the `t3` command it installs (apps/desktop/src/app/DesktopCliShim.ts:133-140). On Linux, Electron's helper processes have its name too. T3's own installs run the server as the `t3` executable they put in `<T3 home>/runtime/versions/<version>` (scripts/npm-launcher/t3.mjs:183-196), and a server run from T3's source runs as `node`.
   So the desktop app's entry in appclass.json (`t3code` on Linux, its product names `T3 Code`, `T3 Code (Beta)` and `T3 Code (Nightly)` on macOS and Windows) has `app_class` `agent_app` and the new role `app_server`, not `desktop`. With `desktop`, every session the desktop's own server starts would get `parent_class` `unknown`, and no T3 message could witness it. The `t3` entry has `app_class` `other`, since the server owns no window. A server run as `node` from T3's source stays `script_runtime`. The app table now names `t3 serve`, so the process scan that docs/errata/2026-11-23-agent-app-context.md leaves to the orchestrator's choice could count it.

14. **Doctor's two T3 Code warnings.** DESIGN 5.1 has doctor say "when a T3 Claude instance has a Claude home of its own" and "when T3 is installed but no session T3 started has reached pairtime in a day".
   For the first, doctor reads T3's settings.json beside each store it finds (`t3code.ClaudeHomes`): each enabled Claude instance's "CLAUDE_CONFIG_DIR path", else the `CLAUDE_CONFIG_DIR` its environment sets, and the `providers.claudeAgent` entry that older T3 versions wrote (apps/server/src/provider/Drivers/ClaudeHome.ts, apps/server/src/serverSettings.ts). It warns of a home whose settings.json holds none of pairtime's hooks and passes over Claude Code's default home, whose hooks doctor's hook line checks. It can't see a `CLAUDE_CONFIG_DIR` that T3's server gets from its own environment.
   For the second, the agent keeps in state.json when it last heard of a session whose walk or `session.start` names an agent app's server. Doctor warns when no such session has reached the agent in the last day and either T3 runs or the reader read messages today that paired with nothing. While T3 isn't running and the reader read nothing today, it says nothing, since no session could have reached pairtime.

15. **Hooks under T3's SDK, not seen live.** That a T3 run's session id is the hook's `session_id` comes from T3's source, `sessionId` and `resume` (ClaudeAdapterV2.ts:1998-2000), and not from a live hook record. T3 passes no `settingSources` to the Claude Agent SDK's query (ClaudeAdapterV2.ts:2043-2111). Its comment that "a user's settings.json env beats the process env in Claude Code" (ClaudeAdapterV2.ts:1970) holds only if the SDK it pins, `@anthropic-ai/claude-agent-sdk` `^0.3.321`, loads the user's settings, hooks included, when that option is left out. This PR didn't check the SDK. If it doesn't load them, no T3 session reaches pairtime, nothing pairs, and doctor's second warning says so.

16. **A store that looks open after T3 stopped.** The reader takes T3 to be running while its store's `-wal` and `-shm` files exist (DESIGN 3.3's `apps` row), and D-relayed-context makes presence's project context live on the same test (docs/errata/2026-11-23-agent-app-context.md). A read-only `sqlite3` that opens the store while those files are missing makes both, and leaves them when it exits, since a read-only connection can't checkpoint. That was checked with sqlite3 3.45.1 on a fixture store. So a T3 that stops while one of the reader's runs has the store open, or a T3 killed before it closed its store, leaves both files behind. From then on the store looks open: the reader reads it every 10 s, and presence samples once a minute with no other context, until T3 next starts and stops cleanly.
   The reader now checks the two files before each run of `sqlite3`, not only at the start of a read (internal/adapters/t3code/reader.go, `query`). That leaves a T3 that stops during a run, or that was killed. The URI parameter `readonly_shm=1`, which SQLite doesn't document, keeps a read from making the `-shm` file, but it still makes an empty `-wal`.

17. **The tests a record of `cron` or `cross_session` takes, and the provider.** The spec names a run of its own, the age test and the `updated_at` test for a record of `declared` `none`. The reader applies all three to `cron` and `cross_session` records too, and records no message of a thread whose run goes to a provider other than Claude Code (a provider thread's `driver` other than `claudeAgent`; doctor's counts call these `OtherHarness`). A `cron` or `cross_session` record that is never written leaves its prompt to rule 4, which takes it as `headless` rather than `scheduled` or `subagent`, so the prompt earns nothing either way and only its label differs. A row held while the agent's git adapter resolves its folder (item 6) takes the age test when the reader decides it, not when the reader first read its stamp.

A VACUUM may renumber the message rows' rowids, as T3 assumes (apps/server/src/persistence/Migrations/069_ThreadMessageSearch.ts:14), but no one has run one on a real store. The reader keeps its cursor check and its resync, so this needs no decision. Item 2 of D-relayed's questions, T3's MCP Apps, wasn't checked again here and stays open there.

## Decision

The orchestrator's rulings in #225, one per question. Each says what #222 does about it.

1. **Q1 (item 1). Changed.** The prefix test stays inside sqlite3, and so does its known limit. On its own, though, it rarely catches anything, as item 1 now says. In #222, a row the guest query returns, by mark or by prefix, stays watched for a day whatever T3 does to it: a promotion to a steer, a decline, a resend, a resync. The reader keeps the watch in `state.json` by its message's key, and every later run of its own counts as a guest's run. The SQL prefix test skips leading white space and an `Ultrathink:` line the way the reader's measure does. The apps component marks `guest`, keeping no text, every `prompt.submit` copy whose text opens with T3's guest wrapper, `Message from guest `, after any white space and an `Ultrathink:` line, on any path, a hook's, a spooled call's, a transcript's or lookback's, since every copy passes through it (internal/agent/adapters.go, internal/agent/apps.go). Reader tests cover a promotion, a decline and a resend, a row first read as a steer and sent again, and a row read before its run exists, and apps tests cover a hook's, a spooled call's and lookback's copies. SM 1.2's `guest` field, SM 2.2's guest sentence, DESIGN 4.1 E-13 and DESIGN 5.1's T3 Code row name the device test. The known limit widens to any prompt, in any harness, that opens with those words: it keeps no text and earns nothing. So D-relayed's "only T3 Code's reader marks a prompt `guest`" (What stays) now has the device test beside it, which can only take credit away.
2. **Q2 (item 2). Changed.** The limit is accepted, but "at level C" is wrong. Rules 6 and 7 read the stamp (pkg/score/turns.go), so a follow-up re-sent while the person types in T3's desktop window here scores `human_typed` or `human_pasted`, with a full prompt lead ending at the late stamp. Accepting it also bends SM 2.2's witness test, which rests on T3's own test, and T3's test leaves follow-ups out. The mark may not need T3 either: the follow-up keeps the steer's old rowid with `createdAt` = now, so its stamp is later than rows T3 stored after it. In #222, SM 2.2's witness bullet and D-relayed's Known limits say that a follow-up the reader first reads after T3 sent it again witnesses its run at the late stamp, and that rules 6 and 7 test it as the message's. WP-ADE1 runs a read-only query of rowids and stamps alone on the owner's live store, like the reader's own reads, counting user rows from `web` or `mobile` stamped more than 2 s after the next row. If only follow-ups show that order, the reader turns such rows away and counts them for `doctor`, and the limit narrows to a follow-up with no row stored between it and its steer.
3. **Q3 (item 3). Kept**, as both critics agree. `RELAY_MATCH_S` is `PENDING_WINDOW_S` less `COMPOSE_MAX_S` (D-relayed decision 3), so counting it from the run's start would let a pairing arrive after the lead's minutes are final. Nothing changes beyond item 3's record.
4. **Q4 (item 4). Changed.** The capture moves off the owner's live T3. Tying a past steer there to pairtime's records needs `K_session` or the hook payloads, which hold prompt text, and a new steer would land in the owner's threads and in the uploads of the owner's linked agent. Guests' steers don't wait for the capture: decision 1's sticky watch and device test cover their `prompt.submit` copies. A hook copy that carries the running turn's `prompt_id` becomes `agent.queue` (internal/adapters/claudecode/claudecode.go), which keeps no text. That `agent.queue` still opened a `Q` anchor at level A or B whenever there was input and T3's window was in front, and #222 makes that window host every T3 session (pkg/score/anchors.go). `PA` and `INT` had no session test either, though SM 2.2 says steers, approvals and stops given through the app earn nothing. In #222, pkg/score opens no `Q`, `PA` or `INT` anchor in a session whose `parent_class` is `agent_app`, with tests, and SM 2.2's "What isn't a message" bullet and SM 2.3's table say so. Two readings are #222's own, not the ruling's, and its description puts them to the orchestrator: it reads the session by its last `session.start` before the act, as rule 4 does, and it still flags a permission answered faster than `PA_MIN_LATENCY_MS` there, since the ruling only removes anchors. Before #222 merges, WP-ADE1 runs the capture with WP-AD0's kit as a throwaway user with its own T3 home and repository, on the machine's installed t3 and Claude Code. Claude Code runs under a scratch `CLAUDE_CONFIG_DIR` whose only hook logs the event, `session_id`, `prompt_id`, the time and whether the prompt opens with T3's guest prefix, then drops the prompt. The only text the capture sends is probe text, an owner's steer and a guest's steer through a throwaway share. It records the T3, SDK and Claude Code versions and every copy a steer leaves: the hook's, OTel's, or a transcript entry by type, `promptSource`, `turnOrigin`, `promptId` and timestamp. Nothing leaves it but counts, booleans and offsets. If the capture can't show a guest's steer, or shows a copy without the prefix, the reader reports the steered row's target run, and the agent marks `guest` every `prompt.submit` copy of that run's sessions stamped from the later of the row's stamp and the run's start to the run's end, past its per-turn cache (internal/agent/apps.go), leaving any prompt a run claimed.
5. **Q5 (item 5). Kept**, as both critics agree. In #222, a step in ci.yml's single job builds the reader's test binary with `CGO_ENABLED=0` and runs it in `ubuntu:20.04` and `debian:11` containers with each distribution's own sqlite3. If either lacks JSON1, `doctor`'s no-JSON line on that distribution says how to get a sqlite3 that has it.
6. **Q6 (item 6). Changed.** The order stands, and so does the project key, since the git adapter keys a repository by its canonical common dir (internal/adapters/git/resolve.go). The ignore test is another matter. `ignoreFileAbove` walks the folder as spelled (internal/adapters/git/ignore.go), so T3's unresolved string and the hook's cwd can get different verdicts, and then the reader reads and measures text in a folder the person ignored, which DESIGN 5.1 rules out. In #222, `appFolder` also resolves T3's string with `filepath.EvalSymlinks` and keeps the folder out when an ignore reaches either spelling, with a test in each direction. WP-ADE1 counts, by a read-only query of the owner's live store, threads whose `worktreePath` is empty, which `COALESCE` picks over the project's root (internal/adapters/t3code/sql.go). If T3 runs such threads in the root, the reader reads an empty `worktreePath` as none.
7. **Q7 (item 7). Changed in where it is written.** As things stood, the server's re-score paired a record from a client that skips the test, and an unpaired record with a future stamp still caps the thread's next lead, because `prevMessage` counts every record of `declared` `none`. In #222, the reader refuses a row stamped more than 2 s after the read that decides it, and counts it for `doctor`. SM 2.2's witness bullet bounds the stamp on both sides of that read, at most `RELAY_SEEN_LAG_S` before it and at most 2 s after. pkg/score's `pairs()` (relay.go), which already repeats the reader's other time tests, also requires `re.T >= sent_at - 2000`, with a test. One reading is #222's own, not the ruling's, and its description puts it to the orchestrator: such a record holds no minute for a pairing it can't make, as one written more than `RELAY_SEEN_LAG_S` after its stamp already held none, and it moves no server's first derived minute to a lead it can't open.
8. **Q8 (item 8). Changed.** `pair()` took runs in order of start and gave each one the earliest prompt up to 2 s after its end (internal/adapters/t3code/reader.go). A run that delivered nothing, because T3 cancelled it or because the agent never asked about its own prompt, then took the prompt of the run T3 starts right after it. Either the owner's next prompt was marked `guest`, or a guest's prompt was witnessed as the owner's and kept its text. And SM 2.2 paired a run with a prompt "at or after the run starts", so the 2 s before the start is an SM rule, not only a DESIGN one. In #222, a run's window opens 2 s before its start and closes at `completed_at`, and guests' runs claim before messages' runs. Reader tests cover an empty run followed within 2 s by a guest's run, and by the owner's next run, and a run whose own prompt is never asked. SM 2.2's Pairing bullet and DESIGN 5.1's T3 Code row state both bounds. The capture measures the gap from `startedAt` to the run's first hook prompt, and whether T3 has committed `startedAt` and the attempt's `nativeThreadId` when the hook fires. WP-ADE1 widens the start slack if that gap needs it. If T3 commits a start late, a guest's run binds its session from its provider thread before it starts, and the agent asks again within 2 s about any prompt of that session, marking it `guest` if the run still hasn't started. The orchestrator's rulings on the review of #222 add a third bound, from the capture: a run takes no prompt stamped at or before the `completed_at` of an earlier run the reader watches in the same session. There a steer during a run's Stop hook fired 111 ms before that run's `completed_at` and 1,586 ms before the next run's `startedAt`, inside the next run's 2 s slack. The next run was T3's notice, which nothing watches, but a queued message's run there would have taken the steer's prompt, and its own prompt would have paired with nothing. The bound only removes pairings, so it adds no credit, and it stays causal, since `completed_at` is known before the later run starts. The reader keeps reading a run that claimed its prompt until it sees the run end, so the bound holds for the run's whole life while the reader watches its message. Its edge: a run's own prompt stamped before the previous run completed would go unpaired, and T3 starts a queued run only after completing the one before, so that doesn't happen in normal flow. A TestPairing case has the capture's timings, and SM 2.2's Pairing bullet and DESIGN 5.1's T3 Code row state the bound.
9. **Q9 (item 9). Changed in where it is written.** The reading is right, but SM 2.2 listed three machine strings while the reader strips four (internal/adapters/t3code/measure.go), and AGENTS.md has SM and code change in the same PR. In #222, SM 2.2's list and D-relayed's class bullet add "`[Assistant quote](t3-citation://...)` links, which count as the comment they carry".
10. **Q10 (item 10). Changed.** Two of item 10's three reasons don't hold. Opt-in backups send encrypted vault segments to the server (DESIGN 4.3), and the vault keeps prompt text for 90 days or until a submission covering it is decided (4.4), which can outlast T3's own copy. "The draw never picks it" holds for live copies, which rule 4 takes. ## The capture

Decisions 2, 4, 6, 8, 10 and 14 rest on WP-ADE1's scratch capture and on two read-only counts of the owner's live store, which ran on 2026-11-23, before #222 merged. What they found, and which branch of each decision follows, is recorded here.

The capture ran T3 Code 0.1.10-nightly.20261112.4606 (`t3 serve` on a loopback port, from a hard-linked copy of the installed runtime), the Claude Agent SDK 0.3.321 and Claude Code 2.1.330, with claude-opus-5-5 in full-access mode, on Ubuntu 24.04.4, as a throwaway account with its own home, T3 home and two-file repository. Claude Code ran under a scratch `CLAUDE_CONFIG_DIR` whose only hooks logged each call's event, `session_id`, `prompt_id` and arrival time, and for `UserPromptSubmit` whether the prompt opens with T3's guest wrapper, and kept no prompt. An agent drove T3's web client through 28 probes in two threads, one in the project's root and one in a new worktree, and one probe's frame never reached T3. The fixture, with ids and paths replaced and every time moved by the same whole number of days, is testdata/fixtures/t3_code/0.1.10-nightly.20261112.4606/linux, and its PROVENANCE.md has the rest.

- **Hooks under T3's SDK (decision 14, item 15).** All 70 hook calls fired from the instance's `CLAUDE_CONFIG_DIR` alone: 28 `UserPromptSubmit`, 23 `Stop`, 17 `PostToolUse` and 2 `SessionStart`, and no `SessionEnd` when the server stopped. So the SDK, with the options T3 passes and no `settingSources`, loads the user's settings, hooks included. The hook's `session_id` was the run attempt's `nativeThreadId` for 28 of 28 prompts, and the provider thread's `nativeThreadRef.nativeId` for both sessions. Each transcript's file name was its `session_id` (2 of 2), and each transcript prompt's `promptId` was the hook's `prompt_id` (28 of 28, with none extra on either side). T3's title-generation runs left two folders in the same Claude home and fired no hook. The fixture keeps every row of the 7 tables testdata/schema.sql creates, with T3's rowids, and the tables, columns and indexes the reader reads were exactly schema.sql's. TestCapture (internal/adapters/t3code) replays it beside the schema.sql tests: the reader records the 21 messages a person sent with a run of its own, pairs each with the prompt its own run delivered, writes nothing for the 3 owner's steers or T3's 2 notification rows, and reports the 3 guest-wrapper stand-ins below as steered, as probes.json says.
- **Steers and guests (decision 4).** T3 makes a guest link only through a running T3 Connect tunnel (apps/server/src/guest/GuestShareService.ts:342-345), which needs a T3 cloud account, so the capture couldn't show a real guest's steer. Three stand-ins whose text opens with the wrapper as GuestShareDecider.ts:217 writes it, and which carry no `context.guest`, took a guest's path instead: a steer, a queued message the owner promoted to a steer, and a steer T3 delivered while the target turn's Stop hook ran. Every copy kept the wrapper (3 of 3), and the reader's prefix test inside sqlite3 took all three rows for guests'. All 6 steers T3 delivered fired `UserPromptSubmit`, each with a `prompt_id` of its own, 119 ms to 7.3 s after the row's stamp, since a steer waits for Claude's next tool boundary. Each left one transcript `user` entry with `promptSource` and `turnOrigin` `sdk` and the hook's `promptId`, after a queue-operation enqueue and dequeue, and one row in the target run, with no `steerWhenReadyRunId`. In the hook and the transcript a steer looks like a typed message; only the store tells it apart. So the fallback applies as ruled. The reader reports each running turn a guest's message was steered into (`t3code.Reader.Steers`), and the agent marks `guest` every copy of a prompt of that turn's sessions stamped from the later of the row's stamp and the turn's start to the turn's end that no run claimed, past its per-turn cache. In the fixture those turns cover the three stand-ins' prompts and no other. SM 1.2's `guest` field, SM 2.2's guest sentence, DESIGN 4.1 E-13 and DESIGN 5.1's T3 Code row say so, and SM 2.2's Pairing bullet now says what Claude Code reports of a steer. This also answers D-relayed's question 3, the steer capture: a steer reaches Claude Code as a prompt of its own, and earns nothing, since it has no run of its own.
- **Follow-ups and the order test (decision 2).** One follow-up was captured. T3 accepted a steer, the turn ended before it landed, and 3.0 s later T3 sent it again in the same row, with its rowid and message id, a new stamp (`created_at` = `updated_at`) and a run of its own, whose hook came 726 ms after the new stamp and 517 ms after the run's `startedAt`. No row was stored between the steer and its follow-up: the row before it is 4.8 s older and the one after 3.3 s newer. So a reader that first reads it then takes it for a fresh message of its own run, and "stamped more than 2 s after the next row" can't see it. On the owner's store, a read-only count over the last 20,000 message rowids found 14 user rows from `web` or `mobile` stamped more than 2 s after the next row by rowid: 9 by `user` with no mark and 5 by `agent` with a `scheduledTaskId`, each with `updated_at` = `created_at` and a started run of its own requested at its stamp, 2 ahead by 2 to 10 s, 11 by 10 to 60 s and 1 by 60 to 600 s. For all 14 the next row is in another thread and has no run: a fork's copied history with its old stamps (8,979 such rows, in 1,392 threads, every one forked). Taking the next row in the same thread instead, none is from `web` or `mobile`. The order test doesn't single out follow-ups, so the reader turns no row away for it, and the known limit stays as SM 2.2 and D-relayed state it.
- **Empty `worktreePath` (decision 6).** Of the owner's 11,080 thread rows, read-only, `worktreePath` is JSON null in 4,722 (4,658 neither archived nor deleted, 217 with a run) and set in 6,358, and no row has an empty string or lacks the key. T3's contract types it `NullOr(TrimmedNonEmptyString)` (packages/contracts/src/orchestrationV2.ts:476), so T3 can't store an empty one, and RuntimePolicy.ts:162-185 runs a thread whose `worktreePath` is null in its project's root, as the capture's root thread ran. `folderOf`'s `COALESCE` matches T3, so it doesn't change.
- **The pairing window (decision 8).** For each of the 21 runs a person's message started, the run's own hook prompt came 220 to 2,335 ms after its `startedAt`, never before it; the longest was a new worktree thread's. At the hook's moment, for 27 of the 28 prompts, the run was running with `startedAt` committed, and the attempt's `nativeThreadId` and the provider thread's `nativeId` already named the hook's session. The exception is a turn Claude Code started itself for a background command's notice, whose hook came 875 ms before its run's `startedAt` and 422 ms before its `requested_at`. T3 stores that turn's row as an agent's, with a `notification` mark, so it witnesses nothing. No prompt of a run came after its `completed_at`; the latest came 111 ms before it, a steer during the Stop hook. That steer also fell 1,586 ms before the next run's `startedAt`, inside its 2 s slack. The next run was T3's notice, which nothing watches, so nothing paired wrongly, and decision 8's third bound now keeps such a prompt from any later run. A queued message's hook came 32.8 s after its stamp, when its run started. So the 2 s before the start is enough, and T3 never committed a message's start late: the slack stays, and no late-start fallback is built.
- **The entrypoint token (decision 10).** Every transcript entry of T3's two sessions that has an `entrypoint` says `t3-code` (139 entries), and every hook call saw `CLAUDE_CODE_ENTRYPOINT=t3-code` (70 of 70). Typed messages and steers have `promptSource` and `turnOrigin` `sdk`, and the notice's turn has `system` and `task_notification`. So `tokenEntrypoint` (internal/adapters/claudecode/logparse.go) reads `t3-code` as `sdk`, with tests, and SM 2.2 rule 4's sources list it. Rule 4 now takes a T3 session that only its transcript shows, which is what PLAN's WP-SC7 waits for before it scores lookback.
