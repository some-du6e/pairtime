# Erratum: the 25 ms hook gate on windows-latest

Date 2026-11-20. Raised by WP-AG3 (#93). Status: decided 2026-11-20 by the orchestrator for Karim: patched TOML copy, and the hook's cost over an empty Go program, ≤ 10 ms, with an absolute 50 ms ceiling.

## Input

DESIGN 9.7 and PLAN's WP-AG3 entry: "hook p95 under 25 ms over 200 warm calls on `windows-latest`", which DESIGN sets at half the R8 claim of a 50 ms warm round trip on a 2016 laptop, "because a 4-CPU runner with an SSD is several times faster than the target laptop". The oracle is "timing measured by the workflow around the process".

`footprint.yml` starts `pairtime.exe hook --harness claude_code --event UserPromptSubmit` the way a harness runs an exec-form hook: stdin, stdout and stderr on pipes, an 89-byte event written to stdin. It times each call from `Process.Start` to `WaitForExit` with the agent up, 10 warm-up calls and then 200 counted.

## Expected

p95 under 25 ms.

Every call exited 0, printed nothing and reached the agent over the socket. The last two rows ran on the throwaway branch `wp-ag3-probe`, never merged.

The second run's trace splits a call into its parts:

- The hook's own work after `main` (stdin, the message, the dial, the agent's walk, the ack) takes 2.1 ms at p50 and 2.6 ms at p95.
- The time from Windows creating the process to `main` takes 23.8 ms at p50 and 28.5 ms at p95. For an empty Go program, on the next run, it took 5.4 ms at p50 and 6.2 ms at p95.
- `pairtime.exe hook -h`, which only prints its usage, costs as much as a real call: 25.0 ms at p50 and 33.8 ms at p95.

[44774348347](https://github.com/some-du6e/pairtime/actions/runs/44774348347) ran `pairtime.exe hook -h` with `GODEBUG=inittrace=1`. Package initialization took 41.5 ms in all, and `github.com/BurntSushi/toml/internal` took 34.0 ms of it, with 1,578 allocations. The next slowest were `net` at 3.3 ms and `pkg/redact` at 2.0 ms.

## Reasoning

There are two causes, and only the first is pairtime's to fix.

**`BurntSushi/toml` reads the local time zone at package init.** Its `internal/tz.go`, in v1.6.0 and on master, sets `localOffset = func() int { _, o := time.Now().Zone(); return o }()` at package level. That makes Go load `time.Local` in every pairtime process, whatever the command. On Windows, `time.Local` reads the zone's standard name and looks it up among the English zone IDs Go knows. When the name isn't one of them, Go enumerates every key under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Time Zones` and loads each one's display names until one matches. The runner's zone is UTC, whose standard name, "Coordinated Universal Time", isn't a zone ID, so it takes the slow path; the 1,578 allocations fit that enumeration. So does every Windows in a language other than English, which is likely common among Hack Clubbers worldwide. On a 2016 laptop with a hard drive that enumeration costs more than on the runner, so R8's 1.0 gate (a warm round trip under 50 ms, `doctor --report` on five pre-2017 laptops) is at risk too. Only `internal/agent/config` links the module into the client.

**A process costs much more on some `windows-latest` machines than on others.** The empty Go program's p50 was 10.6 ms on one runner and 17.9 ms on another, and `hostname.exe` took 11.7 ms and 19.2 ms. On the slower machine even the build without the TOML module came to a p95 of 29.7 ms. pairtime's own start also outweighs an empty program's: 17.3 ms from creation to `main` against 5.8 ms on that runner, with 4.9 ms of package init. The rest goes with the binary's size, 8.3 MB against 1.7 MB, which the Windows loader maps and relocates. So a fixed 25 ms around the process passes or fails depending on the runner a job lands on.

## For Karim

1. **The TOML module's init.** Whatever happens to the gate, this costs every pairtime command 15 to 35 ms on the runner, and more on a localized laptop. Pick one:
   - (a) Replace `BurntSushi/toml` in the client with a small reader for the TOML pairtime itself writes and reads (`config.toml` now; mappings and plugin manifests later, DESIGN 5.3). The server keeps the module.
   - (b) Use a patched copy through a `replace` directive, with the local offset computed on first use. Upstream has no fix to take.
   - (c) Send the same patch upstream and bump the module when it's released. Until then (a) or (b) would still be needed.
2. **The gate.** Pick one:
   - (a) Keep 25 ms around the process. After the TOML fix it passes on faster runners and fails on slower ones.
   - (b) Gate what pairtime adds over the runner's own floor: the hook's p95 less the p95 of an empty Go program started the same way in the same job, under 15 ms. With the TOML module gone, that was about 9 ms on the slower runner. `footprint.yml` already reports the empty program, so this is one line.
   - (c) Raise the number to what the slower runners need once the TOML fix is in, about 35 ms around the process.

   The 1.0 gate on real laptops stays as DESIGN has it either way.

## Decided

1. (b): `go.mod` replaces `BurntSushi/toml` with `third_party/burntsushi-toml`, a copy of v1.6.0 whose `internal` package reads the local offset under a `sync.Once` the first time it is needed. Its `PROVENANCE.md` has the upstream commit and the patch, and the same patch goes upstream.
2. (b), at 10 ms: `footprint.yml` times 200 calls of the empty Go program in the same job as the hook's 200, gates the hook's p95 less the empty program's p95 at 10 ms, fails outright when the hook's p95 is above R8's 50 ms, and reports both. DESIGN 9.7 and its R8 row say so.
