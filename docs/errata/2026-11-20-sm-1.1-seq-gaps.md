# Erratum: SM 1.1 calls an event's seq gapless, and the ledger numbers checkpoints from the same sequence

Date 2026-11-20. Raised by the ledger fix-up for issue #19, from the review of #5 (WP-LG1). Status: decided 2026-11-20 by the orchestrator for Karim (E-sm-1.1-seq-gaps), amended: `seq` is the record number `s`. Each device numbers every record from 1, checkpoints and upload-failure notes included, with no gap or repeat. Events' `seq` rise strictly and skip those numbers. Verifiers and CC7 check gaps over every record's `s` and excuse none, though since D-local-gap a verifier starts a new run after a local-only gap the server recorded at a re-link. The exactly-once clause is dropped. No SM or fixture number moves (Decision, below). PLAN's WP-LG5, WP-AG4, WP-AG5, WP-AG8, WP-LG6 and WP-SB4 say so since #111, and `pkg/score`'s `recordCmp` comment since #112. SM 1.1, DESIGN 3.7, 4.3, 7.3 and 7.11, `docs/spec/ledger-v1.md`, PLAN's WP-PV2 and the READMEs of `testdata/timelines` and `testdata/checks` follow in #343, a docs PR with no code, then `pkg/event`'s comments, the event schema's `seq` description and `internal/timelines`' test names and messages in a code PR, which also states [the check-readings erratum](2026-11-19-check-readings.md)'s code-point unit on `agent.queue`'s `len_chars`.

## Input

A device whose scorer seals a checkpoint for an active project at a UTC minute divisible by 15 (DESIGN 6.5), between two events. Its ledger holds the records:

| `s` | Record | Event `seq` |
|---|---|---|
| 41 | `prompt.submit` | 41 |
| 42 | checkpoint (`0x40`) | none |
| 43 | `agent.output` | 43 |

## Expected

SM 1.1's envelope table: "`seq` | uint64 | Per-device sequence, gapless; the server uses it for exactly-once ingest (SP 8.2)". Read as written, the device's events carry `seq` 41, 42, 43, with no number missing.

## Computed

Spec 4.1 numbers every ledger record from one sequence, checkpoints and upload-failure notes included, and an event's `seq` is the `s` of the record that holds it (decision 4). The events above carry `seq` 41 and 43. The record sequence has no gaps; the events' own `seq` values skip every number a checkpoint or note holds, which is one per active project every 15 minutes. `pkg/event`'s comment on `Envelope.Seq` and `docs/schema/event.schema.json` already say so (changed in #10).

## Reasoning

AGENTS.md makes SM the source of truth that `pkg/event` follows field for field, and SM is an oracle (docs/design/**), so the code and the spec can't change SM's wording themselves. Left alone, a later work package that builds an exactly-once ingest rule or a gap check from SM 1.1 would read each checkpoint as a dropped event and hold the minutes around it.

The ledger can't give events a gapless sequence of their own without a second counter, which spec 4.1 avoids on purpose: one sequence over every record is what lets a verifier find a dropped record of any type (spec 9 step 2).

## For Karim

Reword SM 1.1's `seq` row, for example: "Per-device sequence: the `s` of the ledger record that holds the event (ledger-v1 4.1). Records, checkpoints and upload-failure notes included, are numbered with no gaps, so events' `seq` values skip the numbers those records hold. The server uses it for exactly-once ingest (SP 8.2)." No code changes with it.

## Decision

Decided 2026-11-20 by the orchestrator for Karim (E-sm-1.1-seq-gaps), with four amendments its challenger made the same day.

`seq` is the ledger record number `s`. Each device numbers every record it writes, checkpoints and upload-failure notes included, from 1 with no gap or repeat, so events' `seq` values rise strictly but skip those numbers. No gap is ever legitimate: a crash only frees the numbers of records no sealed batch holds, and the next records reuse them. A restore starts a new device whose chain begins at 1. Verifiers and CC7 check gaps over every record's `s`, never over events alone, and never excuse one: a gap fails the batch where it shows (or the missing batch that explains it), and CC7 holds that batch's minutes as it does for any batch that doesn't verify.

The meaning cell of SM 1.1's `seq` row becomes "Per-device record number: the `s` of the ledger record that holds the event (ledger-v1 4.1). The agent numbers every ledger record from 1 as it writes it, checkpoints and upload-failure notes included, with no gap or repeat, so a device's events have rising `seq` values that skip the numbers those records hold. Gaps are looked for among records, never among events (ledger-v1 9)". This drops 'gapless' and 'the server uses it for exactly-once ingest (SP 8.2)'.

Two corrections to the sections above. First, checkpoints come for every project with records in the last 24 hours at each UTC quarter-hour (up to 96 a day per project, DESIGN 3.6), plus one note per failed upload, not 'one per active project every 15 minutes'. Second, the proposal's 'exactly-once ingest (SP 8.2)' clause is dropped, because the server dedupes batches on `(device_id, b)` (DESIGN 3.10, ledger-v1 6) and tier 1 uploads no events.

Its challenger kept all of this, with these amendments:

(a) ledger-v1 4.1, and a new decision in its section 13, read: "Every record of a sealed batch keeps its number. A seal makes its records durable no later than its batch row: sync the segment before writing the row, or write the row into the segment so one fsync covers both. The uploader sends only durable rows, and a backup holds only sealed records, so a crash can cut only records that no sealed batch holds. At start the writer drops a torn tail and seals the records that survived. It gives the next record the number one past the larger of the last surviving `s` and the last sealed batch's `last_seq`. A sealed record lost anyway is lost evidence, which CC7 holds, and its number is never reused." WP-LG5's Build replaces "one fsync per seal" with this order. Its crash loop also throws away every byte written after the last sync, as a power cut would, and checks that no `s` repeats or skips.

(b) ledger-v1 3, decision 32 and WP-AG5 get a rollback rule. Before its first upload after a start, and whenever the server refuses its request counter or its `prev`, the client compares `GET /api/v1/ingest/state` with `batches.seg`. It starts a new device, as a restore does, if the server holds a batch of this `device_id` that the ledger lacks or holds under another head, or if the install has `K_dev` but no ledger. It then retires that `device_id` and `K_dev`, keeps them only to read and open the old chain, uploads nothing more under them, and starts a new `device_id` and `K_dev` from `s = 1` and `b = 1`. D-new-device-wp-ag8 later gave the new device a WP of its own: after a fork or a `device_mismatch`, WP-AG5 uploads nothing more under the old pair, and WP-AG8 starts the new device (ingest-v1 5.3).

(c) DESIGN 3.7 and WP-AG4's Build say the scorer steps over newly sealed records. The agent seals, steps and writes any quarter-hour checkpoint with no record numbered in between, so a checkpoint's state covers exactly the records numbered below it (DESIGN 6.5).

(d) The DESIGN 7.3 Catches sentence becomes "No crash or restore leaves a gap, so CC7 excuses none; a reviewer can still clear held minutes (D7)."

D-local-gap later made one gap honest: when a device signs in again, the server records the batches the device skipped, which it never sends, as a local-only gap, and a verifier starts a new run after it (ledger-v1 6, 9 steps 1 and 2). The device's own numbering still has no gap or repeat.
