# Erratum: SM 1.1 calls an event's seq gapless, and the ledger numbers checkpoints from the same sequence

Date 2026-11-20. Raised by the ledger fix-up for issue #19, from the review of #5 (WP-LG1). Status: decided 2026-11-20 by the orchestrator for Karim: an event's `seq` is the `s` of the ledger record that holds it, and records, checkpoints and upload-failure notes included, are numbered with no gap or repeat, so events' `seq` values rise but skip those numbers. No crash or restore leaves a gap, and the proposal's exactly-once-ingest clause goes (Decision, below).

## Input

A device whose scorer seals a checkpoint for an active project at a UTC minute divisible by 15 (DESIGN 6.5), between two events. Its ledger holds the records:

| `s` | Record | Event `seq` |
|---|---|---|
| 41 | `prompt.submit` | 41 |
| 42 | checkpoint (`0x40`) | none |
| 43 | `agent.output` | 43 |

## Expected

SM 1.1's envelope table: "`seq` | uint64 | Per-device sequence, gapless; the server uses it for exactly-once ingest (SP 8.2)". Read as written, the device's events carry `seq` 41, 42, 43, with no number missing.

## Computed

Spec 4.1 numbers every ledger record from one sequence, checkpoints and upload-failure notes included, and an event's `seq` is the `s` of the record that holds it (decision 4). The events above carry `seq` 41 and 43. The record sequence has no gaps; the events' own `seq` values skip every number a checkpoint or note holds, which is one per active project every 15 minutes. `pkg/event`'s comment on `Envelope.Seq` and `docs/schema/event.schema.json` already say so (changed in #10).

## Reasoning

AGENTS.md makes SM the source of truth that `pkg/event` follows field for field, and SM is an oracle (docs/design/**), so the code and the spec can't change SM's wording themselves. Left alone, a later work package that builds an exactly-once ingest rule or a gap check from SM 1.1 would read each checkpoint as a dropped event and hold the minutes around it.

The ledger can't give events a gapless sequence of their own without a second counter, which spec 4.1 avoids on purpose: one sequence over every record is what lets a verifier find a dropped record of any type (spec 9 step 2).

## For Karim

Answered on 2026-11-20 by the decision below.

Reword SM 1.1's `seq` row, for example: "Per-device sequence: the `s` of the ledger record that holds the event (ledger-v1 4.1). Records, checkpoints and upload-failure notes included, are numbered with no gaps, so events' `seq` values skip the numbers those records hold. The server uses it for exactly-once ingest (SP 8.2)." No code changes with it.

## Decision

Decided 2026-11-20 by the orchestrator for Karim: the rewording above, amended. SM 1.1's `seq` row now reads "Per-device record number: the `s` of the ledger record that holds the event (ledger-v1 4.1). The agent numbers every ledger record from 1 as it writes it, checkpoints and upload-failure notes included, with no gap or repeat, so a device's events have rising `seq` values that skip the numbers those records hold. Gaps are looked for among records, never among events (ledger-v1 9)".

1. No gap is legitimate. A crash cuts only records no sealed batch holds, and the next records reuse their numbers. A restore starts a new device whose chain begins at 1 (ledger-v1 3). Verifiers and CC7 look for gaps over every record's `s`, never over events alone, and excuse none: a gap fails the batch where it shows, or the missing batch that explains it, and CC7 holds that batch's minutes as it does for any batch that doesn't verify (DESIGN 7.3, ledger-v1 4.1 and 9).
2. The proposal's "The server uses it for exactly-once ingest (SP 8.2)" is dropped. The server dedupes batches on (`device_id`, `b`) (DESIGN 3.10, ledger-v1 6), and tier 1 uploads no events.
3. A correction to Computed: checkpoints come for every project with records in the last 24 hours at each UTC quarter-hour, up to 96 a day for a project (DESIGN 3.6), plus one note for each failed upload, not one for each active project every 15 minutes.

No fixture's expected value and no SM worked number changes. The fixtures hold no checkpoints or notes, so their events' `seq` rise by 1, and `testdata/checks/checks.py` and `pkg/ledger` already look for gaps over records' `s`.
