## Decision

Option 2. SM's rows stay, and SM 6.5's 20:39 row now reads "Opens `Hero.css` in VS Code (heartbeat at 20:39:20) and works out the margin the hero needs". The only VS Code heartbeats before the save are the 20:39:20 `navigate` and the 20:41:00 save: the file in front stays `Hero.css`, and the save comes 100 s after the first heartbeat, under `TIME_BETWEEN_HEARTBEATS_MS` (HC 1.5). In `testdata/timelines/6.5` the 20:39:20 heartbeat is now for `Hero.css`, the 20:40:51 Ctrl+P and the 20:40:52 heartbeat are gone, and rows 20:39 and 20:40 no longer name this erratum. No number in SM or the fixture changes.

The heartbeat moves labels, not credit. Each minute credits 60 s either way, `E` and `NAV` both count in `hand_credited_s` (SM 5.4), and the 20:41:00 save still ends the loop. So SM's numbers stay and one story cell changes, the way 6.3 keeps Sam's test in `src/parse.rs` so that no switch heartbeat appears.

Two rule changes were turned down. Ranking a typed edit's lead above a navigation's can't give SM's rows, as "Computed" says. A rule that a `navigate` in the file of the next typed edit, inside that edit's lead, opens no window would give them. But it adds an exception to SM 2.3's editor-navigation anchor, it labels the 92 s he spends reading `Navbar.css` as `hand_edit` instead of `reviewing`, and it changes a scoring rule, so SM and `pkg/score` would change together in a PR with the `oracle-change` label and a MAJOR `scoring_version` (SM 7.6).

"What the rules give" and "Computed" stay as the record of what a switch does: 92 s move from `E` to `NAV`, and the hour's `NAV` and `E` become 142 and 188.
