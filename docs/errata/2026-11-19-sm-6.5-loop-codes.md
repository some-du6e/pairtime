# Erratum: SM's rules don't decide which code 6.5's loop seconds carry

Date 2026-11-19. Raised by WP-FX2. Status: decided 2026-11-20 by the orchestrator for Karim. A loop's seconds are the ones a scoring with no turn discounted, with each slot's focus unchanged, would credit while the scoring doesn't. Each takes the code of the latest discounted turn at or before it, or of the next one when it falls before the loop or after the undiscounted prompt that ends it. Two detectors on one turn give the first of X.reroll, X.same_error, X.autopilot and X.rewrite_loop. Normalization strips edge punctuation and apostrophes, which ledger-v1.md 10.4 step 6 has done since #67. SM 4.2, 2.7, 5.1, 5.2 and 6.5 say so, and testdata/timelines/6.5 and 4.2-alternation no longer name this erratum.

SM 6.5, the rows around the loop:

Totals: `excluded_loops_s` 2,010 s, "from 20:05:00 to 20:38:30".

[...] Seconds that would have been credited are reported under their discount code." SM 5.2: `X.agent_only` is "An agent turn ran and nothing credited the second".

## Expected

A rule that, applied to the events, gives each of these codes and their seconds.

## What the rules give

1. **Which discount code.** Read literally, "seconds that would have been credited" points at the window or bucket that would have credited each second had none of the loop's turns been discounted. That doesn't give SM's rows:
   - 20:03:20-:40 is inside T3's lead, 143 s from 20:02:37, which would have credited it as `P`. So it would be `X.rewrite_loop`, not `X.agent_only`.
   - All of 20:05 is inside T4's lead, which starts at 20:04:35. So it would be T4's `X.reroll`, not `X.rewrite_loop`.
   - 20:06 is inside T4's lead too, apart from the browser check, which would have been a lookup between two stretches of that lead. So it would be `X.reroll` as well, not `X.rewrite_loop`.
   - All of 20:07 is inside T5's lead, from 20:06:39. T5 is a paraphrase in this fixture, so it would be `X.rewrite_loop`, not `X.reroll`.

   SM's rows fit another reading: each second from a discounted prompt's submit to the next human prompt, or to the first credited second after the loop, carries that turn's code. A discounted prompt's own lead isn't reported under any discount code, and its seconds that nothing else credits keep their usual code. That reading gives 20:03, 20:05, 20:06, 20:07 and 20:38 as SM writes them, and exactly 2,010 s from 20:05:00 to 20:38:30. SM doesn't state it anywhere.
2. **Discount codes and `X.agent_only`.** In 20:05 T3's agent runs and nothing credits a second, which is `X.agent_only` by SM 5.2's wording. SM's row has `X.rewrite_loop` 60, so SM lets a discount code win over `X.agent_only` inside a discounted turn without saying so. "Would have been credited" settles it only for seconds that a window or a bucket would have covered. This fixture's loop has one stretch that nothing would have covered: 20:13:20-:40, while T7's agent runs. T7's bucket holds only its 20 s base until its edit at 20:13:40, and the next prompt, T8, "pls fix the overlap", is a 19-character go-ahead whose lead is 20 s. Every other second from 20:05:00 to 20:38:30 would have been covered by the next anchor's lead, a bucket or a bracketed browser check. Read literally, then, 20:13:20-:40 stays `X.agent_only` and 20:03:20-:40 becomes `X.rewrite_loop` (point 1). `excluded_loops_s` stays 2,010 and `X.agent_only` 100 only because the two 20 s stretches trade places, and the excluded seconds are no longer "from 20:05:00 to 20:38:30".

   That count takes the whole loop's discounts away at once, as point 1 does. Taking them away one turn at a time leaves much more uncovered, because "the lead of a later, credited anchor never reaches back past the stop of the most recent discounted turn in the same project" (SM 4.2) then cuts each loop prompt's lead at the stop of the turn before it. For each of T3 to T18, nothing would have credited the 20 s between its base running out and its edit, 20:05:20-:40, 20:07:20-:40 and so on to 20:35:20-:40. T19's 20:37:20-:40 is still covered, by the 20:39:20 `NAV` lead, which T19's discount no longer cuts. That is 320 s, which would make `excluded_loops_s` 1,710 and `X.agent_only` 400. Another 470 s would have two claimants, one turn's bucket and the next turn's cut lead. A scratch run of gen.py's reading, changed to take one turn's discount away at a time, gave those numbers.
3. **Two detectors on one turn.** T4 is attempt 3 and rewrite repeat 3. SM's 20:07 row gives `X.reroll`, but no rule says which code wins. SM 5.2 happens to list `X.reroll` first.
4. **Punctuation.** SM 4.2's normalization lowercases, replaces pasted blocks, numbers, paths, URLs, hex strings and backticked identifiers, turns retry phrases into `<retry>` and collapses whitespace. It doesn't remove punctuation. Then T2 and T4 normalize to `still overlapping on mobile. <retry>` and `still overlapping on mobile, <retry>!!`. Each has five tokens, so they are compared by character 5-shingles, and their Jaccard similarity is 0.69, under `SIM_JACCARD` = 0.8. T4 would be attempt 1, discounted only as `X.rewrite_loop`. SM's 20:07 row says T4 "normalizes to the same text", which needs punctuation removed, as SM 2.2 removes it for prompt classes.

A related point: if T3 to T18 ran 60 s like T1 and T19, the minutes 20:06, 20:08 and so on to 20:36 would have no credit and no running agent, so SM 5.1 would write no bucket for them and their discount seconds would be in no upload. That is point 3 of [the 6.6 erratum](2026-11-19-sm-6.6-uncredited-codes.md). This fixture's loop turns run 75 s, so every loop minute has a bucket.

## Decision

Decided 2026-11-20 by the orchestrator for Karim.

1. Which seconds. SM 4.2 now takes point 1's literal reading with every discount removed at once (point 2). A loop's seconds are the ones a second scoring of the same records, with no turn discounted and each slot's focus unchanged, credits to the project and the scoring itself doesn't, at that scoring's weight. The span reading was turned down. It puts discount codes on seconds no rule would credit, such as an absent stretch inside a loop, and DESIGN 6.2 D12 lets a reviewer raise those seconds back.
2. Which code. The latest discounted turn in the project at or before the second, unless an undiscounted human prompt came between them. Otherwise the next one, or the latest if none follows. That keeps SM's 20:05, 20:06, 20:07 and 20:38 rows. 20:03:20-:40 is T3's `X.rewrite_loop`. 20:13:20-:40, which nothing would have credited, stays `X.agent_only`. So does any other second inside a discounted turn that no rule would credit (point 2).
3. Two detectors. The first of `X.reroll`, `X.same_error`, `X.autopilot` and `X.rewrite_loop`. The three decided when the prompt is sent come before the one that needs the turn's edits. T4 stays `X.reroll`.
4. Punctuation. #67 settled it. ledger-v1.md 10.4 step 6 strips each word's edge punctuation and apostrophes before step 7 matches retry phrases, so T2, T4 and T16 all normalize to `still overlapping on mobile <retry>`. SM 4.2's normalization sentence now says so.
5. Minutes with no bucket. SM 5.1 now writes a bucket for every minute a loop cost a second in, so a loop's seconds reach the upload whatever its turns' lengths. Point 3 of the 6.6 erratum still holds for minutes without loop seconds.
6. Loop rows. DESIGN 6.2 D12 makes one row per loop, with each code's seconds, so the split between codes never decides what a reviewer can raise.

`testdata/timelines/6.5` gives every loop minute its seconds: `X.reroll` 460 and `X.rewrite_loop` 1,550. The span reading gave 480 and 1,530, and labelling by the turn behind each second would give 550 and 1,460. Credited 1,490, `excluded_loops_s` 2,010 and `X.agent_only` 100 don't change. `4.2-alternation`'s 19:45 stays `X.reroll` 60.
