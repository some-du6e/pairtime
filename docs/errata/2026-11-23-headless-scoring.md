# Erratum: on a computer whose agent can't sample, the scorer stopped finalizing 15 minutes after each agent start

Date 2026-11-23. Raised by WP-HL1, from a linked alpha device's counts and times. Status: decided 2026-11-23 by the orchestrator for Karim: option 2, with the bound on a sample's reach the review of #234 added and the wait before that bound takes effect its fix-verify added (#241), applied to SM 2.1, `pkg/score` and the agent's scorer loop by the PR that adds this file, under `oracle-change`.

## Input

A Linux server with no graphical session runs pairtime v0.1.0-alpha.6, linked and online, beside an agent app's server (T3 Code) that runs Claude Code sessions. It has no idle source and no focus channel (`internal/agent/presence/presence.go`, `internal/agent/focus/os_linux.go`). Its ledger holds no `os.presence` and no `os.power` record since 2026-11-21, and five `os.focus` records, each `app_class` `unknown`: since #192 the focus component writes one each time the agent starts and never repeats it. Its minute buckets stopped about 15 minutes after each agent start, while batch roots kept flowing. Stretches of up to three hours between starts were never derived, and two of the minutes left pending reached the server as empty final revisions. The scorer's window stayed where it started, so each Step re-scored about 57,000 records and the agent ran at about 38% CPU. `doctor` said ok throughout.

The code it ran:

- `pkg/score/score.go`: the scorer's present is `min(high, own + PENDING_WINDOW_S)`, where `high` is the latest record's `t` and `own` the latest `os.presence`, `os.focus` or `os.power`. `FinalBefore` is the slot of `now - PENDING_WINDOW_S`.
- `pkg/score/presence.go`: with no sample, slots start at the later of the first record and `BUCKET_TTL_S` before now. A device counts as never sampling, which gives it whole minutes and SM 5.2's codes for a live slot whose presence is unknown, only when it has no `os.presence`, `os.focus` or `os.power` record at all.
- `internal/agent/scorer/loop.go`: a minute whose latest revision is pending and that a Step's view doesn't hold gets an empty revision, final once `FinalBefore` passes it.

## Expected

- SM 2.1: `unknown` is a slot where "the sampler wasn't running: ... a machine with no desktop to sample, such as a server", and SM 5.2 gives "every slot of a server with no desktop" the codes for a live slot whose presence is unknown.
- DESIGN 3.7 and 6.2 D1: a minute stays pending for `PENDING_WINDOW_S` after it ends, and then it is final.
- SM 5.1: a minute in which an agent ran has a bucket, with its `agent_running_s`.

## Computed

Take an agent that starts at T0, so its `os.focus` is at T0, and runs turns for hours.

1. `own` is T0, so `now` is at most T0 + 900 s and `FinalBefore` at most T0. No minute after T0 becomes final, and none after T0 + 15 minutes is derived.
2. The agent restarts at T1 and writes its next `os.focus`. `now` becomes T1 + 900 s, and with no sample the slots start at T1 + 900 s − 7,200 s. The minutes from T0 + 15 minutes to about T1 − 1 h 45 min are never derived. The pending minutes from T0 to T0 + 15 minutes aren't in the Step's view, so the loop gives each an empty final revision, zeroing its agent time.
3. The window starts `Lookback` before `FinalBefore`, which stays at T0, so it keeps every record since T0 − 6 h and grows until the next start.
4. Because of the `os.focus` records, the device doesn't count as never sampling, so its uncredited seconds are `X.absent` rather than SM 5.2's codes for a live slot whose presence is unknown, and its slots aren't whole minutes.

The same holds on a desktop that gives no idle time, KDE and wlroots among them (`internal/agent/presence/os_linux.go`), where the user is at the keyboard.

## Options

1. **The agent repeats a timed record.** While a project context is live, the agent writes an `os.focus` saying focus is `unknown` every `SLOW_SAMPLE_S`, so `own` keeps up. The scorer's rules stay as they are. But the record would say nothing new each minute, against SM 1.2's "one record with `unknown` each time focus turns unknown". Ledgers written before the change keep the stall. The slots after a silence longer than `BUCKET_TTL_S` still start `BUCKET_TTL_S` before now, so the minutes pending before the silence are still lost. And the device still doesn't count as never sampling.
2. **The scorer's clock reads only the presence sampler's records.** An `os.presence` comes every 15 to 60 s while a project context is live, and an `os.power` comes with one, since a power event takes a sample at once (DESIGN 3.3). In the agent both come from the presence sampler, which records neither on a device with no idle source. An `os.focus` comes only when focus changes, so it says nothing about how far the present has come. On a device with neither, nothing else keeps time, and the latest record does, as it already does for a device with no OS record at all (#219's relayed cases). The same records decide whether a device never samples.

## Proposal

Option 2, which is the smallest rule SM can state, is deterministic from the records, so the server's re-score (DESIGN 6.5, CC6) gets the same result, and also mends ledgers already written once the agent re-derives them.

1. **The clock.** The scorer's present is the latest record's `t`, but no more than `PENDING_WINDOW_S` past the latest `os.presence` or `os.power`, while that record keeps the clock. It keeps it until another record the agent stamps itself, a hook's, one of its own watchers' or an agent app reader's, is dated more than `BUCKET_TTL_S` after it, and the newest record is `PENDING_WINDOW_S` - `READ_HORIZON_S`, 300 s, past that one. An earlier sample keeps the clock the same way while a record that ends its reach waits those 300 s. Log and bridge records don't count, so a skewed transcript time still can't move the clock. With no sampler record, or once the latest one's reach has ended, the present is the latest record's `t`. So a minute is final once a record is dated `PENDING_WINDOW_S` past its end, and on a sampling device also a sample or an `os.power` dated past its end. On a sampling device every `os.focus` comes with a sample at its time (DESIGN 3.3), so this changes nothing there, except after an `os.focus` that comes after the last sample. There `FinalBefore` used to run ahead of the samples, into slots no sample had decided yet, which were then never derived.
2. **Never sampling, slot by slot.** A sample or an `os.power` keeps the slots after it a sampling device's until its reach ends: a record the agent stamps itself, not the sampler's, is dated more than `BUCKET_TTL_S` after it and before the sampler's next record, and the newest record is 300 s past that record. Until then a record of the sampler's dated before it can still arrive and keep the reach, as a resume does that is still on the presence queue when a later-dated stop hook seals its batch, and since the reach keeps the clock (1), nothing after the sample is final meanwhile. So one Step and a Step a batch agree for any record up to 300 s late, the allowance the pending window already leaves past `READ_HORIZON_S` (E-return-lookahead). A slot is a never-sampling device's when the agent wrote some record by a path other than a log reader's, and no record of the sampler's dated before the slot ends keeps sampling there, because there is none or its reach ended. Its `os.focus` records don't count. Such a slot is `unknown`, has no hard break, and takes SM 5.2's codes for a live slot whose presence is unknown, and the derived slots begin and end with whole minutes where they begin and end with such slots, as for #219's server with no OS record. No lock, suspend or gap from before such a stretch reaches the slot of the sampler record that ends it either, so a Step over the agent's window, whose carry drops a record whose reach ended (4), derives that slot as one Step over every record does. The rule reads only records of the sampler's dated before the slot ends, so a device's first sample, or its sampler starting again, changes no slot before it. One Step over every record and a Step a minute then give the same slots across that change, as the Output contract and the server's re-score (CC6) need. A device that sampled and stops, as a desktop reached over SSH after its session ends, waits for its next sample until its agent's own records come `BUCKET_TTL_S` after the last one, and from then on is a never-sampling device from that sample on. A sample dates an input in such a slot, for the slot itself and for an act's evidence test, only when it came within `SLEEP_GAP_S` of the input, as the sample the agent takes at the hook that starts it does, with that prompt's typing just before it. Whatever such an input decides is still pending when its sample comes, so no later sample changes anything already final.
3. **Where the slots start.** They start `BUCKET_TTL_S` before the first record the agent stamped itself, where its own records start, instead of `BUCKET_TTL_S` before now on a device that never samples and before the first sample on one that does. A Step after a silence longer than `BUCKET_TTL_S`, or after a restart, then derives the minutes still pending before it, and the agent's window, a fresh `State` each Step, derives every minute from the window's start. One Step over a never-sampling device's records now gives what a Step a minute gives, which it didn't for streams longer than `BUCKET_TTL_S` (`scoreRelayed`'s old note). A record dated years back by a transcript or the bridge still moves nothing, since neither is a record the agent stamps itself.
4. **The loop's carry.** The carry dates a record it keeps no earlier than `carryGraceMS` before the window, so that the window's Steps see what it says. It no longer does that for a sample or an `os.power` whose reach has ended: it drops it, since dated again it would look like a sample the agent just took, keep the clock and keep the device a sampling one. It keeps the latest record the agent stamped itself among those it folds, to tell. A reach has ended when that record, or one of the window's that comes before the window's first record of the sampler's, is dated more than `BUCKET_TTL_S` after the carried record, as `pkg/score` reads a reach: a record after the sampler's next one ends nothing, so a sampler silence longer than `Lookback` that ends with a sample, or a suspend that long, keeps the carried record. A cut the carry sees has taken effect, since `FinalBefore` stays at a sample while a cut of its reach waits, and the window passes a record only once `FinalBefore` is `Lookback` past it.
5. **No empty final for a minute no Step derived.** The loop gives an empty revision only to a pending minute the Step derived with no credit and no agent time. A pending minute the Step didn't derive at all keeps its latest revision, and stays pending unless a later Step derives it. Once `FinalBefore` passes it, no Step can make it final, and the loop stops looking at it, as `pkg/score`'s `Revisions` already does with a minute it no longer derives. After 3, this happens only to a minute whose records the ledger no longer holds, or that an earlier version left pending.
6. **Version.** Rules 1 to 3 change outputs on such devices, so `pkg/score/VERSION` becomes 0.5.0 (DESIGN 6.6, a 0.x MINOR), and `BuiltinScoringVersion` with it. No timeline's golden changes except in `v`: no timeline has an `os.focus` without samples. The evidence definition 0.4.0 covers 0.5.0, since DESIGN 6.4 doesn't change. PLAN's WP-SC6 takes 0.6.0.

### What SM 2.1 gains

The `unknown` row's rule reads "The sampler wasn't running: no daemon yet (lookback), or a machine whose agent can't sample, such as a server with no desktop or a desktop that gives no idle time (KDE, wlroots)". After the paragraph on hard breaks:

> A machine whose agent can't sample, one with no desktop or with a desktop that gives no idle time (KDE, wlroots), records no `os.presence` and no `os.power`, so every live slot there is `unknown`. The `os.focus` its agent writes as it starts, saying focus is `unknown` (1.2), is no sample. A sample or an `os.power` keeps a machine sampling only so far. Once a record the agent stamps itself, a hook's, one of its own watchers' or an agent app reader's but never a log reader's or the bridge's, is dated more than `BUCKET_TTL_S` after it with no sample or `os.power` between, the machine counts as one that can't sample from that sample on, as when its desktop session ends and the agent runs on. Such a slot has no hard break, and no lock, suspend or gap from before it reaches the slot of the sample or `os.power` that starts the sampler again. That takes effect once the newest record is 300 s past the record that ends the sample's reach: `PENDING_WINDOW_S` - `READ_HORIZON_S`, what the pending window leaves for records that arrive late. Until then the reach holds and no minute after the sample is final, so a sample or an `os.power` dated before that record that arrives in that time, such as a resume still queued behind a stop hook, keeps the machine sampling. Whether a slot is one where the machine can't sample is decided from the samples and `os.power` records dated before the slot ends. A sample dated after such a slot dates an input in it only at most `SLEEP_GAP_S` before the sample, such as the typing of the prompt whose hook starts the agent. So a machine's first sample, or its sampler starting again, changes no minute already final. Where the machine can't sample, its records do what samples do elsewhere. Its slots start `BUCKET_TTL_S` before the first record the agent stamped itself. And a minute is final once a record is dated `PENDING_WINDOW_S` past the minute's end (DESIGN 3.7). A sampling machine also needs a sample or an `os.power` dated past the minute's end, so that a record dated ahead of the clock waits for the samples. The minutes after a sampler stops wait until a record the agent stamps itself is dated `BUCKET_TTL_S` past its last sample, and the newest record is 300 s past that one.

DESIGN's text doesn't change, since the agent records what it recorded before. The rule makes one exception to it: a minute no Step derives stays pending on the device, against DESIGN 3.7's "after 900 s a bucket is `final`" and D1, which D-server-settles-pending settles on the server only.

## Decision

Decided 2026-11-23 by the orchestrator for Karim, on #234, with the review's rulings (#241):

1. The scorer-side rule is taken over repeating a timed `os.focus`. The scorer's clock reads only the presence sampler's records, `os.presence` and `os.power`, and with neither, now is the newest record. The same records decide whether a device never samples. This rescues ledgers already written, records nothing new, and needs no change to DESIGN 3.3.
2. A sampler record's reach is bounded. An `os.presence` or `os.power` keeps the clock, and keeps the device a sampling one, only until a record the agent stamps itself, by a hook, `os` or an app's reader, never a log reader, the bridge or another path whose time comes from outside, is dated more than `BUCKET_TTL_S` after it. Past that, the slots after the sample are a never-sampling device's, and the loop's carry drops a sampler record whose reach has ended instead of dating it again.
3. Never sampling is decided per slot, from the sampler's records dated before the slot and still within their reach, never from a sample dated after it, so a device's first sample changes nothing already final.
4. On a device that never samples, a record dated ahead of the clock moves now, as the first limit below says. DESIGN 7.4's refusal bounds what a submission can carry, not what the device does: the server refuses a record dated more than 5 minutes after its batch's receipt, but on the device such a record still makes the minutes before its time final early, by as far ahead as it is dated. A guard on the device, the ledger writer refusing a record dated more than 5 minutes after it takes it in, is a follow-up after #224.
5. A minute no Step derived stays pending and is never made final from a stale revision. Only a minute a Step derived with nothing in it gets an empty revision.

The fix-verify of #234 added two rulings (#241, comment 7110771624):

6. A cut takes effect only once the stamped record that makes it is 300 s, `PENDING_WINDOW_S` - `READ_HORIZON_S`, behind the newest record. Until then the reach holds, now stays bounded by it, and a sampler record dated before the stamped one that arrives in that time still keeps the reach. This stays in `pkg/score`, with no change to the writer's sealing.
7. The carry applies `pkg/score`'s rule: it drops its latest sampler record only when the carry's latest stamped record is more than `BUCKET_TTL_S` after it, or when a stamped window record dated after that comes before the window's earliest sampler record in record order.

## Limits

- On a device that never samples, a record dated ahead of the device's clock, such as a bridge prompt with a skewed transcript timestamp, moves the present with it, so the minutes before its time become final early, by as far ahead as it is dated, and the records that come after them can't change them. That was already so for a device with no OS record. DESIGN 7.4's refusal of a record dated more than 5 minutes after its batch's receipt bounds what a submission can carry, not what the device does, and a guard on the device waits for a follow-up after #224. Bounding the present by the records pairtime stamps itself, a hook's, an app reader's or an OS watcher's, would also guard against it, but it would stall a device whose only harness records come by a log reader, such as Codex with untrusted hooks, Claude Code with its folder trust pending or a `--bare` run, which is the failure this erratum fixes.
- A machine that samples at some times and not at others, as a desktop reached over SSH while its graphical session is logged out, waits after its last sample until a record its agent stamps itself is dated `BUCKET_TTL_S` past it, and a record 300 s after that one, and then finalizes those minutes as a never-sampling device's. When the record that ends the reach is the newest for hours, as a turn's last stop hook of the evening can be, the minutes since the sample stay pending until the next record, and doctor's stall warning says so meanwhile. A log-only harness on a device that once sampled waits for the next record the agent stamps, such as the `os.focus` at its next start.
- After a long silence, the first Step on a device that never samples derives every slot of the silence once, as a sampling device's first Step after a long suspend already does.
- A minute that the old code gave an empty final revision stays as it is, since a final revision never changes. On a device that ran the old code, the first Step after the upgrade derives every minute from where the scorer stopped, up to the window's records.
