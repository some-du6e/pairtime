# Erratum: SM 6.1's Hackatime figures don't replay from its own timeline

Date 2026-11-19. Raised by WP-FX3. Status: waiting for Karim. No credited second depends on it, and `testdata/timelines/6.1` keeps SM's figures as approximate totals.

## Input

SM 6.1's totals table: "Hackatime-equivalent `logged_s`: about 8,300; of which `ai_logged_s`: about 4,050, each run plus the 120 s gap credit before each prompt, 270 s a cycle; `handbook_s`: about 5,600." The paragraph after it says "pairtime credits about 1.8 times what the handbook rule would allow" and "`ai_ratio` is 5,965 / 4,050 = 1.47". SM 6 calls its Hackatime figures approximate "because they depend on exactly when WakaTime plugins fire".

## Expected

SM 5.3's `logged_s` rule and SM 5.4's `ai_logged_s` rule, applied to the events SM describes, give about these numbers.

## Computed

gen.py replays the window's events under `min(gap, 120 s)`. The editor heartbeats are the ones vscode-wakatime would send for what SM describes (HC 1.5): two at the start of each cycle, where he opens a file, and two for each hand edit, one at his first key, more than 120 s after the last heartbeat, and one at the save.

| | SM, about | Replay | Why they differ |
|---|---|---|---|
| `ai_logged_s` | 4,050 | 3,930 | The first prompt, at 14:04:00, has no agent event before it in the window, so cycle 1 gets its 150 s run and no 120 s gap credit |
| `logged_s` | 8,300 | 7,712 | See the breakdown below. 8,300 needs 553 s a cycle |
| `handbook_s` | 5,600 | 5,092 | `logged_s - ai_logged_s + ai_logged_s / 3` |
| credited / `handbook_s` | 1.8 | 1.98 | |
| `ai_ratio` | 1.47 | 1.52 | |

The breakdown of `logged_s`. A cycle has 80 s between its two heartbeats, 120 s to the prompt, the 150 s run and 120 s after the stop, which is 470 s. A hand edit adds 38 s from his first key at 11:02 to the save at 11:40 and 50 s from the save to the next cycle's first heartbeat, so a hand-edit cycle is 558 s. Two cycles differ. Cycle 7's first heartbeat is the click at 15:12:40, 70 s before its second, so it is 548 s. Nothing in the window follows cycle 15's stop, so it is 350 s. Five cycles at 470 s (1, 3, 6, 9 and 12), eight at 558 s (the hand-edit cycles other than 7), cycle 7 and cycle 15 make 2,350 + 4,464 + 548 + 350 = 7,712.

Getting to 8,300 would take heartbeats in the long gaps, while he reads in iTerm, plays in the browser or commits. VS Code sends none then, because heartbeats need activity in the focused window (SM 3.2), and SM's rows name none.

The heartbeat before the window. The replay doesn't count the 13:57:05 heartbeat, the last record before 14:00:00, because SM 5.3 sums the records in the window. Hackatime's boundary-aware path, which is how Stardance reads a project's hours and which DESIGN D15 follows for `hackatime_logged_s`, pulls in the heartbeat just before the window (HC 1.4). Its gap to the 14:00:30 heartbeat is 205 s, worth 120, so that reading gives `logged_s` 7,832, `handbook_s` 5,212 and credited / `handbook_s` 1.94. No agent event comes before the window, so `ai_logged_s` is 3,930 either way.
