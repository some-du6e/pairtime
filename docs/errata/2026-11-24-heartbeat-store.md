# Erratum: DESIGN 3.5 and 4.4 have no row for the WakaTime heartbeat store that 6.2 D15 keeps 180 days

Date 2026-11-24. Raised by item 6 of #236's list of what WP-AD16 part 2 has to do. Status: decided 2026-11-24 by the orchestrator for Karim (D-ad16-heartbeat-store). Applied to DESIGN 3.5, 4.4, 6.2 D15 and D19, 7.2 and 7.12, and to PLAN's WP-AD16 and WP-SB3, in the docs PR that adds this erratum. docs/retention.json's `device.heartbeats` entry and its `TestDesignPeriods` case come first in WP-AD16 part 2's PR. That test holds retention.json's periods to DESIGN 4.4's rows, so the entry can't land before the row.

## Input

- 6.2 D15 says "The agent keeps `(time, project HMAC, category)` per heartbeat for 180 days, paths for 30." PLAN's WP-AD16 says the same, "for WP-PG11".
- DESIGN 3.5 lists the files the client keeps, and 4.4 gives each kind of data its period. Neither lists this store, so docs/retention.json has no entry for it, and `TestDesignPeriods` would refuse one with days.
- 5.7 replaces paths with per-device HMACs on arrival. The bridge (#236) puts no path, entity or project name in a record and nothing in the vault, so nothing keeps a heartbeat's path for D15's 30 days.
- 5.10 says pairtime keeps no heartbeats on the server, and 4.3 says nothing on the WakaTime path leaves the machine.
- 6.2 D19 says that `logged_s`, `ai_logged_s` "and D15's `hackatime_logged_s`, count only records with `via` in `hook`, `log`, `otel` or `editor`, plus bridge records from heartbeats that passed the peer-process check". A transcript-derived heartbeat with neither `ai_prompt_length` nor `ai_line_changes` above 0 makes no record (5.7), and Hackatime counts it all the same: 3 of the 26 heartbeats the captured `ai-sync` run sent pairtime are such `ai coding` heartbeats (testdata/fixtures/wakatime/2.28.4/linux/ai-sync).
- 8.8 keeps an excluded folder out of pairtime entirely. 4.2 says hours logged in local-only mode "can never be submitted", and the uploader never sends a batch sealed before the computer's link or in a local-only gap (docs/spec/ingest-v1.md section 5).
- Hackatime's sums in testdata/upstream/hackatime/durations.sql select heartbeats by exact project name and read only their time and category. They leave out `browsing`, `meeting` and `communicating` by `LOWER(category)` before they order the heartbeats or pick the one before the window, leave out a heartbeat with no category, and give each gap to the category of the heartbeat that ends it. Hackatime stores a heartbeat with no category as `coding`, or `browsing` for a `domain` or `url` one (`default_category` in testdata/upstream/hackatime/excerpts/app/services/heartbeat_ingest.rb). wakatime-cli v2.28.4 sends plain coding with no category, as the captured dual-send run shows (testdata/fixtures/wakatime/2.28.4/linux/dual-send).
- wakatime-cli v2.28.4's `ParseCategory` (`pkg/heartbeat/category.go` at its tag, `9fee1b464bfb`) takes 21 names and refuses any other: `advising`, `ai coding`, `browsing`, `building`, `code reviewing`, `coding`, `communicating`, `debugging`, `designing`, `indexing`, `learning`, `manual testing`, `meeting`, `notes`, `planning`, `researching`, `running tests`, `supporting`, `translating`, `writing docs`, `writing tests`.
- The endpoint answers 503 while `Accept` fails, and remembers nothing (internal/adapters/wakatime/endpoint.go). wakatime-cli v2.28.4's `SendHeartbeats` sends to its destinations in sorted order and stops at the first that fails, and pairtime's `http://127.0.0.1` line sorts before every `https://` server, so a 503 from pairtime holds back the teen's Hackatime too (the review of #306). DESIGN 1's first principle: "A release that could break a teen's Hackatime doesn't ship."

## Decision

1. **Where.** On the device only, in the data directory, as `heartbeats/YYYY-MM-DD.jsonl`: JSON lines, appended, one file per UTC day of the heartbeat's time, each line with a newline before it as well as after it, as `commits/` writes its lines, so a line a power cut left short can't take the next with it. The agent writes a batch's lines when it passes the batch through `Bridge.Records`, after the batch's folders resolve. `Records` also returns each heartbeat's placement, so the store keeps out exactly what the bridge kept out. A reader beside the writer returns the lines of a range of days. It passes over a line a crash cut short and a line whose `m` doesn't verify, and counts both. Only 6.2 D15's figure reads the store, on the device: WP-SB3 runs WP-PG11's `pkg/wakacompat` over it. The scorer never reads it, so WakaTime's category still credits nothing (5.7).
2. **Which heartbeats.** A heartbeat gets a line, whether or not it made a record, when all of these hold:
   - the endpoint took it, which it doesn't for a replay that `Seen` answers as taken before;
   - its batch passed the peer-process check (`Batch.Peer.Pass()`);
   - it names a WakaTime project, a `project` that isn't empty;
   - the bridge doesn't keep it out of pairtime: a file in a folder out of it, any heartbeat of a session `SessionIgnored` names, and one with no file that such a mark places;
   - its category as item 3 stores it is one of wakatime-cli v2.28.4's 21 names other than `browsing`, `meeting` and `communicating`, which D15 leaves out, so a `domain` or `url` heartbeat with no category, which Hackatime files under `browsing`, gets none;
   - it is dated on `retention.From(now, days)` or a later day, and no more than 10 s, the bridge's `lateRead`, after the agent's clock when its batch came in, so no line lands in a file the sweep would never reach.

   An `ai coding` heartbeat with neither a prompt length nor line changes makes no record and still gets a line, because Hackatime counts it. The writer doesn't judge the mode. In local-only mode, and on a computer that isn't signed in, it keeps lines as it does otherwise, since a heartbeat wakatime-cli queued can reach the agent in a later stretch than the one it was made in. Item 5 keeps them out of every figure.
3. **What a line holds.** Exactly `{"t", "p", "c", "m"}`:
   - `t`, the heartbeat's time in Unix seconds with fractions, as `wakacompat.Seconds` reads it, which is how Hackatime reads it.
   - `p`, its WakaTime project name keyed under `K_session` over a domain of its own, `"w" || hex(HMAC-SHA256(K_session, ascii("pairtime/v1/session/wakatime-project") || 0x00 || part(name))[0:16])`, with `name` the heartbeat's `project` byte for byte as wakatime-cli sent it. It is never the name, and never a plain hash, which a reader could recompute from a guessed folder name.
   - `c`, its category as Hackatime stores it: its own, or `coding` when it has none. A `domain` or `url` heartbeat with none would be `browsing`, and gets no line (item 2).
   - `m`, `"h" || hex(HMAC-SHA256(K_session, ascii("pairtime/v1/session/heartbeat-line") || 0x00 || part(T) || part(p) || part(c))[0:16])`, with `T` the line's `t` exactly as its JSON number is written. The reader counts no line whose `m` fails, so a line added to or changed in a file by hand counts for nothing.

   docs/spec/ledger-v1.md section 3 lists both beside the memory key, and `TestKeys` pins a vector of each. The store holds no path, entity, project name, branch, language, user agent, session, line count or event id. `t` is a time, `c` a name from wakatime-cli's fixed list, `p` an opaque project key keyed per device (AGENTS.md), and `m` a digest of the three. The lines keep the order the endpoint took them in. A replay the endpoint takes again after a restart writes the same line again, which adds nothing to any of Hackatime's sums.
4. **A write never fails the endpoint.** A failed append never fails `Accept` and never changes the endpoint's answer. The ledger's path alone decides that answer, because a 503 from pairtime holds back the teen's Hackatime too. The agent keeps the lines a failed append didn't take in memory, up to 10,000, and appends them with the next batch's. It counts the lines it drops past that bound, and `pairtime doctor` warns about the heartbeat store while any line waits or was dropped since the agent started. Lines still waiting when the agent stops are lost.
5. **Nothing uploads it, and a submission carries only seconds.** No tier-1 upload, project names request, backup or reveal carries a line. When the client first learns that a submission froze, before its next retention sweep, WP-SB3 computes D15's `hackatime_logged_s` and its `ai coding` part from the store with `pkg/wakacompat` (WP-PG11), or the follow-up after both does if WP-PG11 lands later. It keeps the seconds with the batches the metadata reveal covers until the server has stored that reveal, which carries them. The figure leaves out every line dated at a moment whose minutes can never be submitted (4.2): a moment where the uploader's judgement of a commit line (D-ag5-D1) would withhold it, because local-only mode may have seen it, because it comes before the computer's link, or because it falls in a local-only gap. The reveal names the start and end of each span of the window the figure left out, so 7.2's cross-check reads Hackatime's figure over the same time. WP-SB4 copies the figure into `SubmissionTotals`, which gains its fields in `pkg/event` and the schema in the PR that first sends them. Until then SM 5.4's reconstruction stands in, as D15's fallback.
6. **180 days.** That is the submission horizon in 3.5 and 4.4. A submission's window starts no earlier than 180 days before its freeze (DESIGN 7.5 step 2, D-sb1-submissions), so an older heartbeat can't fall in any window D15 computes for. The seconds item 5 keeps need no line past its 180 days, so no submission holds lines the way it holds ledger records. A shorter period would hand most of a long window to SM 5.4's fallback and give honest teens a false `hackatime_mismatch` (7.2). A longer one would keep a to-the-second log of the teen's editor activity that no submission can use. D15's "paths for 30" goes, since the store keeps no path.
7. **What deletes it.**
   - The agent's daily retention sweep, `retention.Sweep` (WP-LG6), deletes a day's file once the day is before `retention.From(now, days)`, as it deletes `buckets/`. `days` comes from docs/retention.json's `device.heartbeats` through `retention.Device()`, as `Periods.Heartbeats`, with `Stores.Heartbeats` (`Drop(from string) (int, error)`), `StoreHeartbeats` ("the WakaTime heartbeats"), a `Swept` count and a line in the package's table.
   - "Delete everything", `pairtime privacy delete`, deletes `heartbeats/` with the rest of the data directory. `wipeKeeps` doesn't change.
   - `pairtime uninstall` deletes it and can't keep it. Its `pairtimeEntries` names it, so it also goes through a linked data directory.
   - Nothing else does. Logging out, local-only mode, unlinking a program, removing the device on the dashboard and excluding a folder later leave it. The lines name no folder, so the sweep takes those.
8. **What the teen sees.** `pairtime privacy show` prints the next upload byte for byte. No upload carries a line, so it shows nothing of the store, and its text stays as it is. `pairtime privacy delete`'s usage lists "what pairtime keeps of your WakaTime heartbeats" among what it deletes. The dashboard's Privacy page and /privacy list the store from docs/retention.json's entry, and no other sentence changes.
9. **Forging.** A client that reads `K_session` off the device can write lines whose `m` verifies, and deleting lines can move part of the real total into `ai coding`. The new 7.12 row says what bounds that.

| Path | Format | Holds | Kept |

| `heartbeats/YYYY-MM-DD.jsonl` | JSONL, appended, a file per UTC day of the heartbeat's time | A line for each WakaTime heartbeat the endpoint takes that passed the peer-process check (5.7), names a WakaTime project and isn't kept out of pairtime (8.8), whether or not it made a record. The line holds its time as Hackatime reads it, its project name as an HMAC under `K_session` over a domain of its own, its category as Hackatime stores it, `coding` for none, and an HMAC of those three under `K_session`, so the agent counts no line it didn't write. Nothing of it is uploaded, and a submission carries only the seconds D15 computes from it (docs/errata/2026-11-24-heartbeat-store.md) | 180 days, the submission horizon |
