## Decision

Decided 2026-11-20 by the orchestrator for Karim, with [the presence-start erratum](2026-11-19-presence-start-after-silence.md). Its decision and this one's gave different rules for where presence starts after a silence. The orchestrator's ruling of 2026-11-20 takes the presence-start erratum's rule, with 6.4's 23:37:12.7 move re-timed to 23:37:15.5, and keeps this decision's focus at the act and its open question 2. This decision's own start rule, from the start of the slot with two exceptions, doesn't apply.

1. A tail ends `PRESENCE_TAIL_S` after the last input, to the millisecond. In the slot whose input ends a run that isn't bridged, because the run is longer than `PRESENCE_GAP_S` or has no input before it, presence starts again at the second holding the earliest key or pointer input that any sample reports in that slot. Run lengths stay in whole slots, and every other slot with input counts from its start, including the first slot after a hard break. The sample at 15:12:40 shows the click, not that nothing came before it; SM 2.1 takes the switch as his return because it is the first input a sample reports in that slot. So 6.1 keeps every row and total. SM 2.3's presence tests count a slot with input as present from its start.
2. Question 2 stays open. The decision left it with point 3 of [the 6.6 uncredited-codes erratum](2026-11-19-sm-6.6-uncredited-codes.md), whose own decision, applied by #271, says only that minutes in which the script only sleeps have no bucket (SM 5.1), not whether SM's totals count such seconds. So 6.1 keeps `X.absent` 330 stated, with 90 in buckets.
3. An evidence test that names focus reads the window in front at the act, and a slot's longest focus decides only where windows are realized, lookups and attribution. For the click that is VS Code (SM 2.3), although iTerm held the slot from 15:12:30 longest, 10 s to VS Code's 5 (SM 2.5), so the click stays a NAV anchor.
