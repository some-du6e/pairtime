# Erratum: Claude Code reports a failed tool call, such as a test run that exits non-zero, only to PostToolUseFailure

Date 2026-11-20. Raised by WP-AD2, from the review of #115 (#139). Status: decided 2026-11-23 by the orchestrator for Karim: Reasoning 1 to 3, with `PostToolUseFailure` installed right after `PostToolUse` under the same matcher; in a session its hooks cover, the transcript reader writes no Edit, Write or Bash call but one the person cancelled; and a test or build command that ran in the foreground to its end and fired `PostToolUse` has `exit_code` 0. The Decision section below has the rest.

## Input

- Claude Code's hooks reference (code.claude.com/docs/en/hooks, read 2026-11-20). `PostToolUse` "runs immediately after a tool completes successfully". `PostToolUseFailure` "runs when a tool that started executing fails: the tool threw an error, or an MCP tool returned an error result". It doesn't fire for a call rejected before it ran: an unknown tool, input that fails validation, or a permission denial. Its input is `PostToolUse`'s `tool_name`, `tool_input` and `tool_use_id`, with `error`, `is_interrupt` and `duration_ms` in place of `tool_response`. For Bash, "a command that ran and exited produces a first line `Exit code N`, then any output the command produced as one block with stdout and stderr interleaved", and the reference's own example is a failed `npm test`. Claude Code middle-truncates a long error around a `... [N characters truncated] ...` marker and can insert lines of its own, such as `Command timed out after 2m 0s`. `is_interrupt` is true "when the failure reached Claude Code as an abort rather than as an error the tool reported. Cancelling a running tool does not fire this hook; the tool result carries the interruption message instead", and the reference says to key a hook on `tool_name`, `is_interrupt` and the `Exit code N` line and to treat the rest as display text.
- HS 3.1 lists `PostToolUseFailure` beside `PostToolUse`, and the hooks notes have `PostToolUse` fire when a "Tool call succeeded" and `PostToolUseFailure` when a "Tool call failed" (`docs/research/notes/signals.md`).
- WP-AD1's Claude Code 2.1.327 capture has no `PostToolUseFailure`, because pairtime doesn't install it, and every Bash call in it exited 0. Step 8's tests and the subagent's runs went through `| tail`.

## Expected

DESIGN 5.1's Claude Code row installs `PostToolUse` with matcher `Edit|Write|Bash`, and no `PostToolUseFailure`. SM 4.2 reads error signatures "from agent tool output (test and build runs)" and counts "a test or build command whose outcome changed" as a change event. SM 2.4 fills the reading bucket with the lines a run shows.

## Computed

With DESIGN 5.1's hooks, a failing `pytest` or `go test` that the agent doesn't pipe makes no `agent.tool`: no `tool_class` `test`, no `error_sig`, no `visible_output_lines`, no `t_start` or `t_end`. Failing runs are what SM 4.2's loops are made of, so the hook path misses them every time. A run the person cancels makes no `agent.tool` even with `PostToolUseFailure` installed, since cancelling doesn't fire the hook. Its interrupt is in the transcript, which is WP-AD3's to read.

## What the adapter does

`internal/adapters/claudecode` reads `PostToolUseFailure` for Edit, Write and Bash as it reads `PostToolUse`, and lists it in `Events` and `Sources` under the same matcher. A failed command is `agent.tool` with its class and `cmd_hash`. It has `exit_code` N from the error's `Exit code N` line, and the output after that line gives its `visible_output_lines` and `error_sig`, which equals the signature a `PostToolUse` with the same output gets. An error with no exit-code line, as when the shell didn't start, has no `exit_code`, and its message counts as what the call showed. An aborted call, with `is_interrupt` true, shows Claude Code's text rather than the command's, so it has no `exit_code`, no visible lines and no `error_sig`: an abort message such as `AbortError: The operation was aborted` would otherwise read as an error signature, which SM 4.2 counts. A failed edit changed nothing, so it is `agent.tool` with its class and no file or lines. Naming its file would let DESIGN 5.7 take the person's next edits of that file, within 120 s, for the agent's. `testdata/gen_expected.py` does the same.

## Reasoning

1. DESIGN 5.1's Claude Code row should add `PostToolUseFailure`, matcher `Edit|Write|Bash`, after `PostToolUse`. `internal/install`'s `claudeHooks` and its goldens follow, and `internal/agent/hookpath`'s `native` map gives it `agent.tool`, as it gives `PostToolUse`, for presence.
2. `pkg/event`'s `agent.tool` has no field that marks a failure without an exit code: a failed edit, an abort, or a shell that didn't start. `exit_code` covers commands that ran. Until the scorer needs more, those failures are `agent.tool` records without `exit_code`, and a failed edit's has no file and no lines.
3. WP-AD1 should rerun step 8 with a test command that exits non-zero and isn't piped, so that a capture holds a `PostToolUseFailure` and the adapter's expected records cover it.

## Decision (E-cc-tool-failure)

1. Reasoning 1 to 3 stand. DESIGN 5.1's Claude Code row installs `PostToolUseFailure` right after `PostToolUse`, under the same matcher, `Edit|Write|Bash`, and the two tool hooks keep one matcher from now on. Existing installs get the new hook at their next `pairtime install`, which both install scripts run unless told not to, and until then doctor warns that it is missing. The install doesn't wait for a capture, as `StopFailure`'s didn't.
2. Since #176 the transcript reader writes failed Edit, Write and Bash calls in hooked sessions too, so a failing run already reaches the scorer wherever Claude Code writes a transcript. Computed above predates #176. The hook is still the better source. Its fields are documented, the hooks reference says to add it for calls that fail, and it arrives as the call ends. A transcript's failure entry has a format no capture shows yet. Where file notifications lag, it reaches the agent up to `HotPoll` (5 s) late, or up to `QuietPoll` (30 s) late after a call that ran longer than `QuietAfter` (2 min). It is missing where Claude Code writes no transcript (HS 3.2). And with the hook, a hooked session no longer takes failed runs from a file any process can write to.
3. From `session.nativeAt` on, the transcript reader writes no Edit, Write or Bash call but one the person cancelled. `PostToolUse` reports a call that succeeded and `PostToolUseFailure` one that ran and failed, and a call refused before it ran gets a record from neither. A call the person cancels with Esc fires neither hook, so the reader writes it, as `agent.tool` with its class and command and nothing from its output: no `exit_code`, no lines and no `error_sig`. So every call that ran counts once, and a cancelled command still reaches the git watcher. Until a capture pins its form, a cancelled call is a tool result with `is_error` true whose text is Claude Code's interruption message, `[Request interrupted by user for tool use]`, or a Bash result with `interrupted` true. The reader's memory of the hooks' calls (`postedNative`) stays as a second guard but can't replace the rule: a kill can lose that memory while the tailer reads the line again, and a failure counted twice counts its error signature twice toward `SAME_ERROR_LIMIT`. Lookback, `--bare` and other sessions no hook reported keep every call from the transcript. Lookback writes only lines dated before the ledger began, when no pairtime hook ran (#177), so the rule never applies there.
4. Claude Code counts a Bash command's non-zero exit as a failure, except exit 1 from `grep`, `rg`, `egrep`, `fgrep`, `find`, `diff`, `test`, `[`, `git diff` and `git grep`, and reports a failure to `PostToolUseFailure`, not to `PostToolUse` (the tools and hooks references, read 2026-11-23). So the adapter gives a Bash call of class `test` or `build` `exit_code` 0 when its `PostToolUse` has a `tool_response` object, that object isn't marked `interrupted` and names no background task (no `backgroundTaskId`, and no `... was moved to the background` notice), and its `tool_input` doesn't set `run_in_background`. A `PostToolUse` hook from managed settings, which also runs after some failed calls, gets the error as a string `tool_response` and so no `exit_code`. The transcript reader does the same for a result without `is_error`. Every live Claude Code timeline already has this shape, such as SM 6.1's cycle-11 run and `4.2-same-error`'s pass at 16:20:25, so SM 4.3 reads Claude Code's exit status as it reads any harness's. A piped run's status is the pipeline's, as with every harness. A record with no `exit_code` is neither a pass nor a fail: a background start, a cancelled call, an abort and a failure with no `Exit code N` line have none. Bash calls of other classes get no `exit_code` when they succeed, since SM 4.2 and 4.3 read only test and build outcomes and a search's exit 1 is a valid result there.
5. Known losses. A session whose settings hold pairtime's hooks without `PostToolUseFailure` records no failed Edit, Write or Bash call while its hooks report it, as one without `PostToolUse` records no successful one. That covers an install that kept the old set, through `install.sh --no-install` or the Claude Code item unticked at a reinstall, and one whose hook was taken out by hand. Doctor warns about the missing hook. A failure the spool delivers during an agent outage is lost in such a session, as a spooled success already is (DESIGN 5.2).
6. The hook gate is unchanged. `footprint.yml` times one call, and each Edit, Write or Bash call that ran fires exactly one of `PostToolUse` and `PostToolUseFailure`.
7. No number moves. No SM number, timeline or `pkg/score` version changes, since the timelines already model Claude Code's failed runs with their exit codes and its test and build passes with `exit_code` 0. The 2.1.327 capture's expected records gain `exit_code` 0 on its four test runs, from hooks 000033, 000042, 000045 and 000075, all piped through `tail`.
8. Owners. The code is one WP-AD2 follow-up PR. WP-AD1's next Linux CLI capture adds an unpiped step 8 and steps 24 to 26, which pin a cancel's form and what a background start's result holds. WP-SC6 reads `exit_code` as SM 4.3 says.
9. Raised alongside: E-cc-powershell-tool (`docs/errata/2026-11-23-claude-code-powershell-tool.md`), which this decision doesn't settle.
