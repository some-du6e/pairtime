# Erratum: a desktop stops sampling while T3 Code waits for a phone message, so the message's minutes read as slept through

Date 2026-11-23. Raised by the review of #219 (issue #221). Status: decided 2026-11-23 by the orchestrator for Karim (D-relayed-context): DESIGN 3.3's project context gains "an agent app that drives sessions, such as T3 Code's server, is running", so the presence sampler keeps sampling while relayed credit is possible. The agent's project-context test counts a running agent app's server the way it counts a running harness. Amended the same day by the rulings on the review of #222 (issue #225, finding 4, finding 7 and Q15): while an agent app alone keeps the context live, presence samples once a minute whatever the input, and focus records nothing about the window in front; T3 Code runs when the agent's process scan finds its server and its store has both its `-wal` and `-shm` files; and T3 counts only while the reader can read its store. Amended again the same day by the orchestrator for Karim (D-relayed-sleep), which decides the question that amendment raised (below): relayed credit reads a slot as slept through only across a suspend or a gap between samples of more than 120 s. Its rider, D14's cadence for a context an agent app alone keeps live on a desktop whose focus is unknown, is deferred to WP-SC8, so for now the once-a-minute cadence holds on every desktop. Amended a third time the same day by the orchestrator's rulings on the review of #222 after D-relayed-sleep (below): the process scan doesn't count a harness process whose chain classifies as `parent_class` `agent_app`, such as the Claude Code T3 keeps running in a thread between its runs, and the known limit of a T3 run from its source as `node` says what happens to its messages. DESIGN 3.3, SM 2.1, `pkg/score`, the agent and their tests take the change together, in the PR that adds this file (WP-ADE1, PR 3, #222).

## Input

- DESIGN 3.3's `presence` row samples only while a project context is live: a harness session process runs, a terminal, editor or agent app had focus in the last 600 s, or a checked editor heartbeat came in the last 600 s. Outside one, nothing is sampled or recorded (D14).
- SM 2.1, as `pkg/score` reads it: a gap between two samples longer than `SLEEP_GAP_S` (30 s) is sleep, unless the first of them showed `CONTEXT_IDLE_S` (600 s) with no input and the gap is at most the 120 s that sampling once a minute leaves. A slot a sleep covers takes no credit, and its seconds are `X.absent`.
- SM 2.2 rule 9 and 2.3: a message a person sent from T3 Code's phone app, `client` `mobile`, credits its typing lead before the app's stamp, and the session's reading after the turn it started, at level C, in any slot that isn't asleep, whatever this device saw of the person.
- T3 Code's server isn't a harness process, so the process scan counts nothing for it. The Claude Code it drives fires hooks only once a message's run has started.

## What happens

The person leaves the desktop with T3 Code's server running and sends messages from the phone. Once 600 s pass with no focus on a terminal, editor or agent app, no hook and no running turn, the context ends and the sampler stops. The next message's run starts a turn, whose prompt hook makes the context live again and takes a sample. The message's lead ends at the app's stamp, a moment before that sample, so it falls in the stretch with no samples. `pkg/score` reads that stretch as sleep: the lead earns nothing and its seconds are `X.absent`. Reading after a turn's stop goes the same way once the hook's 600 s have passed.

A server never samples, so `pkg/score` derives its whole minutes from the records, and there the same message earns its lead (D-relayed, `t3-away`). A desktop earns less for the same message than a server does, because it samples.

Expected: while T3's server runs, the desktop keeps sampling, once a minute after 600 s with no input, which the scorer tells apart from sleep. A phone message's lead and reading then earn level C credit, as on a server.

## Why

D14 stops sampling outside a project context so that pairtime never records general computer use. A running agent app is a place where work can arrive at any moment, from a device pairtime doesn't run on. While it runs, relayed credit is possible, and only samples tell the scorer an awake machine from a sleeping one.

Relayed credit reads neither focus nor this device's input (SM 2.3), so while the app is the only sign of a context, a sample a minute is all pairtime takes. The first text of this decision kept the usual cadence and the focus component there too, and the review of #222 found what that cost. T3's background service restarts whenever it stops (T3 d8f3feff, apps/server/src/cloud/bootService.ts:116, 180), so for its users the app's context was live from login to logout. Every 15 s while there was input, pairtime wrote a presence sample, and it wrote an `os.focus` record for each app the person switched to, kept 180 days: browsing, games, anything outside a project. The amendment leaves a sample a minute, whatever the person does, while T3 runs and nothing else keeps a context, and nothing about which app is in front. A harness session left running costs more: a sample every 15 s while there is input, and the window in front. The amendment's sample a minute holds on every desktop for now, whether or not pairtime can tell which window is in front (D-relayed-sleep, below).

## Decision

D-relayed-context, as the Status line says, with #225's amendment and D-relayed-sleep (below).

## What changes

- DESIGN 3.3's `presence` row lists "an agent app that drives sessions, such as T3 Code's server, is running" among the signs of a project context, by the `apps` row's test. While a running agent app is the only one of those signs, presence takes one sample every 60 s whatever the input, a focus change takes no sample, and the focus component records nothing about the window in front, no `os.focus`. With the app's own window in front, focus on an agent app is a sign of its own, and the usual rules apply. A harness session whose `parent_class` is `agent_app`, such as the Claude Code T3 keeps running in a thread between its runs, or one typed into T3's own terminal, is a sign only by its hooks: the process scan doesn't count its process, which the app's own sign covers (below).
- DESIGN 3.3's `apps` row: T3 Code runs when the agent's last process scan found an `app_server` process of this user, or of any session on Windows, where T3's scheduled service may run outside the user's session, and the store the reader picks has both its `-wal` and `-shm` files. A failed scan counts no process. T3 counts toward the context, and toward the reader's 10 s cadence, only while the reader can read its store: `sqlite3` on PATH, with JSON functions, and a schema the probe passes. The first text counted T3 whether or not `sqlite3` was there and whether or not the probe passed, though then no relayed credit is possible. `doctor`'s warning that no session T3 started has reached pairtime uses the same test.
- The agent: the apps component tells presence how many agent apps run (`presence.Sampler.AgentApps`), as the process scan tells it how many harness session processes run (`HarnessProcesses`), leaving out each one whose chain classifies as `parent_class` `agent_app` (`procs.Options.Running`), and any one makes the context live. The scan also hands the apps component what it listed (`procs.Options.Listed`), in which `t3code.ServerIn` looks for T3's server, and the reader says whether T3 runs from that and its store's files (`t3code.Status.Running`). The apps component checks on every read, every 10 s while T3 runs and every minute while it doesn't, so the context goes live within a minute of T3 starting and ends within a minute of it stopping. Presence says when an agent app alone keeps the context live (`presence.Status.AppOnly`), and the focus component then records nothing. A harness process the scan finds while the app alone keeps the context live brings the 15 s cadence back with a sample at once, as a hook or a project app's focus does.
- SM 2.1 and `pkg/score`: relayed credit reads a slot as slept through only when it overlaps a suspend or a gap between samples of more than twice `SLOW_SAMPLE_S`, whatever D14 makes of the gap (D-relayed-sleep, below). `pkg/score` keeps that apart from a slot's `asleep`, which still makes the hard break for every other window unless slow sampling explains the gap (D14), and takes the 120 s as twice `SLOW_SAMPLE_S` on its own, not from D14's bound, so it can't drift from SM 2.1 under a later table. A slot slept through is `asleep` too. `Slot` keeps the two apart in a field its JSON leaves out, so the JSON doesn't change, and under every parameter table so far twice `SLOW_SAMPLE_S` is also D14's bound, so taking the 120 s apart from that bound moves no output. The rule itself does move relayed credit: a phone message's lead in once-a-minute minutes with input now earns it. No timeline of the regression corpus has such a lead (Version, below).
- Tests: the presence gate and the sampler keep sampling past a terminal's 600 s while an agent app runs, and stop at the 600 s without one. A context live only through T3 gives one sample a minute and no focus record, whatever the input, unknown focus included, and with T3's window in front the usual rules apply. The apps component makes the context live on a read that finds T3 running with a store it can read, and makes none on one that finds T3 stopped, no store, no `sqlite3` or a schema the probe refuses. A `sqlite3` without JSON functions slows the reader to once a minute. Leftover `-wal` and `-shm` files with no server process, T3's server with its files, and another user's server each have a case. `pkg/score` credits a phone message's lead in minutes sampled once a minute with no input, and none in a stretch with no samples. D-relayed-sleep adds its cases below, and so do the rulings on T3's own Claude Code.

## What stays

- The process scan counts harness session processes alone for presence, and of those not one whose `parent_class` is `agent_app` (below). T3's server has the app table's `app_server` role, which the scan finds without counting it as a harness. A process name proves nothing, since a script can set its own (DESIGN 5.1), and the files alone don't say T3 runs, since a T3 that was killed while it held its store, or that stopped during one of the reader's runs, leaves both behind (docs/errata/2026-11-23-t3-reader.md, item 16). So T3 runs only with both. The reader still checks both files before every `sqlite3` run, and still picks the store by them.
- A T3 run from its source as `node` isn't in the app table, so it doesn't run by DESIGN 3.3's test and keeps no project context of its own, a known limit. The Claude Code it runs classifies under `node` as `script_runtime`, so the process scan counts it as any harness process, and the agent never asks the reader about its prompts. Its messages are read only once a minute, which is as long as `RELAY_SEEN_LAG_S`, so some age out and the rest pair with nothing, and `doctor` says pairtime doesn't recognize T3's server (below).
- With no agent app running and no other sign of a context, nothing is sampled.
- With any other sign of a context, D14's cadence holds as before: after 600 s with no input and no running turn, one sample a minute.
- Unknown focus changes no cadence: a context an agent app alone keeps live takes one sample a minute on every desktop until WP-SC8 (below).
- For every window but a relayed anchor's, a gap between samples longer than `SLEEP_GAP_S` is still a hard break, unless slow sampling explains it (D14).

## One sample a minute, against SM 2.1's sleep gap (D-relayed-sleep)

#225's amendment raised one question. The orchestrator decided it for Karim on 2026-11-23, after one challenger (D-relayed-sleep). The same day, its rulings on the implementation added a clause to SM 2.1's sentence and deferred the decision's rider to WP-SC8 (below).

- **The question.** The amendment samples once a minute whatever the input. SM 2.1, as `pkg/score` read it (Input above), took a gap of more than 30 s as sleep unless the sample before it showed 600 s with no input. So while T3 alone kept the context live and the person used this computer, or for the first 600 s after they stopped, every gap read as sleep. The slots were asleep, and relayed credit there earned nothing, since it is realized in a slot of any presence but one the machine slept through.
  - Input: T3's server runs, a browser is in front, and nothing else has kept a context live for 20 minutes: no harness process, no hook, no terminal, editor or agent app in front. The person types a 90-character message into T3's web client in that browser, stamped at 12:00:00. Presence samples at 11:58:00, 11:59:00 and 12:00:00, and each shows input a few seconds before it.
  - Expected, by D-relayed-context: the message is relayed, since no window here hosts its session at the stamp, and its lead, 90 / 1.5 = 60 s from 11:59:00, earns 60 s at level C with `via_relay`. So does a phone message sent within 600 s of the person leaving such a desktop.
  - Computed with the amendment: both gaps before the stamp read as sleep, so the lead earned 0 s. The message's run starts a turn whose hooks bring back the 15 s cadence, so the reading after its stop is sampled as before.
- **Decided.**
  1. Relayed credit, SM 2.3's relayed leads and SM 2.4's relayed reading, reads a slot as slept through when it overlaps a suspend that `os.power` records, from a `suspend` to its `resume` or the next sample, or from the last sample to a `resume` with no `suspend` before it, or a gap between consecutive samples longer than twice `SLOW_SAMPLE_S` (120 s). A shorter gap, such as the minute between samples while an agent app alone keeps the context live, is a hard break for every other window, unless slow sampling explains it (D14), but not for relayed ones. SM 2.1's relayed sentence says so, in the challenger's words with that clause, which the orchestrator's rulings on the implementation added.
  2. While an agent app alone keeps the context live, presence samples once a minute whatever the input, and records no `os.focus`. The decision added a rider for a desktop whose focus is unknown, as GNOME on Wayland without the extension, KDE and wlroots are. T3's own window can't be told from other use there, so presence would sample at D14's cadence, every 15 s with input or a running turn and every 60 s after 600 s with neither, still with no `os.focus`. A message typed in T3's window that passes rule 6 or 7 would then keep its lead and its reading.
  3. The rider is deferred to WP-SC8. Until WP-SC8 lets unknown focus pass rule 6, the rider costs 15 s samples and earns nothing. A message typed in T3's window on those desktops falls to rule 9, which the 120 s rule in (1) realizes at one sample a minute, so holding the rider loses no credit. So for now an agent app alone samples once a minute on every desktop, focus known or unknown, with no `os.focus`, and DESIGN 3.3's `presence` row, the privacy notice and the local Privacy page say so. PLAN's WP-SC8 takes the rider with rule 6's pass. The presence gate would then follow the last focus report, so a brief unknown, as on Windows' secure desktop or while an X11 connection is re-made, would switch the cadence until the next window report.
  - So the question's message earns its 60 s lead at level C with `via_relay`: the gaps before its stamp are a minute each. A gap of more than 120 s with no `os.power` record, as where logind is missing, still reads as slept through, and so does a stretch with no samples.
- **Why not the alternatives.**
  - Reading only `os.power`'s suspends as sleep for relayed credit, as the challenger first proposed, fails open. Sleeps with no `os.power` record are real: no context yet when T3 starts, Linux without logind, Windows Modern Standby, which is unverified, reboots and crashes. It would also reverse the decided case of a stretch with no samples, which credits nothing. The 120 s bound keeps that case.
  - Sampling every 15 s with input wherever T3 alone keeps the context live fails on privacy: #225's privacy lens ruled out 15 s samples all day under an always-on T3 where focus shows the person is elsewhere. It would stay only where focus is unknown, which is the rider WP-SC8 takes.
  - A mark on `os.presence` that says an agent app alone kept the context live is an event-model change that the two rules above make unnecessary.
- **Tests.** `pkg/score`'s TestRelayedPresence: minutes sampled once a minute with input realize a phone message's lead; a message typed into T3's web client in a browser here is relayed and realized in the same minutes; a gap over 120 s with no `os.power` record reads as slept through, and a gap of exactly 120 s doesn't; a suspend inside a once-a-minute gap is slept through from the suspend to its resume, and so is a resume with no suspend from the sample before it; the stretch with no samples stays `X.absent`; a typed prompt's lead in the same minutes stays behind the hard break; and a Step a minute, and the records DESIGN 6.5 reveals, give the same relayed seconds. TestPresence: a slot in a 60 s gap after a sample with 5 s of idle is asleep but not slept through, and one in a 121 s gap is both. TestSleptGap, under a table whose D14 bound is 180 s: a 150 s gap after 600 s without input is slept through and asleep, and a 120 s one is neither. The presence gate: an agent app alone samples once a minute whatever the input once 600 s have passed since the last project app's focus and hook, and a project app's focus, a hook or a harness process brings the 15 s cadence back at once, with a sample, which the sampler's tests check for a harness process, a hook and T3's own window. The focus component writes no `os.focus` while an agent app alone keeps the context live, unknown focus included, and a change to a project app is written and ends that. The rider's gate test, 15 s samples with input where focus is unknown, goes to WP-SC8 with the rider.
- **Version.** One `pkg/score` bump with #225's Q4 and Q7, PATCH if no golden moves and MINOR if one does (DESIGN 6.6). No golden moves: of the timelines with relay records, only `relayed/t3-here` has a gap the rule changes, 80 s at its start, and its one prompt is `human_typed`, so nothing relayed meets it. The bump stays 0.4.1.
- **Follow-up, not #222.** The scorer dates a gap's end inside its slot, as `markStarts` does, so that a return after a stretch with no context keeps its slot and its bridge. That was the challenger's second item, and it is on main too. It is issue #252, for the next `pkg/score` slot.

## T3's own Claude Code, and a T3 run from its source (rulings on the review of #222)

The review of #222 after D-relayed-sleep found two places where the code and this decision parted. The orchestrator ruled on both on 2026-11-23.

- **T3's own Claude Code.** The process scan counted every harness process of this user for presence, hooked or not. T3 runs `claude` as each thread's session and keeps that process between runs: in the capture, one session took 27 prompts over 1,227 s with one process and no `SessionEnd`. So once T3 had run a thread, its Claude Code was a sign of work for as long as T3 kept the process, with 15 s samples while there was input and an `os.focus` for each app the person switched to. The privacy notice said less than pairtime recorded.
  - Decided: the scan counts only the harness processes whose chain doesn't classify as `parent_class` `agent_app` (`platform.Classify`, which the scan already ran for the sessions it reports, and now runs once a scan for each harness process it counts, and for no other process). T3's own count, from the apps component, keeps the context live at the slow cadence. A claude typed into T3's own terminal drops out too, since the chain skips the shell and lands on T3's server (#225 Q12). Its hooks still make a context, as any hook does, and so does T3's own window in front, on a desktop where the desktop app owns it. In T3's web client the window is the browser's, so there only the hooks do.
  - It costs no credit: hooks still sample at once during runs, and the slow cadence is what the amendment chose.
  - Leaving these processes out can only lower what pairtime records, with fewer samples and no `os.focus`, so there is no fraud angle.
  - DESIGN 3.3's `presence` row, the privacy notice, the local Privacy page and `doctor`'s T3 Code line say the same thing: while T3 runs and nothing else keeps a context, one sample a minute and nothing about the app in front. The Claude Code T3 keeps open between messages is no sign of work, but a reply it's writing is, and so is T3's own window in front, until 600 s after the reply ends or focus moves away.
  - Tests: in TestScanCountsRunningHarnesses (internal/agent/procs), a claude that T3's server or its desktop app started doesn't count, hooked or not, nor does one typed into T3's terminal; the same claude under a terminal counts, and so does one that a script under T3's server runs. TestProcsUnderAnAgentApp (internal/agent) wires the scan to presence and focus as the agent does: with T3 running, such a claude alive with no input leaves one sample a minute and no `os.focus`, and the same claude under a terminal gives the usual context, 15 s samples and `os.focus` records. With the claude in T3's terminal, T3's own window in front and a hook from that claude each make a context of their own.
- **A T3 run from its source.** The known limit said such a T3's messages were still read when a prompt's hook asks. Its sessions classify under `node` as `script_runtime`, so the agent never asks the reader about their prompts. Its messages are read only once a minute, which is as long as `RELAY_SEEN_LAG_S`, so some age out and the rest pair with nothing, and `doctor`'s warning that none paired blamed the hooks.
  - Decided: the limit says so (What stays), and so do DESIGN 3.3's `apps` row and the code's comments. When none of the day's messages paired and none was read while the agent's process scan found T3's server, `doctor` says pairtime doesn't recognize T3's server, as with one run from its source under `node`, instead of blaming the hooks. The reader counts the messages it read while T3 ran (`t3code.Counts.WithServer`, `with_server` in `GET /v1/status`), so a T3 that has stopped since still gets the right warning. The line names no command line, path or argument, since the scan reads none and `doctor --report` can be shared.
  - Tests: TestRunning (internal/adapters/t3code) counts a message read with T3's server and not one read from files alone, and TestT3Line (internal/agent/doctor) has the warning for messages read with no server, while T3's store is open, once T3 has stopped, and beside a home of its own, and the hooks' warning when some were read with the server.
