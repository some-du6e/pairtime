# Erratum: a desktop stops sampling while T3 Code waits for a phone message, so the message's minutes read as slept through

Date 2026-11-23. Raised by the review of #219 (issue #221). Status: decided 2026-11-23 by the orchestrator for Karim (D-relayed-context): DESIGN 3.3's project context gains "an agent app that drives sessions, such as T3 Code's server, is running", so the presence sampler keeps sampling while relayed credit is possible. The agent's project-context test counts a running agent app's server the way it counts a running harness. Amended the same day by the rulings on the review of #222 (issue #225, finding 4, finding 7 and Q15): while an agent app alone keeps the context live, presence samples once a minute whatever the input, and focus records nothing about the window in front; T3 Code runs when the agent's process scan finds its server and its store has both its `-wal` and `-shm` files; and T3 counts only while the reader can read its store. DESIGN 3.3, the agent and their tests take the change together, in the PR that adds this file (WP-ADE1, PR 3, #222). One question the amendment raises is left open below.

## Input

- DESIGN 3.3's `presence` row samples only while a project context is live: a harness session process runs, a terminal, editor or agent app had focus in the last 600 s, or a checked editor heartbeat came in the last 600 s. Outside one, nothing is sampled or recorded (D14).
- SM 2.1, as `pkg/score` reads it: a gap between two samples longer than `SLEEP_GAP_S` (30 s) is sleep, unless the first of them showed `CONTEXT_IDLE_S` (600 s) with no input and the gap is at most the 120 s that sampling once a minute leaves. A slot a sleep covers takes no credit, and its seconds are `X.absent`.
- SM 2.2 rule 9 and 2.3: a message a person sent from T3 Code's phone app, `client` `mobile`, credits its typing lead before the app's stamp, and the session's reading after the turn it started, at level C, in any slot that isn't asleep, whatever this device saw of the person.
- T3 Code's server isn't a harness process, so the process scan counts nothing for it. The Claude Code it drives fires hooks only once a message's run has started.

## What happens

The person leaves the desktop with T3 Code's server running and sends messages from the phone. Once 600 s pass with no focus on a terminal, editor or agent app, no hook and no running turn, the context ends and the sampler stops. The next message's run starts a turn, whose prompt hook makes the context live again and takes a sample. The message's lead ends at the app's stamp, a moment before that sample, so it falls in the stretch with no samples. `pkg/score` reads that stretch as sleep: the lead earns nothing and its seconds are `X.absent`. Reading after a turn's stop goes the same way once the hook's 600 s have passed.

A server never samples, so `pkg/score` derives its whole minutes from the records, and there the same message earns its lead (D-relayed, `t3-away`). A desktop earns less for the same message than a server does, because it samples.

Expected: while T3's server runs, the desktop keeps sampling, once a minute after 600 s with no input, which the scorer tells apart from sleep. A phone message's lead and reading then earn level C credit, as on a server.

## Why

D14 stops sampling outside a project context so that pairtime never records general computer use. A running agent app is a place where work can arrive at any moment, from a device pairtime doesn't run on. While it runs, relayed credit is possible, and only samples tell the scorer an awake machine from a sleeping one.

Relayed credit reads neither focus nor this device's input (SM 2.3), so while the app is the only sign of a context, a sample a minute is all pairtime takes. The first text of this decision kept the usual cadence and the focus component there too, and the review of #222 found what that cost. T3's background service restarts whenever it stops (T3 d8f3feff, apps/server/src/cloud/bootService.ts:116, 180), so for its users the app's context was live from login to logout. Every 15 s while there was input, pairtime wrote a presence sample, and it wrote an `os.focus` record for each app the person switched to, kept 180 days: browsing, games, anything outside a project. The amendment leaves a sample a minute, whatever the person does, while T3 runs and nothing else keeps a context, and nothing about which app is in front. A harness session left running costs more: a sample every 15 s while there is input, and the window in front.

## Decision

D-relayed-context, as the Status line says, with #225's amendment.

## What changes

- DESIGN 3.3's `presence` row lists "an agent app that drives sessions, such as T3 Code's server, is running" among the signs of a project context, by the `apps` row's test. While a running agent app is the only one of those signs, presence takes one sample every 60 s whatever the input, a focus change takes no sample, and the focus component records nothing about the window in front, no `os.focus`. With the app's own window in front, focus on an agent app is a sign of its own, and the usual rules apply.
- DESIGN 3.3's `apps` row: T3 Code runs when the agent's last process scan found an `app_server` process of this user, or of any session on Windows, where T3's scheduled service may run outside the user's session, and the store the reader picks has both its `-wal` and `-shm` files. A failed scan counts no process. T3 counts toward the context, and toward the reader's 10 s cadence, only while the reader can read its store: `sqlite3` on PATH, with JSON functions, and a schema the probe passes. The first text counted T3 whether or not `sqlite3` was there and whether or not the probe passed, though then no relayed credit is possible. `doctor`'s warning that no session T3 started has reached pairtime uses the same test.
- The agent: the apps component tells presence how many agent apps run (`presence.Sampler.AgentApps`), as the process scan tells it how many harness session processes run (`HarnessProcesses`), and any one makes the context live. The scan also hands the apps component what it listed (`procs.Options.Listed`), in which `t3code.ServerIn` looks for T3's server, and the reader says whether T3 runs from that and its store's files (`t3code.Status.Running`). The apps component checks on every read, every 10 s while T3 runs and every minute while it doesn't, so the context goes live within a minute of T3 starting and ends within a minute of it stopping. Presence says when an agent app alone keeps the context live (`presence.Status.AppOnly`), and the focus component then records nothing.
- Tests: the presence gate and the sampler keep sampling past a terminal's 600 s while an agent app runs, and stop at the 600 s without one. A context live only through T3 gives one sample a minute and no focus record, whatever the input, and with T3's window in front the usual rules apply. The apps component makes the context live on a read that finds T3 running with a store it can read, and makes none on one that finds T3 stopped, no store, no `sqlite3` or a schema the probe refuses. A `sqlite3` without JSON functions slows the reader to once a minute. Leftover `-wal` and `-shm` files with no server process, T3's server with its files, and another user's server each have a case. `pkg/score` credits a phone message's lead in minutes sampled once a minute with no input, and none in a stretch with no samples.

## What stays

- The process scan counts harness session processes alone for presence. T3's server has the app table's `app_server` role, which the scan finds without counting it as a harness. A process name proves nothing, since a script can set its own (DESIGN 5.1), and the files alone don't say T3 runs, since a T3 that was killed while it held its store, or that stopped during one of the reader's runs, leaves both behind (docs/errata/2026-11-23-t3-reader.md, item 16). So T3 runs only with both. The reader still checks both files before every `sqlite3` run, and still picks the store by them.
- A T3 run from its source as `node` isn't in the app table, so it gives no project context, a known limit. Its messages are still read when a prompt's hook asks and once a minute.
- With no agent app running and no other sign of a context, nothing is sampled.
- With any other sign of a context, D14's cadence holds as before: after 600 s with no input and no running turn, one sample a minute.

## Left open

1. **One sample a minute, against SM 2.1's sleep gap.** The amendment samples once a minute whatever the input. SM 2.1, as `pkg/score` reads it (Input above), takes a gap of more than 30 s as sleep unless the sample before it showed 600 s with no input. So while T3 alone keeps the context live and the person uses this computer, or for the first 600 s after they stop, every gap reads as sleep. The slots are asleep, and relayed credit there earns nothing, since it is realized in a slot of any presence but one the machine slept through.
   - Input: T3's server runs, a browser is in front, and nothing else has kept a context live for 20 minutes: no harness process, no hook, no terminal, editor or agent app in front. The person types a 90-character message into T3's web client in that browser, stamped at 12:00:00. Presence samples at 11:58:00, 11:59:00 and 12:00:00, and each shows input a few seconds before it.
   - Expected, by D-relayed-context: the message is relayed, since no window here hosts its session at the stamp, and its lead, 90 / 1.5 = 60 s from 11:59:00, earns 60 s at level C with `via_relay`. So does a phone message sent within 600 s of the person leaving such a desktop.
   - Computed with the amendment: both gaps before the stamp read as sleep, so the lead earns 0 s. The message's run starts a turn whose hooks bring back the 15 s cadence, so the reading after its stop is sampled as before.
   - Two ways out: SM 2.1 reads a gap of at most 120 s as no sleep when the samples say an agent app alone kept the context live, which needs a mark on `os.presence` the scorer can read; or presence samples such a context every 15 s while there is input and once a minute after 600 s without, which is the first text's cadence, still with no focus record. Until the orchestrator decides, the code samples once a minute, as the ruling says, and SM 2.1 stays as it is.
