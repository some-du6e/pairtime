## A related point: 6.3's two windows

SM assumes the agent sees Sam switch between iTerm's two windows and knows which session each window hosts. DESIGN's focus source on macOS is `NSWorkspace` app activation (DESIGN 3.3's table, CP 3.3), which reports a change of app, not of window, and both windows belong to the one iTerm process, whose process tree holds both sessions. So the agent DESIGN describes would record 6.3 the way 6.3-tabs records it, and score it as above. Telling the windows apart needs a window identity, such as the Accessibility API's focused window, which needs a permission CP 3.3 avoids, and a map from each window to its sessions.

## Decision

1. Point 1 is the first option, amended. SM 3.2 rule 1 gives a slot to the session of the first human anchor in the window after the slot begins, if the slot lies inside that anchor's lead, or if that anchor comes within `READ_HORIZON_S` and its session's reading bucket isn't empty when the slot begins; otherwise `ATTRIB_STICKY_S` applies, then `ambiguous`. In 6.3-tabs that gives 14:00:00-14:01:30 A, 14:01:30-14:05:00 B, 14:14:00-14:20:30 A and 14:20:30-14:25:00 B: SM's A 480, B 480, 1,800 s. The look-ahead as first written, to any anchor within 600 s, gives the same rows here. But it hands a slot to the session prompted next even when it has nothing to credit, so watching an agent just prompted, which `ATTRIB_STICKY_S` credits as `SUP`, would go uncredited whenever the next tab has nothing to read. 'After the slot begins' is strict: with 'at or after', A's prompts at 14:01:30.000 and 14:20:30.000 would take the slots they start, giving A 510, B 450.
2. Point 2: no window-level focus. macOS focus stays per app (DESIGN 3.3), so every window and tab of one terminal app counts as one window, as the windows of one terminal process do on Windows and Linux. SM 6.3's main table will put B's Codex session in macOS Terminal, so its A 510, B 450 rest on app switches the agent sees, and every number stays. A second that SM 3.2 rule 1 gives to a session takes no better level than the anchor that gave it (DESIGN 6.4).
3. Why not the alternatives. Accessibility means a permission prompt and the ability to read every window's title, which DESIGN 3.3 never reads, and it still gives no map from a window or tab to the sessions in it. `ITERM_SESSION_ID` and `TERM_SESSION_ID` say which tab a session runs in, not which tab is in front, and asking iTerm2 or Terminal through their scripting interfaces needs Automation consent. Someone gaming focus would use tabs anyway. A possible later study, unverified: window order from `CGWindowListCopyWindowInfo`, which HS 13.4 says needs Screen Recording only for window names, with each window bound to sessions by the prompts typed while it is in front.
4. What follows. The look-ahead now reads the next session's bucket, which the rest of its project's records decide, so DESIGN 6.5's reveal set (d) will cover every record of a project that shares a terminal with the submitted one. DESIGN 7.12 will record that keys typed in one tab vouch for a prompt a script writes into another, and [2026-11-20-cross-tab-typing](2026-11-20-cross-tab-typing.md), which this erratum's WP-ERR1 PR adds, asks what to do about it.
