# Erratum: DESIGN 10 describes the deploy bundle that #97 replaced

Date 2026-11-20. Raised by the review of #97, the deploy bundle (#119), and filed with its fix-up, #123. Status: decided 2026-11-20 by the orchestrator for Karim: DESIGN 10 follows the bundle as built.

## Input

DESIGN 10 at e100a1d: its introduction, 10.1, 10.3, 10.4 and 10.5. The bundle is `deploy/`, `Dockerfile.pairtimed`, `server-image.yml` and `restore-drill.yml`, as #97 built them and #123 changes them, with `deploy/runbook.md` as its procedure. #117 rewrites DESIGN 10.2's key table, 10.3's evidence row and 10.5's items 3 and 4 and steps 4 and 5, so this list leaves those out, except what #117 keeps of step 4.

## Expected

DESIGN 10 says what the bundle does, since WP-OP2's deploy agent follows both it and the runbook (PLAN, WP-OP2).

## What differs

| Where | DESIGN 10 says | The bundle as built |
|---|---|---|
| Introduction | `release.yml` builds and signs the image and publishes it to GHCR, and the host pulls pinned tags | `server-image.yml` builds the image from each commit on main that changes what goes into it and pushes it to GHCR as `sha-<12 hex digits of the commit>`. Nothing signs it: compose pins it by tag and digest. Client releases stay in `release.yml`, under its signing key (decided 2026-11-20) |
| 10.1, `image` | `ghcr.io/some-du6e/pairtimed:<pinned version>` | `ghcr.io/some-du6e/pairtimed:sha-<commit>@sha256:<digest>`, from a `server-image.yml` run's summary |
| 10.1, `command` and the config mount | `-config /etc/pairtime/litestream.yml`, with `litestream.yml` in `config/` | `-config /etc/litestream.yml`. Images built from #123 on carry that file, so each runs the Litestream settings and `exec` line it was built and drilled with; while compose pins an older image, it mounts `litestream.frozen.yml` there, a copy of `litestream.yml` that changes only with that image. `config/` holds `pairtime.toml`, `tier2.toml`, `secrets.env`, `tunnel.env` and the witness deploy key |
| 10.1, `healthcheck` | `["CMD", "/pairtimed", "healthcheck"]` | `["CMD", "pairtimed", "healthcheck", "-live"]`, which asks `/healthz` on the ops port. `/readyz` commits a row on each call, so a Docker health check on it would make Litestream upload every 30 seconds; pairtimed's 5-minute heartbeat asks `/readyz` instead |
| 10.1, services | `pairtimed` and `cloudflared` | Also `witness`, a sidecar with git and OpenSSH that pushes the day roots pairtimed writes to `witness-roots/` with a deploy key, since pairtimed's image has neither (decided 2026-11-20). `pairtimed` runs as 65532 and, like the sidecar, on a read-only root filesystem; every container drops its capabilities, the sidecar keeping one to read the roots and the key, and runs with `no-new-privileges` |
| 10.3, Continuous | `sync-interval` 10 s, "which stays inside R2's free request tier"; about 10 s of writes at risk | `sync-interval` 10 s, `monitor-interval` 10 s, compaction of L1, L2 and L3 every 5 minutes, hour and 6 hours, and level 0 checked for removal every 5 minutes. With Litestream v0.5.18's defaults, a 10 s `sync-interval` alone comes to 3.1M to 3.9M Class A operations a month on an idle server, over R2's free 1M; these settings come to about 0.3M to 0.45M (`deploy/litestream.yml`, Cost). So about 20 s of writes are at risk when the disk is lost; a restart loses none |
| 10.3, Drill | `restore-drill.yml`, weekly and on every image bump, restores the latest replica into a throwaway container | Two jobs. The minio job runs weekly, on PRs that change the bundle or the image, and by hand: it deploys with `compose.yml` against MinIO, destroys the container and its disk, restores the keys from their backup and the database from the replica, checks it, decrypts the snapshot and key backup with the `age` tool, and runs the production job's read-only steps against MinIO. It drills the image `compose.yml` pins, after checking that a commit on main built it, unless the change is to what goes into the image, when it builds one from source. The production job runs weekly and by hand once the `restore-drill` environment holds read-only keys: it restores the real replica into a throwaway container, checks it, serves the copy and checks that the newest snapshot and key backup exist, writing nothing |
| 10.4, `/readyz` | Litestream lag under 60 s | The same 60 s, measured from the oldest local level-0 file the replica lacks and from the oldest commit that changed rows and that no local LTX file has followed yet |
| 10.4, dead man's switches | Two, on Healthchecks.io | Three push monitors on any service a GET marks up; the pilot's are Uptime Kuma monitors on the LAN, off Cloudflare. Litestream pings one while the database has synced, pairtimed one every 5 minutes while `/readyz` passes, and one after each nightly snapshot |
| 10.4, pins | Renovate PRs bump every image tag | Renovate bumps cloudflared's and the sidecar's. pairtimed's pin is bumped by hand from `server-image.yml`'s newest run (`deploy/runbook.md`, The image pin), in a PR whose drill runs that image |
| 10.5, item 6 | A fine-grained token with contents write on `pairtime-witness` | A deploy key with write access to `pairtime-witness`, which only the sidecar mounts, so pairtimed holds no GitHub credential (decided 2026-11-20). The read-only forge token is still WP-SV10's |
| 10.5, item 7 | Healthchecks.io: two check URLs | Three push-monitor URLs, in `secrets.env` |
| 10.5, steps 2 and 3 | `init`, then fill `secrets.env` and `tunnel.env` | `secrets.env` and `tunnel.env` come first, since `init` reads the `PAIRTIME_S3_*` variables from the environment compose builds from `secrets.env`. compose mounts `config/` read-only, so `init -config-out -` writes `pairtime.toml` to standard output, into `config/pairtime.toml.new`, which is then moved into place: a redirect straight to `pairtime.toml` would make an empty file before `init` runs, and `init` refuses to replace one |
| 10.5, step 4, as #117 leaves it | doctor makes "a dry-run push to `pairtime-witness`" and checks "both Healthchecks URLs" | doctor compares the witness repository's latest commit, through GitHub's public API, with the newest root the sidecar should have pushed, and checks the deploy key's file. It checks each of the three push monitors and pings one only when its owner would. It also checks both buckets' lifecycle rules: none that deletes objects in the first, and one in the second that deletes the snapshots within the 30 days `docs/retention.json` gives them (#123) |
| 10.5, step 6 | Upgrades merge the Renovate PR, pull and restart; "a rollback is the previous tag" | An upgrade keeps a copy of `pairtime.toml` first. A rollback puts back the previous commit's `deploy/`, so `compose.yml` and every file it mounts are the ones that image ran with, and the kept `pairtime.toml` when the newer release added a value to an existing key (`deploy/runbook.md`, Rolling back) |

## Decision

DESIGN 10 follows the bundle as built: a later docs-only PR changes its introduction and 10.1 to 10.5 to say what the right-hand column says, after #117. Until then, `deploy/runbook.md`, `deploy/compose.yml` and the workflows are what a deploy agent follows where they and DESIGN 10 differ.
