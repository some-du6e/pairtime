# Erratum: SM 2.7 and 3.3 drop SM 3.2's "anchors still count" in an ambiguous slot

Date 2026-11-20. Raised by the review of #105 (WP-SC3) in issue #121. Status: decided 2026-11-20 by the orchestrator for Karim (D-ambiguous-anchors): in an ambiguous slot the bucket doesn't drain, but every anchor window that covers the slot competes, whatever its project and whether or not its act has a session, and SM 3.3 rules 2 to 6 choose among them. The slot's `p` is the project whose window credits its first second. `pkg/score` does this from #105, and no fixture's expected output changes.

## Input

- SM 3.2 rule 1, in the wording the decision on [the two-tab erratum](2026-11-19-sm-6.3-two-tabs.md) keeps: in a terminal hosting several sessions, a slot that neither the look-ahead nor `ATTRIB_STICKY_S` gives to a session "is `ambiguous` (anchors still count, the bucket doesn't drain)".
- SM 2.7's pseudo-code adds an anchor window as a candidate only where `focus_project(slot(τ)) == A.project`, and a bucket only where `focus_project(slot(τ)) == σ.project`.
- SM 3.3 rule 1: "Only candidates whose project equals the slot's `focus_project` survive, except lookups (resolved by their brackets) and returned slots".
- SM 5.1: each 15-second slot of a minute bucket has one project, `p`.

## What the rules give

An ambiguous slot has no `focus_project`, so SM 2.7 and 3.3 rule 1, read word for word, let nothing credit it, and 3.2's "anchors still count" does nothing. #105 as first written read them that way. In a terminal hosting sessions of two projects:

- A prompt's lead almost never starts on a slot boundary. Take a 45-character prompt sent at 457 s from a session with nothing left to read: its lead starts at 307 s, the slot from 300 s is ambiguous, and seconds 307 to 314 came out `X.ambiguous`. A window hosting only that session credits them as `P`.
- A command typed in a plain shell in another tab of the window, or a commit made there, has no session, so it never resolves a slot. Its lead, its run and its trail came out `X.ambiguous` wherever no session's anchor resolved the slots.

macOS reports focus per app, so every window and tab of one terminal app counts as one window (the two-tab decision), and terminals hosting several projects' sessions are common there.

## Decision

SM 2.7's pseudo-code and SM 3.3 rule 1's `focus_project` filter are read through 3.2's clause. In an ambiguous slot:

1. The bucket doesn't drain.
2. Every anchor window that covers a present second competes, whatever its project and whether or not its act has a session. SM 3.3 rules 2 to 6 choose among them, so a lead beats a trail or a command's run, and a tie goes to the lower project key.
3. The project whose window credits the slot's first credited second is the slot's `p` (SM 5.1). From then on only that project's windows credit the slot's seconds, so the slot keeps one project.
4. A second that no window credits stays `X.ambiguous`.

A terminal hosting no harness is the same case. SM 3.2 rule 1 calls it `ambiguous` until v1.5's shell hook reports a `cwd`, and on 2026-11-20, in the #112 fix-up, the orchestrator ruled: "a terminal hosting no harness is SM 3.2 rule 1's other ambiguous case ... Treat it the way D-ambiguous-anchors treats a multi-session terminal." So a commit or command typed in a plain terminal credits its lead under the four points above, as in a shared terminal. `pkg/score` does this from #112, where `attribute` marks a terminal slot that resolves to no project as ambiguous. An agent app hosting no session keeps SM 3.2 rule 3 and stays unresolved.

SM keeps its wording. This erratum records the reading.

## What pkg/score does

`attribution.ambiguous` marks such a slot, and `attribution.admits` lets every window compete until one credits a second, then only that project's windows (`pkg/score/attrib.go`). The credit pass skips the bucket there, and the slot's `Credit.ProjectKey` is the project of its first credited second (`pkg/score/credit.go`). `TestAttribution` has three cases: a lead that starts mid-slot; a commit's lead that takes a slot's first second from a command's trail under SM 3.3 rule 3; and a command's trail that takes a slot, after which a commit's lead credits nothing more in it.

`6.3-tabs` is the only fixture whose terminal hosts sessions of two projects, and its expected output doesn't change.
