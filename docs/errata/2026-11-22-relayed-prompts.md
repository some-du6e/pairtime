# Erratum: a message a person sends through an agent app counts for nothing

Date 2026-11-22. Raised by the owner on 2026-11-22: after hours of work through T3 Code and a chat bot, their dashboard showed 0m. Status: decided 2026-11-22 by the orchestrator for Karim (D-relayed), and amended the same day, as D-relayed v2 and v2.1, after a red team with three lenses: fraud, SM coherence, and privacy and feasibility. Applied by the PR that adds this file to SM 1.2, 2.1, 2.2, 2.3, 2.4, 2.5, 2.7, 2.8, 3.2, 3.3, 3.4, 5.1, 5.2, 5.4, 6.6, 8.1, 8.6, 8.7, the Risks and Open question 11; to DESIGN 3.2, 3.3, 3.4, 3.5, 4.1, 5.1, 5.2, 5.4, 5.9, 6.2 (D2, D11, D19), 7.3, 7.5, 7.12, 8.3 and 9.3; to docs/spec/ledger-v1.md 4.2, 4.5, 10.1 and 10.7; and to PLAN's WP-SC7. Two edits land with the scorer PR instead, under the `oracle-change` label, because tests pin their text to code that PR changes: DESIGN 6.4, and the `0x13` row of tools/ledger_ref.py ("What changes" below).

## Input

What the owner's server recorded on 2026-11-22. pairtime saw 212 `prompt.submit` records over 52 Claude Code sessions. Every `session.start` had `entrypoint` and `parent_class` `unknown` and no TTY, so SM 2.2 rule 4 made every prompt `headless`, and none was an anchor. That is right for the roughly 200 prompts agents sent. It is wrong for the 12 the owner typed into T3 Code, from T3's web client on other computers.

T3 Code's store says which is which. In the last 20,000 rows of its message table, user-role messages split by `createdBy` and `creationSource` into `agent/provider` 1,584, `agent/mcp` 230, `agent/server` 218, `agent/web` 41 and `user/web` 12, and the 12 are exactly the owner's typed messages that day.

SM 3.4 already named the gap: "An SSH or cloud dev box is the known gap ... v1 doesn't credit them." SM Open question 11 left remote setups to Karim, who has answered that agent apps count.

## Expected

The owner's typing and reading count, at a level that says this device saw no person. The agents' prompts count nothing.

## What the rules gave

0 s. Rule 4 takes every prompt of a session T3 Code's server starts.

## What T3 Code's source says

From pingdotgg/t3code at d8f3feff, read in place, and from the live store on the server, schema and metadata only, with read-only queries over rowid ranges.

- **The store** is `statev2.sqlite` in `<T3 home>/userdata/`, where the home is `T3CODE_HOME` or `<home>/.t3`, on every OS (apps/server/src/os-jank.ts:232-238; config.ts:139-150). T3's background service sets `T3CODE_HOME` in its systemd unit or launchd plist (cloud/bootService.ts:105, 165). It runs in WAL mode with readers in mind (persistence/Sqlite.ts:88-110). T3's VACUUM, run by `t3 doctor`'s compaction, can renumber message rowids (Migrations/069_ThreadMessageSearch.ts:14). A rollback after a failed update copies an older store over the live one, and T3 has already moved its store to a new file once, from `state.sqlite`.
- **Migrations** are recorded in `effect_sql_migrations`. The head at d8f3feff is 85, `TurnItemCounts`, and 55, `OrchestrationV2`, is the base of the schema pairtime reads. T3 ships nightly builds, so the head moves often.
- **`createdBy` `user` doesn't mean a person typed.** T3 stamps it on every command any client sends over its WebSocket (ws.ts:1964-1971). Any process running as the owner can mint such a client with `t3 auth session issue` (cli/auth.ts:169-184). Every firing of a task the owner made in T3's UI carries it, with `creationSource` `web` and a `scheduledTaskId` (scheduledTasks/ScheduledTaskService.ts:1538-1539 and 1020-1080), and webhook tasks render outside request text into such messages. So does the `/compact` T3's web composer sends before a person's message when compaction is due, marked `idleCompaction` (apps/web/src/components/chat/useComposerSend.ts:1223-1241). So does a guest's message the owner sends on, prefixed "Message from guest <name>, sent by the owner:" and marked `context.guest` (orchestration-v2/GuestShareDecider.ts:217). And so do messages T3 makes itself, with `creationSource` `server`: feedback on a request, answers to the agent's question, imported sessions with their original times (project/AgentSessionImporter.ts:148, 165). Messages agents send through T3's MCP tools are `createdBy` `agent`.
- **T3's own tests.** Its test for a message a person sent from a client is `createdBy` `user`, `creationSource` `web` or `mobile`, no `scheduledTaskId`, and not a steer's follow-up (orchestration-v2/Orchestrator.ts:7036-7041). Its test for a message nobody attended is `createdBy` other than `user` or a `scheduledTaskId` (Orchestrator.ts:3069-3072). The stored message's optional marks are `notification`, `scheduledTaskId`, `senderThreadId`, `linkedSender`, `idleCompaction`, `workflowScript`, `context` and `delegatedCompletion` (packages/contracts/src/orchestrationV2.ts:1349-1379).
- **Delivery.** A message sent while a turn runs is steered into it by default, or, with T3's queue setting, gets a queued run that T3 hands to the agent when the active run ends (orchestration-v2/QueuedRunOrder.ts:12-32). Held queues wait for the next client message, so no bound exists on the delay. A steer is pushed into the live SDK query as a user message. Whether Claude Code then fires `UserPromptSubmit` for it is in neither T3's source nor HS, so it needs a capture.
- **Binding.** T3 runs Claude Code through the Claude Agent SDK and chooses the session id itself, passing it as `sessionId` or `resume` (orchestration-v2/Adapters/ClaudeAdapterV2.ts:1998-2000). The hook's `session_id` is therefore the `nativeThreadRef.nativeId` of the provider thread, and a message's run carries `userMessageId`. That ties a message to the prompt its run delivered with no text at all.
- **The text Claude Code sees is not the message.** T3 stores an `Ultrathink:` line before the trimmed text at that effort (packages/shared/src/model.ts:556-572), appends a line per attachment and the captured window's JSON (packages/provider-core/src/server/attachmentPrompt.ts:160-230), turns context references into tokens and an appended envelope (packages/shared/src/composerContextReferences.ts:394-428), and splits a skill's prompt into two blocks (ClaudeAdapterV2.ts:2596-2626). An attachment-only message is stored as a fixed 121-character placeholder (composerContextReferences.ts:178-179). None of that is typing, and T3 keeps no paste flag.
- **Rows change in place.** Messages are upserted by `message_id` (orchestration-v2/ProjectionStore.ts:2789), so an edit keeps the rowid, and an agent's `t3_queue` edit replaces a queued message's text while keeping its `createdBy` and `createdAt` (Orchestrator.ts:11131-11225).
- **Clock.** T3 stamps `created_at` at intake on its server, which spawns Claude Code, so the stamp and the hook share a clock, WSL backends apart.
- **Hooks.** T3 sets `CLAUDE_CODE_ENTRYPOINT=t3-code` and `CLAUDE_CONFIG_DIR` for every Claude Code it runs (apps/server/src/provider/Drivers/ClaudeHome.ts:44, 76). A Claude instance with a home of its own loads none of pairtime's hooks.
- **Its desktop app** spawns its own server (apps/desktop/src/backend/DesktopBackendManager.ts:415), so the sessions that server runs live under the desktop window's process.
- **The `sqlite3` tool.** JSON output first shipped in 3.33.0, and Ubuntu 20.04 has 3.31.1. Debian and Ubuntu don't install the tool by default, Windows has none, and macOS ships it. A read-only connection creates `-wal` and `-shm` files when they are missing and the folder is writable (sqlite.org/wal.html, section 5). The tool runs `~/.sqliterc` first unless told not to.

The brief's premise that `createdBy` `user` marks a person's typing doesn't hold, and its plan to match by text can't work. The red team found both, and v2 and v2.1 replace them with the rules below.

## Decision

D-relayed, as v2 and v2.1 amend it.

1. **A new origin, `relayed`: SM 2.2 rule 9.** A prompt is relayed when an app message witnesses it, no rule from 1 to 7 labels it, and rule 4 lets it through. It comes before rule 8.
   - *The witness* is a `relay.message` of `declared` `none`. For T3 Code, that is a user-role message passing T3's own client-send test above, with none of its other marks (`idleCompaction`, `senderThreadId`, `linkedSender`, `workflowScript`, `notification`, `delegatedCompletion`), no `context.guest`, a run of its own, and first seen by the reader at most `RELAY_SEEN_LAG_S` after T3 created it. A message T3 made itself (`creationSource` `server`) never witnesses anything, nor does a guest's, nor one whose row changed after the reader first saw it.
   - *The app's declarations.* The reader records only the messages T3 stores with `createdBy` `user`. An agent's message, `createdBy` `agent`, gets no record, so its prompt is unwitnessed and rule 4 takes it, as in the `agent-day` case. Of the recorded ones, a message with `scheduledTaskId` gets `declared` `cron`, and one with `senderThreadId` or `linkedSender` gets `declared` `cross_session`. Rules 1 and 3 then make its prompt `scheduled` or a cross-session `subagent`, as they do for the harness's own declarations.
   - *Pairing is structural.* A message pairs with the first `prompt.submit` its own run delivered to the run's session, no earlier than its stamp `sent_at` and at most `RELAY_MATCH_S` after it, one to one. The agent writes the pairing on whichever record arrives second, as the prompt's `relay` or the message's `prompt`, and the scorer checks its session and times. No same-text fallback exists. A steered message, which has no run of its own, earns nothing until a capture shows what Claude Code records for it.
   - *Rule 4* is skipped only when the session's nearest non-shell ancestor is the app's own server process, the new `parent_class` `agent_app`. A chain that reaches a script runtime, a scheduler or another harness first stays headless.
   - *Rules 6 and 7, at the stamp.* For a witnessed prompt, rules 6 and 7 read `sent_at` in place of the prompt's `t`. T3's desktop window on this computer hosts the sessions its server drives, so a message typed there is `human_typed` or `human_pasted` at its usual level, with its lead ending at the stamp. A message the app says came from its phone app skips rules 6 and 7.
   - *Its class and typed length* come from the app's own text with its machine strings removed (a leading `Ultrathink:`, the attachment-only placeholder, context-reference tokens), never longer than the hook's `typed_len_est`, and an upper bound, since T3 keeps no paste flag.
2. **What a relayed anchor earns: SM 2.8's shapes, at level C.** The person was at another device, so this device's evidence says nothing about them.
   - *Lead:* typing time only, `min(typed_len_est / COMPOSE_CPS, COMPOSE_MAX_S)`, capped at the seconds since the thread's previous witnessed message, ending at `sent_at`. No think part, whatever the class, and no return credit.
   - *Reading:* from the relayed prompt's pickup, the session's bucket holds at most `UNKNOWN_BUCKET_MAX_S` = 120 s. It drains, as `READ`, only after one of the session's stops, until the thread's next relayed anchor is sent or the session's next turn starts, and only when that anchor's message comes within 600 s of the stop. A message that paired with nothing, or whose prompt another rule took, vouches for no reading. There is no relayed `SUP`.
   - *Where it lives.* In this device's slots, under its anchor's project and reason, realized in a slot of any presence except one the machine slept through, a locked slot included. The slot's presence stays as sampled. Relayed typing is the explicit exception to SM 2.3's keyboard rule, `COMPOSE_NEEDS_KEYS` and a `track` anchor's typing rule. Every second is level C with the label `via_relay`, and the witness label is the live one, not `backfilled`.
   - *Contests.* Relayed candidates come after every local one, and 3.3 rule 1's focus test doesn't apply to them, so a local window with A or B evidence always beats a relayed one. Between two relayed sessions, E-2.8-lookback's rule decides: the session whose next relayed anchor's lead holds the second, else the one whose latest relayed message is the most recent, else the lower `project_key`, then the lower `session_key`. In SM 3.4's merge, a slot whose credit is all relayed loses to another device's slot with OS presence behind it, whatever their seconds, and the pair raises no `concurrent_devices`.
   - *Nowhere else.* A relayed anchor is never a human anchor for another session's reading horizon or level, for a returned run, or for a lookup's brackets.
3. **Timing and finality.** The reader accepts a row only when T3 created it at most `RELAY_SEEN_LAG_S` = 60 s before the reader first saw it. That turns away imported and backdated rows. Credit stands at the app's stamp, and the minutes a relayed lead touches can't become final until a prompt pairs with the message or `RELAY_MATCH_S` passes. `RELAY_MATCH_S` = 600 s is the most that keeps DESIGN 6.2 D1's finality: a lead's first minute is open for 900 s after it ends, and a lead starts at most `COMPOSE_MAX_S` = 300 s before its stamp. A message queued longer earns nothing.
4. **Containment.** Relayed minutes get D11's lookback treatment: level C, shown with `via_relay` on the owner's dashboard, never in public totals, build days, boards or badges, and in a submission only under a program's level-C opt-in and D5. The tier-2 flag `relayed_share` marks submissions and days where relayed credit is more than half, and SM 5.4's evidence line and the handbook text count relayed messages apart from typed prompts. Relay records never count toward `logged_s`, `ai_logged_s` or `hackatime_logged_s`, but the harness's own records of a relayed turn count as any turn's do, so a person who works only from a phone isn't zeroed.
5. **Chat bots: `pairtime relay`.** The bot passes the chat app's name, the send time, the project folder and the sender's chat id, and the message on stdin, never in an argument, where the process list would show it. Only the owner's own messages count: setting the bot up pins the owner's chat id, kept only as an HMAC, and a call from any other sender is dropped before its text is read. The agent strips chat markup, redacts the text with `pkg/redact`, and uses it only to pair and to class the call. The record is `via = plugin` with `source = cli`, a claim from any process, and a send time more than 5 s from the call's arrival is replaced by the arrival, as DESIGN 5.3 does for a plugin's `t`. A call never opens an anchor of its own. It pairs with the first hook or log prompt delivered in a session of its project at or after the send time, within `RELAY_MATCH_S`, whose redacted text is a near-duplicate of the call's, and that prompt is relayed only where rule 4 allows. A call that pairs with nothing raises `relay_without_prompt`.
6. **Not in this job: the cross-device join.** Another linked device of the same account seeing keyboard input with an agent app's client focused just before the message would raise it to level B. That is v1.5, and Open question 11's remaining half.
7. **Privacy.** The app's text is read on the device, measured and classed, and dropped: no copy goes to the vault, the ledger or any field. The reader opens the store with `sqlite3 -readonly -batch -bail -init <null device>`, only while the store's `-wal` file exists, so it creates nothing in T3's folders. It reads a row's text only after a `WHERE` clause has checked that the row isn't a guest's and that its thread's folder is one pairtime tracks and doesn't ignore. It never touches T3's search table. T3's thread, run and message ids enter pairtime only as HMACs under a device key. Uploads carry the usual numbers and one new value, `via_relay`, in the existing `lbl` field.

## The parameters

Both go in SM 8.1 and, with the scorer PR, in the next parameter table with its hash.

| Parameter | Value | Why |
|---|---|---|
| `RELAY_MATCH_S` | 600 s | The longest wait for a pairing that keeps D1's finality: `PENDING_WINDOW_S` 900 s less `COMPOSE_MAX_S` 300 s. T3 queues with no bound, so a longer queue earns nothing rather than reopening final minutes |
| `RELAY_SEEN_LAG_S` | 60 s | The oldest a stamp may be when the reader first sees the row. The reader looks every 10 s while T3 runs, so an honest message is always younger, and imported and hand-written rows with old stamps are turned away |

`RELAY_MIN_GAP_S` is dropped. The brief's 20 s gap between relayed anchors of a session changes no total once each lead is capped at the seconds since the thread's previous message: two messages 5 s apart already give the second at most 5 s of typing. A rule that removed those 5 s and the second message's base would change nothing a script could use, and the red team's fraud lens showed it never binds a farm. Without it, a message sent seconds after another keeps its few seconds of typing, its base and its turn.

## Readings this erratum settles for relayed anchors

The lookback erratum ([2026-11-19-sm-2.8-lookback](2026-11-19-sm-2.8-lookback.md)) leaves five points open for lookback's own shapes. For relayed anchors this erratum settles them, and the oracle rows depend on these answers:

1. A go-ahead's relayed lead is its typing time: `yes` earns 2 s, not `LOW_LEAD_S`.
2. An answer's relayed lead has no 60 s think part.
3. Codes. In a slot whose presence is unknown, live or backfilled, an uncredited second is `X.bucket_cap` where only the 120 s cap kept a session from reading, else `X.agent_only` while a turn a person started runs, or a `no_input` one, else `X.automated` while an automated turn runs, else `X.no_anchor` (SM 5.2). That is E-6.6-codes' order with its presence and focus steps skipped, as E-2.8-lookback decided it for lookback, applied to live slots too, since relayed credit makes them creditable.
4. An automated turn between a stop and the next relayed message fills the same capped bucket, and its own stop opens reading the same way.
5. A message sent before a stop, as a queued one is, doesn't vouch for that stop's reading, and reading ends when the thread's next relayed message is sent or the session's next turn starts.

## Red team: how a script on the machine could farm the rule, and what bounds it

The fraud lens's verdict stands: no rule that trusts an app's word can tell a script that drives the app from a person, so the bound is the level, not the rule.

1. **A script drives real agents through T3 Code.** It mints a client token with `t3 auth session issue`, or drives T3's web client in a browser that holds the owner's session, and sends a stream of LLM-written messages. T3 records each as a person's, each starts a run, and each pairs with its prompt. Bound: up to all of wall time at level C on the owner's own dashboard, capped at `DAY_CAP_S`, 12 h. Level C never counts toward public totals, build days, boards or badges (D11). A program takes it only by opting in to level C, only inside commit intervals whose closing commit is forge-verified, and only up to a third of the window's `ai_logged_s` (D5). Relay records add nothing to `ai_logged_s`, but the farm's own agent turns do, so the most it can submit is the handbook's third of the agent time it caused, what the flat third would have paid anyway. The `relayed_share` flag, the drawn sample's prompts beside the messages they answer, and the hours-weighted audit do the rest. DESIGN 7.12 gets this row.
2. **A script writes rows into T3's store by hand.** It needs no token, since the store is a file the owner can write. A hand-written row with an old stamp fails `RELAY_SEEN_LAG_S`. A fresh one still needs a run of its own whose prompt reaches a session T3's server started, so the script has to drive T3 anyway, which is case 1.
3. **A script calls `pairtime relay`, or writes T3's store, beside its own `claude -p` loop**, SM 6.6's Casey. The witnessed prompt skips rule 4 only when the session's nearest non-shell ancestor is an agent app's server, and here it is the script. So rule 4 still takes every prompt: 0. An unpaired call opens nothing and raises `relay_without_prompt`.
4. **T3's own scheduler or a webhook.** A task the owner made fires every 10 minutes with `createdBy` `user`. Its `scheduledTaskId` makes the record `declared` `cron`, and rule 1 makes its prompt `scheduled`: 0. Before v2 this was a blocker, worth about 7.5 h a day with nobody there.
5. **Messages nobody typed that look typed.** An automatic `/compact`, a guest's message, a message from another thread or environment, an answer an agent gave through `t3_pending_request`, an imported session, and a queued message an agent edited all fail the witness test or declare themselves: 0.
6. **Backdating.** T3 stamps `created_at` at intake, on the machine that runs the agent. A row older than `RELAY_SEEN_LAG_S` at first sight is turned away. A `pairtime relay` send time more than 5 s off is replaced by the arrival. A lead never reaches before the thread's previous message, and no minute past its finality changes.
7. **Many threads at once.** One timeline per device: a second goes to one candidate, so ten relayed threads can't credit more than wall time, and SM 3.4's merge keeps relayed credit off a second another device's witnessed credit holds.
8. **A jiggler on a desktop that runs T3 Code.** A script posts messages through T3's API with `creationSource` `web` while a jiggler moves the pointer and T3's window is in front. Rules 6 and 7, tested at the stamp, see input and a hosting window, so the prompt is `human_typed`, at level B on a machine without the key counter. That is DESIGN 7.12's accepted "pty driver plus a jiggler on a level-B machine", reached through T3's window instead of a terminal, and bounded the same way. A message the app says came from its phone app skips rules 6 and 7, so a phone message can't be passed off as typed here.

## Known limits

- Approvals, answers and stops given in T3's own interface aren't messages, so they earn nothing in v1. Neither does an answer to the agent's question that T3 delivers as a message, since T3 makes it with `creationSource` `server`.
- A message queued longer than `RELAY_MATCH_S` earns nothing.
- A steered message earns nothing until a capture shows whether and how Claude Code reports it.
- A row the reader first sees more than `RELAY_SEEN_LAG_S` after its stamp earns nothing: one sent while pairtime's agent was down, or while T3 was closed and then reopened later.
- A thread whose run T3 can't tie to a session pairtime sees, such as one on a provider pairtime has no hooks for, earns nothing.
- A Claude instance T3 runs with a home of its own loads none of pairtime's hooks, so its messages never pair. `doctor` says so.
- The cross-device join that would raise relayed credit to level B is v1.5.

## Questions for the orchestrator

1. **Phone messages skip rules 6 and 7.** This erratum adds it, from the SM-coherence lens: without it, a phone message sent while a jiggler moves the pointer on the desktop would score `human_typed` at level B there. T3's `web` source can't say which computer a browser ran on, so the same can still happen with a message typed in a browser elsewhere, as item 8 of the red team says. Confirm, or ask for the stricter rule: rules 6 and 7 for a witnessed prompt only with key presses, so only level A can beat `relayed`.
2. **A relay call's text isn't kept.** The brief had the vault keep it as it keeps `track` text. v2 made a relay call open no anchor of its own, so the challenge draws the prompt it paired with, whose own text is committed, and keeping the bot's copy would only keep a second copy of the owner's chat. Confirm.
3. **MCP Apps.** T3's MCP Apps can send app-chosen text as an ordinary user turn, `createdBy` `user` and `creationSource` `web`, with no mark to tell it apart (packages/client-runtime/src/mcpApps/host.ts:275-292). It needs the web UI open and an app the owner installed. Such a message counts as relayed. Accept it as a known limit, or ask T3 for a mark.
4. **The steer capture.** Who schedules it, and against which Claude Code version: WP-AD0's kit, through T3?
5. **Deploy order.** The server must accept `via_relay` in `lbl` (ingest-v1 2.3.2 and its shape check) before any client sends it. The scorer PR changes both. The server goes out first.

## What stays

- Live prompts keep rule 4 as it stands. Only a witnessed prompt whose session an agent app's server started skips it, and SM 2.8 applies to backfilled records only, so lookback and live T3 sessions never meet.
- Nothing about typing into a terminal, an IDE or an agent's own desktop app changes.
- No tier-1 field is added. `lbl` gains one value, which is why DESIGN 4.3's table doesn't change.
- DESIGN 4.4 gains no row. The agent keeps no copy of an app's text or a relay call's: it reads them, measures and classes them, and drops them. The T3 reader's cursor lives in `state.json` (3.5), which holds nothing personal. The records themselves are ledger records like any other, kept as 4.4 already says.
