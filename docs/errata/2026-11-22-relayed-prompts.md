# Erratum: a message a person sends through an agent app counts for nothing

Date 2026-11-22. Raised by the owner on 2026-11-22: after hours of work through T3 Code and a chat bot, their dashboard showed 0m. Status: decided 2026-11-22 by the orchestrator for Karim (D-relayed), and amended the same day, as D-relayed v2 and v2.1, after a red team with three lenses: fraud, SM coherence, and privacy and feasibility, and again by the rulings on the review of the PR that adds this file (#194). Those rulings took the chat bot's `pairtime relay` out of this decision, to issue #193, so it covers T3 Code alone. Applied by the PR that adds this file to the SM, DESIGN, docs/spec/ledger-v1.md and PLAN sections "What changes" lists. Two edits land with the scorer PR instead, under the `oracle-change` label, because tests pin their text to code that PR changes: DESIGN 6.4, and the `0x13` row of tools/ledger_ref.py ("What changes" below).

## Input

What the owner's server recorded on 2026-11-22. pairtime saw 212 `prompt.submit` records over 52 Claude Code sessions. Every `session.start` had `entrypoint` and `parent_class` `unknown` and no TTY, so SM 2.2 rule 4 made every prompt `headless`, and none was an anchor. That is right for the roughly 200 prompts agents sent. It is wrong for the 12 the owner typed into T3 Code, from T3's web client on other computers.

T3 Code's store says which is which. In the last 20,000 rows of its message table, user-role messages split by `createdBy` and `creationSource` into `agent/provider` 1,584, `agent/mcp` 230, `agent/server` 218, `agent/web` 41 and `user/web` 12, and the 12 are exactly the owner's typed messages that day.

SM 3.4 already named the gap: "An SSH or cloud dev box is the known gap ... v1 doesn't credit them." SM Open question 11 left remote setups to Karim, who has answered that agent apps count.

## Expected

The owner's typing and reading count, at a level that says this device saw no person. The agents' prompts count nothing.

## What the rules gave

0 s. Rule 4 takes every prompt of a session T3 Code's server starts.

## What T3 Code's source says

From pingdotgg/t3code at d8f3feff, read in place, and from the live store on the server, schema and metadata only, with read-only queries over rowid ranges.

- **The store** is `statev2.sqlite` in `<T3 home>/userdata/`, where the home is `T3CODE_HOME` or `<home>/.t3`, on every OS (apps/server/src/os-jank.ts:232-238; config.ts:139-150). T3's background service sets `T3CODE_HOME` in its systemd unit or launchd plist (cloud/bootService.ts:105, 165). It runs in WAL mode with readers in mind (persistence/Sqlite.ts:88-110). T3's VACUUM, run by `t3 doctor`'s compaction, can renumber message rowids (Migrations/069_ThreadMessageSearch.ts:14). A rollback after a failed update copies an older store over the live one, and T3 has already moved its store to a new file once, from `state.sqlite`.
- **Migrations** are recorded in `effect_sql_migrations`. The head at d8f3feff is 85, `TurnItemCounts`, and 55, `OrchestrationV2`, is the base of the schema pairtime reads. T3 ships nightly builds, so the head moves often.
- **`createdBy` `user` doesn't mean a person typed.** T3 stamps it on every command any client sends over its WebSocket (ws.ts:1964-1971). Any process running as the owner can mint such a client with `t3 auth session issue` (cli/auth.ts:169-184). Every firing of a task the owner made in T3's UI carries it, with `creationSource` `web` and a `scheduledTaskId` (scheduledTasks/ScheduledTaskService.ts:1538-1539 and 1020-1080), and webhook tasks render outside request text into such messages. So does the `/compact` T3's web composer sends before a person's message when compaction is due, marked `idleCompaction` (apps/web/src/components/chat/useComposerSend.ts:1223-1241). So does a guest's message the owner sends on, prefixed "Message from guest <name>, sent by the owner:" and marked `context.guest` (orchestration-v2/GuestShareDecider.ts:217). And so do messages T3 makes itself, with `creationSource` `server`: feedback on a request, answers to the agent's question, imported sessions with their original times (project/AgentSessionImporter.ts:148, 165). Messages agents send through T3's MCP tools are `createdBy` `agent`.
- **T3's own tests.** Its test for a message a person sent from a client is `createdBy` `user`, `creationSource` `web` or `mobile`, no `scheduledTaskId`, and not a steer's follow-up (orchestration-v2/Orchestrator.ts:7036-7041). Its test for a message nobody attended is `createdBy` other than `user` or a `scheduledTaskId` (Orchestrator.ts:3069-3072). The stored message's optional marks are `notification`, `scheduledTaskId`, `senderThreadId`, `linkedSender`, `idleCompaction`, `workflowScript`, `context` and `delegatedCompletion` (packages/contracts/src/orchestrationV2.ts:1349-1379).
- **Delivery.** A message sent while a turn runs is steered into it by default, or, with T3's queue setting, gets a queued run that T3 hands to the agent when the active run ends (orchestration-v2/QueuedRunOrder.ts:12-32). Held queues wait for the next client message, so no bound exists on the delay. A steer is pushed into the live SDK query as a user message. Whether Claude Code then fires `UserPromptSubmit` for it is in neither T3's source nor HS, so it needs a capture.
- **Binding.** T3 runs Claude Code through the Claude Agent SDK and chooses the session id itself, passing it as `sessionId` or `resume` (orchestration-v2/Adapters/ClaudeAdapterV2.ts:1998-2000). The hook's `session_id` is therefore the `nativeThreadRef.nativeId` of the provider thread, and a message's run carries `userMessageId`. That ties a message to the prompt its run delivered with no text at all.
- **The text Claude Code sees is not the message.** T3 stores an `Ultrathink:` line before the trimmed text at that effort (packages/shared/src/model.ts:556-572), appends a line per attachment and the captured window's JSON (packages/provider-core/src/server/attachmentPrompt.ts:160-230), turns context references into tokens and an appended envelope (packages/shared/src/composerContextReferences.ts:394-428), and splits a skill's prompt into two blocks (ClaudeAdapterV2.ts:2596-2626). An attachment-only message is stored as a fixed 121-character placeholder (composerContextReferences.ts:178-179). None of that is typing, and T3 keeps no paste flag.
- **Rows change in place.** Messages are upserted by `message_id` (orchestration-v2/ProjectionStore.ts:2789), so an edit keeps the rowid, and an agent's `t3_queue` edit replaces a queued message's text while keeping its `createdBy` and `createdAt` and setting only `updatedAt` (Orchestrator.ts:11131-11225).
- **Clock.** T3 stamps `created_at` at intake on its server, which spawns Claude Code, so the stamp and the hook share a clock, WSL backends apart.
- **Hooks.** T3 sets `CLAUDE_CODE_ENTRYPOINT=t3-code` for every Claude Code it runs unless the provider instance's environment or Claude's settings `env` names another token, and it sets `CLAUDE_CONFIG_DIR` only for a Claude instance it gives a home of its own (apps/server/src/provider/Drivers/ClaudeHome.ts:44, 76, 82-87, as corrected 2026-11-24 by D-t3-code-entrypoint). A Claude instance with a home of its own loads none of pairtime's hooks.
- **Its desktop app** spawns its own server (apps/desktop/src/backend/DesktopBackendManager.ts:415), so the sessions that server runs live under the desktop window's process.
- **The `sqlite3` tool.** JSON output first shipped in 3.33.0, and Ubuntu 20.04 has 3.31.1. Debian and Ubuntu don't install the tool by default, Windows has none, and macOS ships it. A read-only connection creates `-wal` and `-shm` files when they are missing and the folder is writable (sqlite.org/wal.html, section 5). The tool runs `~/.sqliterc` first unless told not to.

The brief's premise that `createdBy` `user` marks a person's typing doesn't hold, and its plan to match by text can't work. The red team found both, and v2 and v2.1 replace them with the rules below.

## Decision

D-relayed, as v2, v2.1 and the review's rulings amend it.

1. **A new origin, `relayed`: SM 2.2 rule 9.** A prompt is relayed when an app message witnesses it and no rule from 1 to 7 labels it. It comes before rule 8.
   - *The witness* is a `relay.message` of `declared` `none`. For T3 Code, that is a user-role message passing T3's own client-send test above, with none of its other marks (`idleCompaction`, `senderThreadId`, `linkedSender`, `workflowScript`, `notification`, `delegatedCompletion`), no `context.guest`, a run of its own, and first seen by the reader at most `RELAY_SEEN_LAG_S` after T3 created it. A message T3 made itself (`creationSource` `server`) never witnesses anything, nor does a guest's, nor one whose row changed after the reader first saw it or had already been edited then, its `updated_at` later than its `created_at`.
   - *The app's declarations.* The reader records only the messages T3 stores with `createdBy` `user` and `creationSource` `web` or `mobile`, and the record's `client` is that source. An agent's message, `createdBy` `agent`, gets no record, so its prompt is unwitnessed and rule 4 takes it, as in the `agent-day` and `t3-here-agent` cases. Of the recorded ones, a message with `scheduledTaskId` gets `declared` `cron`, and one with `senderThreadId` or `linkedSender` gets `declared` `cross_session`. Rules 1 and 3 then make its prompt `scheduled` or a cross-session `subagent`, as they do for the harness's own declarations.
   - *Pairing is structural.* A message pairs with the first `prompt.submit` its own run delivered to the run's session, no earlier than its stamp `sent_at` and at most `RELAY_MATCH_S` after it, one to one. The agent writes the pairing on whichever record arrives second, as the prompt's `relay` or the message's `prompt`, and the scorer checks its session and times. No same-text fallback exists. A steered message, which has no run of its own, earns nothing until a capture shows what Claude Code records for it.
   - *Rule 4 and the app's server.* A message witnesses only a prompt of a session whose nearest non-shell ancestor is the app's own server process, the new `parent_class` `agent_app`. Rule 4 lists that class, so every prompt of such a session is headless unless a message witnesses it, whatever window hosts the session, and a witnessed prompt skips rule 4. A chain that reaches a script runtime, a scheduler or another harness first stays headless. The class comes from the process's name, which a script can set, so the test sorts honest setups and bounds nothing on its own (red team item 3).
   - *A guest's message.* The reader never reads one. It does tell the agent which runs guest messages started, and the prompt such a run delivers is marked `guest`: it keeps no text on the device, and rule 4 takes it whatever its session, even when a message witnesses it, so marking a prompt `guest` can only lose credit (the `t3-unattended` case pins a prompt with both `guest` and `relay` at 0 s).
   - *Rules 6 and 7, at the stamp.* For a witnessed prompt, rules 6 and 7 read `sent_at` in place of the prompt's `t`. T3's desktop window on this computer hosts the sessions its server drives, so a message typed there is `human_typed` or `human_pasted` at its usual level, with its lead ending at the stamp. A message whose record says `client` `mobile`, T3's phone app, skips rules 6 and 7 and is relayed whatever this device's input says (the `t3-phone` case).
   - *Its class and typed length* come from the app's own text with its machine strings removed (a leading `Ultrathink:`, the attachment-only placeholder, context-reference tokens, and, as amended 2026-11-23 by the ruling in #225, `[Assistant quote](t3-citation://...)` links, which count as the comment they carry), never longer than the hook's `typed_len_est`, and an upper bound, since T3 keeps no paste flag.
2. **What a relayed anchor earns: SM 2.8's shapes, at level C**, as amended 2026-11-23 by the ruling in #221. The person was at another device, so this device's evidence says nothing about them.
   - *The anchor* is the `relay.message`, at its `sent_at`, the app's stamp. A record opens no anchor unless it pairs.
   - *Lead:* typing time only, `min(len_chars / COMPOSE_CPS, COMPOSE_MAX_S)`, with `len_chars` the app's own typed length, at most the hook's `typed_len_est`, capped at the seconds since the thread's previous `relay.message` of `declared` `none`, paired or not, ending at `sent_at`. No think part, whatever the class, and no return credit.
   - *Reading:* the relayed prompt resets the session's bucket to its 20 s base at pickup. In a session an agent app's server runs, relayed reading draws on at most `UNKNOWN_BUCKET_MAX_S` = 120 s of the bucket from the session's first fill on, whatever reset came last, while local reading there keeps the usual cap, `BUCKET_MAX_S`. It drains, as `READ`, only after one of the session's stops, until the relayed anchor that vouches for that stop is sent or the session's next turn starts. The anchor that vouches is the first of the thread's relayed anchors sent after the stop among those that pair within `PENDING_WINDOW_S` − 60 s of it (decision 3), and it vouches only when its message comes within 600 s of the stop. One that pairs later keeps its own lead but neither vouches for that stop's reading nor ends it. A message that paired with nothing, or whose prompt another rule took, vouches for no reading. There is no relayed `SUP`.
   - *Where it lives.* In this device's slots, under its anchor's project and reason, realized in a slot of any presence except one the machine slept through, a locked slot included. The slot's presence stays as sampled. Relayed typing is the explicit exception to SM 2.3's keyboard rule, `COMPOSE_NEEDS_KEYS` and a `track` anchor's typing rule. Every second is level C with the label `via_relay`, and the witness label is the live one, not `backfilled`.
   - *Contests.* Relayed candidates come after every local one, and 3.3 rule 1's focus test doesn't apply to them, so a local window with A or B evidence always beats a relayed one. Between two relayed sessions, the session whose next relayed anchor's lead holds the second takes it; when both sessions' next leads hold it, the one whose anchor is sent soonest after it; else E-2.8-lookback's rule: the one whose latest relayed message is the most recent, then the lower `project_key`, then the lower `session_key`. SM 3.4's merge between devices stays as it is in v1 (Known limits).
   - *Nowhere else.* A relayed anchor is never a human anchor for another session's reading horizon or level, for a returned run, or for a lookup's brackets.
3. **Timing and finality.** The reader accepts a row only when T3 created it at most `RELAY_SEEN_LAG_S` = 60 s before the reader first saw it. That turns away imported and backdated rows. Credit stands at the app's stamp, and the minutes a relayed lead touches can't become final until a prompt pairs with the message or `RELAY_MATCH_S` passes. A lead starts at most `COMPOSE_MAX_S` = 300 s before its stamp, and its first minute is final `PENDING_WINDOW_S` = 900 s after that minute ends, so with `RELAY_MATCH_S` = 600 s every minute of a lead is still pending when its pairing comes. That leaves a pairing no margin for late records: one that arrives after a lead's minute is final changes nothing in it. A message queued longer than `RELAY_MATCH_S` earns nothing. Reading needs a tighter bound, because the message that vouches for a stop's reading can be sent up to 600 s after the stop and pair up to `RELAY_MATCH_S` after that, 1,200 s in all, by which time the stop's minute is final. So a message vouches for a stop's reading only if it pairs, when the later of its record and its prompt arrives, within `PENDING_WINDOW_S` − 60 s = 840 s of the stop, while the stop's minute is still pending. A message that pairs later keeps its own lead and vouches for nothing before it (the `t3-late` case). A pairing reaches back from `sent_at`: the lead lies within `COMPOSE_MAX_S` of it and the reading it vouches for within 600 s, so the scorer's bound on how far back a record may change credit, `READ_HORIZON_S` (E-return-lookahead), applies to a pairing counted from `sent_at` and never cuts relayed credit.
4. **Containment.** Relayed minutes get D11's lookback treatment: level C, shown with `via_relay` on the owner's dashboard, never in public totals, build days, boards or badges, and in a submission only under a program's level-C opt-in and D5. The tier-2 flag `relayed_share` marks submissions and days where relayed credit is more than half, and SM 5.4's evidence line and the handbook text count relayed messages apart from typed prompts. Relay records never count toward `logged_s`, `ai_logged_s` or `hackatime_logged_s`, but the harness's own records of a relayed turn count as any turn's do, so a person who works only from a phone isn't zeroed.
5. **Chat bots are not in this decision.** v2 gave chat bots a `pairtime relay` command. The review showed it can't yet be made coherent with DESIGN 5.2's side-door rules: on `track`'s path it would write every chat message, any sender's, to disk before the sender check; its sender and folder would sit in the process list; it has no chat or thread id, though its rules are per thread; and a relay call plus `tmux send-keys` would make a TTY session relayed. It moved to its own issue, #193, and nothing here depends on it.
6. **Not in this job: the cross-device join.** Another linked device of the same account seeing keyboard input with an agent app's client focused just before the message would raise it to level B. That is v1.5, and Open question 11's remaining half, and so is a merge that tells an all-relayed slot apart (Known limits).
7. **Privacy.** The app's text is read on the device, measured and classed, and dropped: no copy goes to the vault, the ledger or any field. The reader opens the store with `sqlite3 -readonly -batch -bail -init <null device>`, only while the store's `-wal` file exists, so it creates nothing in T3's folders, and it passes its SQL on stdin, because the SQL names the folders pairtime tracks and other accounts can read a process's arguments. It reads a row's text only after a `WHERE` clause has checked that the row isn't a guest's and that its thread's folder is one pairtime tracks and doesn't ignore. It never touches T3's search table. The hook still records the prompt T3 makes of a guest's message, so, when the reader runs, the agent keeps no text for it (decision 1), and the privacy notice says so. When the reader can't answer, with no `sqlite3` on PATH, a schema the probe refuses or a read that times out, nothing marks a guest's prompt: pairtime keeps its text as it keeps any prompt's, with `c` as ledger-v1 10.1 requires, and rule 4 takes it, since no record witnesses it, so it earns nothing and the draw never picks it. In a challenge's content reveal, T3's attachment lines and captured-window block, which hold another window's title and on-screen text, collapse to typed markers by default in any prompt a T3 record pairs with (DESIGN 7.5 step 6). T3's thread, run and message ids enter pairtime only as HMACs under a device key. Uploads carry the usual numbers and one new value, `via_relay`, in the existing `lbl` field.

## The parameters

Both go in SM 8.1 and, with the scorer PR, in the next parameter table with its hash.

| Parameter | Value | Why |
|---|---|---|
| `RELAY_MATCH_S` | 600 s | Keeps a lead's minutes pending until its pairing: `PENDING_WINDOW_S` 900 s less `COMPOSE_MAX_S` 300 s (decision 3). It leaves a pairing no margin for late records, and reading has the tighter bound of `PENDING_WINDOW_S` − 60 s from the stop. T3 queues with no bound, so a longer queue earns nothing rather than reopening final minutes |
| `RELAY_SEEN_LAG_S` | 60 s | The oldest a stamp may be when the reader first sees the row. The reader looks every 10 s while T3 runs, so an honest message is always younger, and imported and hand-written rows with old stamps are turned away |

`RELAY_MIN_GAP_S` is dropped. Once each lead is capped at the seconds since the thread's previous message, the brief's 20 s gap between relayed anchors of a session would only take the second message's few seconds of typing away: 5 s in `t3-queued`, whose total would be 181 s instead of 186. That is nothing a farm can use, since a farm that spaces its messages 20 s apart loses nothing to the rule, and the red team's fraud lens showed it never binds one. Without it, a message sent seconds after another keeps its few seconds of typing, its base and its turn.

## Readings this erratum settles for relayed anchors

The lookback erratum ([2026-11-19-sm-2.8-lookback](2026-11-19-sm-2.8-lookback.md)) leaves five points open for lookback's own shapes. For relayed anchors this erratum settles them, and the oracle rows depend on these answers:

1. A go-ahead's relayed lead is its typing time: `yes` earns 2 s, not `LOW_LEAD_S`.
2. An answer's relayed lead has no 60 s think part.
3. Codes. In a live slot whose presence is unknown, as on a server with no desktop, an uncredited second is `X.bucket_cap` where only the 120 s cap kept a session from reading, else `X.agent_only` while a turn a person started runs, or a `no_input` one, else `X.automated` while an automated turn runs, else `X.no_anchor` (SM 5.2). That is E-6.6-codes' order with its presence and focus steps skipped, and the code-placement erratum's order among running turns. Backfilled slots aren't this erratum's: the orchestrator's decision on E-2.8-lookback gives a backfilled second a discount's code first, then `X.bucket_cap` where only the 120 s cap kept a session from reading, then `X.agent_only` or `X.automated` while any turn runs, then `X.no_anchor`, and WP-SC7 applies it with its fixture.
4. An automated turn between a stop and the next relayed message fills the same capped bucket, and its own stop opens reading the same way.
5. A message sent before a stop, as a queued one is, doesn't vouch for that stop's reading, and, as amended 2026-11-23 by the ruling in #221, reading ends when the relayed anchor that vouches for that stop is sent or the session's next turn starts.

## Red team: how a script on the machine could farm the rule, and what bounds it

The fraud lens's verdict stands: no rule that trusts an app's word can tell a script that drives the app from a person, so the bound is the level, not the rule.

1. **A script drives real agents through T3 Code.** It mints a client token with `t3 auth session issue`, or drives T3's web client in a browser that holds the owner's session, and sends a stream of LLM-written messages. T3 records each as a person's, each starts a run, and each pairs with its prompt. Bound: up to all of wall time at level C on the owner's own dashboard, capped at `DAY_CAP_S`, 12 h. Level C never counts toward public totals, build days, boards or badges (D11). A program takes it only by opting in to level C, only inside commit intervals whose closing commit is forge-verified, and only up to a third of the window's `ai_logged_s` (D5). Relay records add nothing to `ai_logged_s`, but the farm's own agent turns do, so the most it can submit is the handbook's third of the agent time it caused, what the flat third would have paid anyway. The `relayed_share` flag, the drawn sample's prompts beside the messages they answer, and the hours-weighted audit do the rest. DESIGN 7.12 gets this row.
2. **A script writes rows into T3's store by hand.** It needs no token, since the store is a file the owner can write. A hand-written row with an old stamp fails `RELAY_SEEN_LAG_S`. A fresh one still needs a run of its own whose prompt reaches a session of an `agent_app` ancestor, so the script has to drive T3 anyway, which is item 1, or take the server's name as well, which is item 3.
3. **A script writes T3's store beside its own `claude -p` loop**, SM 6.6's Casey. Under its own name it gets 0: a message witnesses only a prompt of a session whose nearest non-shell ancestor is an agent app's server, and here that ancestor is the script, so rule 4 takes every prompt. But pairtime's app table classes a process by its name, its alias first, which is a script's own file name or the title a program gives itself, such as a Node program's `process.title`. A farm saved under the name of T3's server, or one that sets its title to it, gets `agent_app` sessions, and with rows it writes for their runs each prompt is relayed. The bound is then item 1's: up to all of wall time at level C, contained by D11 and D5. The ancestor test sorts honest setups; it isn't a security boundary, and DESIGN 5.1 and 7.12 say so.
4. **T3's own scheduler or a webhook.** A task the owner made fires every 10 minutes with `createdBy` `user`. Its `scheduledTaskId` makes the record `declared` `cron`, and rule 1 makes its prompt `scheduled`: 0. Before v2 this was a blocker, worth about 7.5 h a day with nobody there.
5. **Messages nobody typed that look typed.** An automatic `/compact`, a guest's message, a message from another thread or environment, an answer an agent gave through `t3_pending_request`, an imported session, and a queued message an agent edited all fail the witness test or declare themselves: 0. An agent's edit fails it whether the reader saw it happen or found the row already edited at first sight, since T3 stamps `updatedAt` on the edit.
6. **Backdating.** T3 stamps `created_at` at intake, on the machine that runs the agent. A row older than `RELAY_SEEN_LAG_S` at first sight is turned away. A lead never reaches before the thread's previous message, and no minute past its finality changes.
7. **Many threads at once.** One timeline per device: a second goes to one candidate, so ten relayed threads can't credit more than wall time. Across devices, SM 3.4's merge keeps one human-minute per wall-clock minute, so relayed credit on a server and witnessed credit on a laptop can't add up, though in v1 the pair raises `concurrent_devices` (Known limits).
8. **A jiggler on a desktop that runs T3 Code.** A script posts messages through T3's API with `creationSource` `web` while a jiggler moves the pointer and T3's window is in front. Rules 6 and 7, tested at the stamp, see input and a hosting window, so the prompt is `human_typed`, at level B on a machine without the key counter. That is DESIGN 7.12's accepted "pty driver plus a jiggler on a level-B machine", reached through T3's window instead of a terminal, and bounded the same way. A message whose record says `client` `mobile` skips rules 6 and 7, so a phone message can't be passed off as typed here (the `t3-phone` case). An agent's message through T3's MCP tools has no record at all, so rule 4 takes it even while the person types in T3's window (the `t3-here-agent` case).

## Known limits

- Approvals, answers and stops given in T3's own interface aren't messages, so they earn nothing in v1. Neither does an answer to the agent's question that T3 delivers as a message, since T3 makes it with `creationSource` `server`.
- A message queued longer than `RELAY_MATCH_S` earns nothing, and one that pairs more than `PENDING_WINDOW_S` − 60 s after a stop vouches for none of that stop's reading, though it keeps its own lead.
- A steered message earns nothing until a capture shows whether and how Claude Code reports it.
- A follow-up the reader first reads after T3 sent it again, as T3 does when Claude Code declines a steer or the turn ends before the steer lands, witnesses its run at the late stamp, and rules 6 and 7 test it as the message's (as amended 2026-11-23 by the ruling in #225).
- A row the reader first sees more than `RELAY_SEEN_LAG_S` after its stamp earns nothing: one sent while pairtime's agent was down, or while T3 was closed and then reopened later.
- A T3 thread on any provider but Claude Code, Codex included, earns nothing in v1 (as amended 2026-11-23 by the ruling in #225), and neither does a thread whose run T3 can't tie to a session pairtime sees.
- A Claude instance T3 runs with a home of its own loads none of pairtime's hooks, so its messages never pair. `doctor` says so.
- The `agent_app` class rests on a process name a script can set (red team item 3).
- When the reader can't answer, with no `sqlite3` on PATH, a schema the probe refuses or a read that times out, a guest's prompt goes unmarked and keeps its text like any prompt's (decision 7). It still earns nothing.
- In v1 a server's relayed slot merges like any other device's: a laptop and the server crediting the same minute raise `concurrent_devices`, though one person drove the agent from the laptop. A merge that lets the laptop's slot win without a flag needs a slot to say whether all its credit is relayed, which a slot's `ev` and `lbl` can't, and waits for v1.5 with the cross-device join.
- The cross-device join that would raise relayed credit to level B is v1.5.

## Questions for the orchestrator

1. **Phone messages skip rules 6 and 7.** Answered in the review (#194): the record carries `client`, and a `mobile` message skips rules 6 and 7 (the `t3-phone` case). Still open: T3's `web` source can't say which computer a browser ran on, so a message typed in a browser elsewhere while a jiggler moves the pointer here can still score `human_typed` at level B, as red team item 8 says. The stricter rule would apply rules 6 and 7 to a witnessed prompt only with key presses, so only level A can beat `relayed`.
2. **MCP Apps.** T3's MCP Apps can send app-chosen text as an ordinary user turn, `createdBy` `user` and `creationSource` `web`, with no mark to tell it apart (packages/client-runtime/src/mcpApps/host.ts:275-292). It needs the web UI open and an app the owner installed. Such a message counts as relayed. Accept it as a known limit, or ask T3 for a mark.
3. **The steer capture.** Who schedules it, and against which Claude Code version: WP-AD0's kit, through T3?
4. **Deploy order.** The server must accept `via_relay` in `lbl` (ingest-v1 2.3.2 and its shape check) before any client sends it. The scorer PR changes both. The server goes out first. As amended 2026-11-23 by the ruling in #225: the server deploy that carries the T3 Code reader PR (#222), with its privacy notice, goes out before any client release that includes the reader. Only that PR writes `relay.message` records, and only pairtimed serves the notice that says the reader runs.

## What stays

- Rule 4 changes nothing outside agent-app sessions: no terminal, IDE or desktop app is an `agent_app` server, and only T3 Code's reader marks a prompt `guest`. SM 2.8 applies to backfilled records only, so lookback and live T3 sessions never meet.
- Nothing about typing into a terminal, an IDE or an agent's own desktop app changes.
- No tier-1 field is added. `lbl` gains one value, which is why DESIGN 4.3's table doesn't change. `client` and `guest` are event fields, revealed only as tier-2 metadata.
- DESIGN 4.4 gains no row. The agent keeps no copy of an app's text: it reads it, measures and classes it, and drops it, and, when the reader runs, it keeps no text at all for a guest's prompt. The T3 reader's cursor lives in `state.json` (3.5), which holds nothing personal. The records themselves are ledger records like any other, kept as 4.4 already says.
