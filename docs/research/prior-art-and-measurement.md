## 1. Prior art

Everything below was checked against source code, official docs or the project's own site on 2026-11-19 unless marked otherwise. Repo metadata (license, last push) comes from the GitHub API on that date.

The short version: every existing tool measures one of three things. It measures **editor activity** (WakaTime, Hackatime, Wakapi, ActivityWatch), **AI output** (tokens, lines, commits, acceptance; ccusage, Copilot metrics, Cursor, Claude Code analytics, git-ai, Agent Trace), or **screen evidence** (Lapse, Lookout). None of them measures the human's contribution to an AI-assisted session. The tools that put AI work on a clock (WakaTime, Hackatime, vibe-log) all start the clock from agent transcript timestamps, which is the "counts how active your AI agent is" failure Zach describes in BOUNTY.md.

### 1.1 WakaTime: "ai coding" heartbeats from agent transcripts

- **Repo**: [wakatime/wakatime-cli](https://github.com/wakatime/wakatime-cli), BSD-3-Clause, commit `7ab26b5` (2026-11-05). Go.
- **What it measures**: time per project, file, language, branch, plus a category per heartbeat. Categories in `pkg/heartbeat/category.go`: `coding`, `ai coding`, `building`, `code reviewing`, `debugging`, `manual testing`, `running tests`, `writing tests`, `writing docs`, `researching`, `learning`, `planning`, `designing`, `browsing`, `communicating`, `meeting`, `notes`, `indexing`, `translating`, `advising`, `supporting`.
- **AI fields on the heartbeat** (`pkg/heartbeat/heartbeat.go`): `ai_line_changes`, `human_line_changes`, `ai_prompt_length`, `ai_input_tokens`, `ai_output_tokens`, `ai_cached_input_tokens`, `ai_session`, `ai_subscription_plan`. The summaries API adds `ai_additions`, `human_additions`, `ai_deletions`, `human_deletions`, per-model line and cost breakdowns, and `ai_prompt_length_avg` (from the sibling notes on [wakatime.com/developers](https://wakatime.com/developers); not re-fetched).
- **How**: `pkg/ai/` has a parser for each of about 45 harnesses (files such as `claude.go`, `codex.go`, `cursor.go`, `copilot.go`, `copilot_cli.go`, `gemini.go`, `opencode.go`, `windsurf.go`, `cline.go`, `roo.go`, `goose.go`, `amp.go`, `pi.go`, `kiro.go`, `zed.go`, `warp.go`, plus `generic_json.go` and `generic_sqlite.go`). Each parser reads the harness's local transcript or SQLite store after a checkpoint and emits heartbeats:
  - `claude.go` `claudeAppHeartbeat`: one `app`-type heartbeat per user prompt, with `ai_prompt_length` set, stamped with the transcript line's `timestamp`.
  - `claude.go` `claudeFileHeartbeat`: one `file`-type heartbeat per tool result that touched a file, with `ai_line_changes` and `is_write` (`create`/`update`/`delete`), stamped with the transcript time.
  - `transcript_clock.go`: when a transcript line has no timestamp, it reuses the previous line's time or the file mtime, and stores fallback stamps under `<wakatime resources>/ai-timestamps/<sha256(path)>.json` so re-syncs don't move old records.
  - `ai.go`: human editor heartbeats within 2 minutes of AI heartbeats (with no human line changes), or within 30 minutes and before the first human edit, are relabeled `ai coding`. Heartbeats on the same entity and session less than 60 s apart are merged and their counts summed.
  - The server then joins heartbeats into durations with the keystroke timeout (default 15 minutes; [FAQ](https://wakatime.com/faq)).
- **Borrow**: the parser catalogue (BSD-3 is compatible with AGPL-3.0, so code can be ported with attribution). The checkpoint-per-parser design (`checkpoints.go`) for incremental, idempotent transcript reading. The `human_line_changes` vs `ai_line_changes` split. The idea of relabeling editor time near agent activity instead of double-counting it.
- **Falls short**: a heartbeat fires for every agent file edit, so a 3-hour unattended agent run that edits a file every few minutes yields 3 hours of `ai coding` once the 15-minute timeout joins them. There is no notion of the human reading, reviewing, testing or thinking. Prompt *length* is recorded but not prompt intent or repetition. The BOUNTY.md thread notes WakaTime's AI tracking "is widely seen as poor."

### 1.2 Hackatime: WakaTime-compatible server with an AI discount

- **Repo**: [hackclub/hackatime](https://github.com/hackclub/hackatime), MIT, commit `43bde10` (2026-11-19). Rails + Postgres. The sibling doc `hackatime-and-hack-club.md` covers it in depth; this entry is only what matters for prior art.
- **What it measures**: WakaTime heartbeats (it accepts the WakaTime API), with a much shorter join: `app/models/concerns/heartbeatable.rb` sums `LEAST(time - LAG(time), heartbeat_timeout_duration)` per user, where `heartbeat_timeout_duration` defaults to **2 minutes**, not WakaTime's 15. Only categories `coding` and `ai coding` count toward totals (`where(category: [ "coding", "ai coding" ])`).
- **AI handling**: `app/javascript/pages/Home/signedIn/AiCodingMeter.svelte` shows an "AI vs Human Coding" split from `stats["ai coding"]` vs `stats.coding`. `app/models/leaderboard_entry.rb` discounts AI time on the leaderboard: "AI coding earns 90% for the first three hours of a day. After that the rate decays exponentially, halving roughly every 1.4 hours, so a day of AI coding can never be worth more than 90% * (3h + 2h) = 4.5 hours." Constants: `AI_CREDIT_RATE = 0.9`, `AI_FULL_RATE_SECONDS = 3h`, `AI_DECAY_SECONDS = 2h`.
- **Borrow**: the 2-minute gap cap (it keeps idle tails short and is what Hack Club reviewers already calibrate against). The daily diminishing-returns curve as a fallback cap for any signal pairtime can't verify.
- **Falls short**: the discount is a flat haircut on agent-driven time. It can't tell a student reviewing every diff from one who walked away, so it under-credits the first and over-credits the second. Stardance's 123,400 submitted vs 27,600 approved hours (BOUNTY.md R9) is the result.

### 1.3 git-ai: line attribution in git notes

- **Repo**: [git-ai-project/git-ai](https://github.com/git-ai-project/git-ai), Apache-2.0, v1.7.6 (2026-11-05), about 3,000 stars. Rust.
- **What it measures**: which lines of each commit were written by which agent session, model and prompt, and which by a known human. Not time.
- **How**: agents call `git-ai checkpoint` "whenever they write code or modify files with bash scripts" (README). git-ai installs and maintains the agent hooks itself (`git ai install-hooks`, re-checked daily) and does not use git hooks or wrap git. On commit it writes an authorship log as a git note under `refs/notes/ai` ([spec v3.0.0](https://github.com/git-ai-project/git-ai/blob/main/specs/git_ai_standard_v3.0.0.md)). The log is an attestation section (file path, then two-space-indented `<key> <line ranges>`; keys `s_<session>::t_<turn>` for AI sessions, `h_<hash>` for known humans), a `---` divider, and a JSON metadata section with `schema_version: "authorship/3.0.0"`, `base_commit_sha`, `sessions` (each with `agent_id {tool, id, model}` and `human_author`), `humans`, and legacy `prompts` (`total_additions`, `total_deletions`, `accepted_lines`, `overriden_lines`). Supported agents per README: Claude Code, Codex, Cursor, Copilot, OpenCode, Pi, Windsurf, Droid, Amp, Gemini, Continue, Junie, Rovo Dev, Firebender. Prompts are "scanned and redacted, and saved outside of Git."
- **Borrow**: this is the right git-integration layer for R5 and R10. A reviewer can see, per commit, which lines a session wrote and which the human wrote or rewrote (`overriden_lines` is a direct measure of hand-fixing). pairtime can read `refs/notes/ai` if present rather than reimplementing attribution, and can write notes in the same format so reviewers' existing tools work. "Agents report exactly which lines they wrote" (no AI-text detection) matches the BOUNTY.md thread's point that detectors like Pangram are unreliable.
- **Falls short**: no time dimension at all. Lines are a poor proxy for struggle: a one-shot can produce 2,000 attributed lines in two minutes.

### 1.4 Agent Trace (Cursor's attribution RFC)

- **Spec**: [agent-trace.dev](https://agent-trace.dev/), version `0.1.0`, status RFC, dated January 2026, license CC BY 4.0. The page links to `github.com/cursor/agent-trace`, which returned HTTP 404 on 2026-11-19 (moved or made private; the site itself still serves). Credited partners: Amp, Amplitude, Cline, Cloudflare, Cognition, git-ai, Jules, OpenCode, Tapes, Vercel. InfoQ covered it on 2026-02-04 ([article](https://www.infoq.com/news/2026/02/agent-trace-cursor/)).
- **Schema** (JSON Schema 2020-12, `$id` `https://agent-trace.dev/schemas/v1/trace-record.json`, MIME `application/vnd.agent-trace.record+json`): top-level required `version`, `id` (UUID), `timestamp` (RFC 3339), `files`; optional `vcs {type: git|jj|hg|svn, revision}`, `tool {name, version}`, `metadata` (free-form, vendor keys namespaced). `files[] {path, conversations[]}`; `conversations[] {ranges[], url?, contributor?, related[]?}`; `ranges[] {start_line, end_line, content_hash?, contributor?}`; `contributor {type: human|ai|mixed|unknown, model_id?}`. Storage is "implementation-defined" (files, git notes, database).
- **Borrow**: the four-way contributor type (`mixed` is exactly "the human reworked AI code"), and `content_hash` so attribution survives moves. Emitting Agent Trace records alongside git-ai notes costs little and makes pairtime's evidence readable by third-party tools.
- **Falls short**: the only time field is the record `timestamp`. No duration or effort. The spec's own `version` regex (`^[0-9]+\.[0-9]+$`) rejects its `0.1.0` examples, per the fetched page, which says something about its maturity.

### 1.5 vibe-log: session duration from message gaps, LLM-scored prompts

- **Repo**: [vibe-log/vibe-log-cli](https://github.com/vibe-log/vibe-log-cli), MIT, last push 2026-04-19 (quiet since). TypeScript. Reads Claude Code, Codex and Cursor sessions (`src/lib/readers/claude.ts`, `codex.ts`, `cursor.ts`).
- **What it measures**: per-session duration, languages, edited files, model switches, plan-mode exits (`ExitPlanMode` tool uses), and a 0-100 prompt-quality score.
- **How**: `calculateDuration` in `src/lib/readers/claude.ts` sums the gaps between consecutive messages, user *and* assistant, counting only gaps of at most `MAX_IDLE_GAP = 15 * 60` seconds, capped at `MAX_SESSION_DURATION = 8 * 60 * 60`. `src/lib/prompt-analyzer.ts` sends each prompt with 2-3 turns of context to a local Claude (`executeClaude`, default model `haiku`) and asks for a score on "clarity, context, success criteria, examples if needed", a diagnosis of at most 20 words, and an emoji tag (vague, missing context, lacking specificity). Its rubric explicitly scores short direct answers to the agent's questions ("Yes", "PostgreSQL") as 80-100. `src/lib/message-sanitizer.ts` strips content before cloud upload. It also generates standups and "personality" coaching.
- **Borrow**: the prompt rubric, especially "a terse answer to the agent's question is a good prompt", which prevents a length-based score from punishing real steering. Plan-mode exits as an engagement signal. Running the LLM judge locally on the user's own subscription so prompts never leave the machine (R6).
- **Falls short**: duration counts assistant messages, so agent runtime counts as the human's time, which is the same failure as WakaTime. LLM-scored prompts are gameable if the score feeds credit directly.

### 1.6 ccusage: tokens and cost from local logs

- **Repo**: [ccusage/ccusage](https://github.com/ccusage/ccusage) (moved from `ryoppippi/ccusage`), MIT (the LICENSE file is MIT; GitHub reports `NOASSERTION`), v20.0.51 (2026-11-14), about 19,500 stars. TypeScript plus a `rust/` tree.
- **What it measures**: token usage and estimated cost by day, week, month, session, and Claude Code's 5-hour billing window (`ccusage blocks`), for 20 sources: Claude Code, Codex, OpenCode, Amp, Droid, Codebuff, Cline, Hermes Agent, pi-agent, Goose, OpenClaw, Kilo, Kimi, Qwen, Copilot CLI, Gemini CLI, Antigravity, Grok Build CLI, ZCode, DeepSeek Harness (README).
- **Borrow**: its per-source readers are the most widely used open map of where each CLI keeps its logs. A "tokens per human-minute" ratio is a useful dark-flow signal (lots of spend, little steering), and ccusage's math gives the numerator.
- **Falls short**: tokens measure the model's work. Nothing about the human.

### 1.7 SpecStory: local-first transcript capture

- **Repo**: [specstoryai/getspecstory](https://github.com/specstoryai/getspecstory), Apache-2.0 for the repo and CLI; the Cursor and VS Code Copilot extensions are listed as "Closed" source in its README. Last push 2026-11-18.
- **What it does**: saves every AI conversation as Markdown under `.specstory/history/` in the project. CLI providers (open source, `specstory-cli/pkg/providers/`): Claude Code, Codex CLI, Copilot CLI, Cursor CLI, Cursor Cloud Agents (via `CURSOR_API_KEY`), Gemini CLI, Droid, plus others listed in the README. `specstory run <agent>` wraps the agent. Optional sync to `cloud.specstory.com`. `/lore` mines history into agent skills.
- **Borrow**: the in-repo, human-readable transcript as the audit artifact. If a student chooses to submit evidence for R10, a redacted Markdown transcript a reviewer can read is the format reviewers will want. The provider package layout is a model for pairtime's adapter plugins (R7).
- **Falls short**: it records conversations, not time, and wrapping the agent (`specstory run`) is an extra step that R4 forbids. Committing transcripts to the repo is the "security risk" the BOUNTY.md thread warns about.

### 1.8 Wakapi: self-hosted WakaTime-compatible server

- **Repo**: [muety/wakapi](https://github.com/muety/wakapi), MIT, v2.18.2 (2026-10-14), about 4,500 stars. Go.
- **What it measures**: WakaTime heartbeats, so the same thing as 1.1, without the AI-specific parsing (which lives in wakatime-cli).
- **How**: one Go binary. `db.dialect` defaults to `sqlite3` (also `postgres`, `mysql`). Daily summaries are precomputed by cron (`app.aggregation_time`, default `0 15 2 * * *`). `app.heartbeat_max_age` defaults to `4320h` (180 days) for accepting old heartbeats, and `app.data_retention_months` defaults to `-1` (keep forever). `config.default.yml` and README.
- **Borrow**: single binary plus SQLite as the default deployment. Nightly pre-aggregation into summary rows so dashboards never scan raw heartbeats (R11). WakaTime API compatibility, so the existing WakaTime editor plugins can feed pairtime's editor signal for free (R7).
- **Falls short**: inherits WakaTime's activity model.

### 1.9 ActivityWatch: local, privacy-first activity tracking

- **Repo**: [ActivityWatch/activitywatch](https://github.com/ActivityWatch/activitywatch), MPL-2.0, about 19,700 stars, last push 2026-11-15. Python and Rust.
- **What it measures**: active window (app and title), AFK state, browser tab, editor file, per user, all local. No server, no accounts.
- **How**: watchers send *heartbeats* to a local server on `localhost:5600`. A heartbeat merges with the previous event when the data is identical and it arrives within `pulsetime` seconds, so steady state costs one row update instead of one row per poll. The AFK watcher ([aw-watcher-afk](https://github.com/ActivityWatch/aw-watcher-afk), MPL-2.0) polls input every `poll_time = 5` s and marks AFK after `timeout = 180` s without input, sending heartbeats with `pulsetime = timeout + poll_time` (`aw_watcher_afk/config.py`, `afk.py`).
- **Borrow**: the heartbeat-with-pulsetime merge, which is the cheapest correct way to store "still active" on a low-spec laptop (R8). The idea that the AFK signal is *presence*, not content: seconds since last input, never keystrokes (R6). Everything stays local by default.
- **Falls short**: no projects, no server, no AI awareness, and window titles are sensitive (they include file names and page titles), which is more than pairtime should upload.

### 1.10 Lapse and Lookout: Hack Club's timelapse evidence

- **Lapse**: [hackclub/lapse](https://github.com/hackclub/lapse), MIT, commit `202d020` (2026-11-17). "A place for Hack Clubbers to record and share timelapses", which integrates with Hackatime. "All timelapses are encrypted before being published", so only the author can view them until they choose to share. Records through Lookout. Docker services `client`, `server`, `worker` (ffmpeg encoding; "CPU-bound - it's a good idea to put it on a beefy server"), Postgres and Redis. Zach: "currently Lapse is not passive. You need to turn it on to start tracking" (BOUNTY.md).
- **Lookout**: [hackclub/lookout](https://github.com/hackclub/lookout), **AGPL-3.0**, commit `be1b7b9` (2026-11-18), formerly "Collapse". "Simple time-tracking via periodic screenshots as a service, designed to be embedded into Hack Club programs." The client records a short clip every minute (a frame every 10 s, about 6 frames per minute) and uploads it as one capture, or one screenshot per minute if it can't encode video. "The server tracks the number and timing of captures received to validate time." Sessions auto-pause after 10 minutes of inactivity and auto-stop after 24 hours. No users or accounts; a session token issued by the program controls everything. Migration `packages/server/drizzle/0034_capture_activity.sql` adds per-capture `activity` JSON: pointer position as a fraction of the display, the frontmost app and captured-window focus, sampled at every clip frame (marked internal only).
- **Borrow**: Lookout is already AGPL-3.0 and already accepted by Hack Club programs, so pairtime can treat a Lookout session as an optional, user-initiated *evidence attachment* for submitted hours (R10) instead of building its own screen recorder. The per-capture interaction metadata (pointer, frontmost app, focus) is a good model for low-cost presence evidence. The "time is validated by the count and timing of captures the server received" rule is the same idea as server-witnessed timestamps (see grit, 1.14).
- **Falls short**: not passive (R4). Screen capture is the most privacy-invasive option (R6), heavy on a 10-year-old laptop (R8), and expensive to host (video encoding and storage, R11). A timelapse shows a screen, not whether the human was thinking: an agent's terminal scrolling looks busy.

These are enterprise dashboards. None is available to a teenager on a personal plan, but their field choices show what the vendors think is measurable, and Claude Code's local OTel export works on any plan.

- **Borrow**: Claude Code's `active_time` split is the vendor's own admission that agent time and human time are different quantities, and its `type="user"` counter is a ready-made human-time signal for one harness (R2, R7). `tool.blocked_on_user` spans measure human review latency directly. Accept/reject counts per edit are a verification signal. `prompt.id` correlation lets pairtime group everything that followed one human prompt.
- **Falls short**: `user_prompt` also fires for agent-initiated turns, so prompt counts alone overstate human input. Cursor's "non-AI lines" are a remainder, not a measurement. Copilot counts agent edits as added lines with no human acceptance. All three are org-level products; the personal-plan path is local OTel or transcripts.

### 1.12 DX, LinearB, Jellyfish: enterprise AI-impact platforms

- **DX** ([AI Measurement Framework](https://getdx.com/blog/ai-measurement-framework-guide/), updated 2026-05-20): three dimensions. Utilization ("AI tool usage (DAUs/WAUs)", "Percentage of PRs that are AI-assisted", "Percentage of committed code that is AI-generated", "Tasks assigned to agents"); Impact ("AI-driven time savings (developer hours/week)", "Developer satisfaction", "Human-equivalent hours (HEH) of work completed by agents", plus Core 4 measures); Cost ("AI spend", "Net time gain per developer"). Headline from its Q1 2026 report: "developers save an average of 3.9 hours per week with AI coding tools with daily users saving 4.72 hours per week" (no sample size given). Warns that "code generation volume" metrics are "particularly susceptible to gaming" and should not be used "for individual performance evaluation". The page doesn't say how time savings are collected; DX is known for developer surveys (unverified from this page).
- **LinearB** ([AI Insights FAQ](https://linearb.helpdocs.io/article/ww1ciql9uw-linear-b-ai-insights-faq), via the earlier agent's fetch; not re-fetched): four signals: commit co-author trailers, AI-written PR comments, PRs opened by known agents, vendor APIs (Copilot, Claude, Codex). It recommends an `AGENTS.md` rule so Codex appends `Co-authored-by: Codex <codex@openai.com>`, and states it does not store source code for detection.
- **Jellyfish** ([AI Impact](https://jellyfish.co/platform/jellyfish-ai-impact/), via the earlier agent's fetch; not re-fetched): "derives AI signals directly from Git, planning systems, and workflow data"; measures "adoption, usage, spend, and outcomes (speed, quality, productivity)".
- **Borrow**: LinearB's AGENTS.md co-author trailer trick is the cheapest possible universal attribution hook, and it matches Karim's AGENTS.md direction (R7). DX's distinction between utilization (did they use AI) and impact (did it help) maps onto pairtime's split between logged agent activity and credited human struggle.
- **Falls short**: all measure teams and outcomes over weeks, for managers. None measures an individual's effort per hour, and the time-savings numbers are surveys, which are useless for fraud review (R9, R10).

### 1.14 grit in detail (closest competitor)

[N1k0s1/grit](https://github.com/N1k0s1/grit), AGPL-3.0, Go 1.26, pure Go (`CGO_ENABLED=0`), commit `e7cf94e` (2026-11-19 04:36 UTC). Read from README and `internal/score/score.go`, `internal/score/anomaly.go`, `internal/activity/`.

- **Collection**: reads Claude Code transcripts (`~/.claude/projects/*/*.jsonl`) and Codex rollouts (`~/.codex/sessions/**/rollout-*.jsonl`) passively. Other harnesses pipe hook JSON into `grit hook -harness <name> -kind prompt|stop`, appended to `~/.grit/events.jsonl`.
- **Presence signal**: `grit watch` asks the OS every 15 s for seconds since last input (Windows `GetLastInputInfo` + `GetTickCount`; macOS `CGEventSourceSecondsSinceLastEventType` via purego, `ioreg` `HIDIdleTime` fallback; Linux X11 or GNOME Mutter `org.gnome.Mutter.IdleMonitor` over D-Bus). It stores one bit per minute in a 180-byte bitmap per UTC day under `~/.grit/activity`, plus a second bitmap of minutes the sampler was running, so "no input" and "no data" differ.
- **Scoring rules** (`score.Default`): `IdleTimeout` 10 min (a reply within this gap after the agent finishes counts as engaged think time); typing estimate at `ComposeCPS` 3 chars/s clamped to 20 s-4 min; `LowEffortCap` 90 s of think credit for bare go-aheads (a fixed list: "continue", "yes", "ok", "lgtm", "try again", "more", and so on, or any prompt under 4 characters); agent run counts up to `AgentCap` 8 min only if the human came back within `ReturnWindow` 2 min, otherwise only the first `Unsupervised` 1 min; `ReviewTail` 2 min after the last turn. With activity data covering at least `MinCoverage` 50% of the session ("v2"), only minutes with input inside those windows count. Parallel sessions are deduplicated so five agents count as one person.
- **Prompt tags**: `low-effort`, `debugging` (regex for error, bug, crash, traceback, "doesn't work", why, stuck, still, and similar), `specific` (200 or more characters).
- **Session flags** (never change credit): `autopilot` (at least 4 prompts and half or more low-effort), `mostly-agent` (agent time more than 4x credited), `long-idle` (wall time over 1 h and credited under 20% of it), `regular-timing` (6 or more prompts with coefficient of variation of spacing under 0.1), `repeated-prompts` (same prompt or same template with numbers changed, 3 or more times), `no-input-prompts` (prompts arriving with no keyboard or mouse input), `no-output` (1 h or more with no file touched or commit).
- **Attestation**: `grit sync` sends numbers only (start, end, credited seconds, counts, rule strings). Each turn adds a link in a hash chain over (prompt time, kind, sha256 of redacted prompt), salted per session. The server records when it first saw each link. On `grit submit`, the server recomputes the chain: turns seen within 15 min are **witnessed**, later ones **backfilled**, mismatches fail. Trust tier per session: high (witnessed and activity-scored), medium (one), low (neither).
- **Server**: `gritd`, one Go binary with SQLite, public profiles, projects, git links, leaderboard, live updates over SSE, and a review queue where a reviewer reads prompts and approves, deflates or rejects. README estimates 150,000-250,000 sessions/month and about 1 GB/month of new data, "well under $50", not yet load-tested.
- **Self-reported gaps**: scripted prompts plus a mouse jiggler are caught only by timing/repetition flags and reviewers; hand edits are judged per minute; witnessing needs `grit watch` running; Windows and Linux idle paths compile in CI but hadn't been run on real machines.
- **What this means for pairtime**: grit already covers the core thesis, at least on paper. pairtime's differentiation has to come from (a) accuracy validated against reviewer judgments (R2, R9), not hand-tuned windows; (b) broader harness coverage via an adapter model plus AGENTS.md fallback (R7); (c) the motivation layer, which grit barely has (R3); and (d) adoption by programs (acceptance criterion A). The bounty goes to the first entry to reach 1,000 weighted projects, so program adoption is the real race, not features.

## 2. Measurement science

### 2.1 Productive struggle in education research

Zach's phrase "hours of productive struggle" comes from mathematics education. The research gives pairtime a definition to measure against and three warnings.

- **Hiebert and Grouws (2007)**, "The Effects of Classroom Mathematics Teaching on Students' Learning", in *Second Handbook of Research on Mathematics Teaching and Learning* (ed. Lester), pp. 371-404, quoted at p. 387 in [NCTM's productive-struggle slides](https://www.nctm.org/uploadedFiles/Conferences_and_Professional_Development/Institutes/Supporting_Students_Productive_Struggle/ProductiveStruggle_Keynote-Smith_Slides.pdf): struggle means "students expend effort to make sense of mathematics, to figure something out that is not immediately apparent… The struggle we have in mind comes from solving problems that are within reach and grappling with key mathematical ideas that are comprehendible but not yet well formed." Their review names it, with explicit attention to concepts, as one of two features of teaching that build conceptual understanding (from memory of the chapter; the slides quote only the definition).
- **Kapur, productive failure**: "Productive Failure", *Cognition and Instruction* (2008), [doi:10.1080/07370000802212669](https://doi.org/10.1080/07370000802212669). The 2016 framework paper ([doi:10.1080/00461520.2016.1155457](https://doi.org/10.1080/00461520.2016.1155457), *Educational Psychologist*): "Learning and performance are not always commensurable. Conditions that maximize performance in the initial learning may not maximize learning in the longer term." It names four designs: productive success, productive failure, unproductive success, unproductive failure, and argues that even direct instruction "may well be an unproductive success" compared with productive failure. The meta-analysis (Sinha and Kapur 2021, *Review of Educational Research*, [doi:10.3102/00346543211019105](https://doi.org/10.3102/00346543211019105)): 53 studies, 166 comparisons, problem-solving-then-instruction beat instruction-then-problem-solving with "Hedge's g 0.36 [95% confidence interval 0.20; 0.51]", 0.37-0.58 when implemented with high fidelity to productive failure, and 0.87 after correcting for publication bias. Exception: effects "favored I-PS" for second to fifth graders and for domain-general skills.
- **Bjork, desirable difficulties**: Bjork and Bjork (2011), "Making things hard on yourself, but in a good way" ([PDF, Bjork Lab](https://bjorklab.psych.ucla.edu/wp-content/uploads/sites/13/2016/11/Making-Things-Hard-on-Yourself-but-in-a-Good-Way-20111.pdf)): "Conditions of learning that make performance improve rapidly often fail to support long-term retention and transfer, whereas conditions that create challenges and slow the rate of apparent learning often optimize long-term retention and transfer." Desirable difficulties (Bjork 1994) "include varying the conditions of learning… interleaving instruction on separate topics… spacing, rather than massing, study sessions… and using tests, rather than presentations, as study events." The qualifier: "If, however, the learner does not have the background knowledge or skills to respond to them successfully, they become undesirable difficulties."

**What this means for pairtime** (R2, R9):

1. *Struggle is effort toward something not yet understood, within reach.* Its log signature is the human working on a problem the agent hasn't already solved: reading, forming a hypothesis, testing it, fixing. Agent runtime is not struggle, and neither is the human idling while the agent works.
2. *Speed is not the opposite of struggle.* Kapur's quadrants map neatly onto AI coding. A one-shot that works is **unproductive success** (high output, little learning: the "2 minutes of productive struggle" in Zach's vision post). Re-prompting "fix it" until it works, or dark flow, is **unproductive failure** or unproductive success depending on whether it ends up working. A student who hits errors, reads, and fixes them is in **productive failure**, which is the time to credit. A student who already knows what to do and uses the agent to go faster (Barke's acceleration) is in **productive success**, which also counts.
3. *Not all difficulty is desirable.* Bjork's caveat means a beginner stuck for an hour with no progress isn't necessarily struggling productively. Credit should follow evidence of *progress* (a test that starts passing, an error that stops recurring, a commit), not difficulty alone. Otherwise the tracker rewards being lost.
4. *Spacing beats massing.* Short sessions spread over days are better for learning than one marathon, so pairtime's motivation layer (section 4) should reward consistency over long sessions, which also cuts against farming hours.

### 2.2 How people program with AI

#### CUPS (Mozannar, Bansal, Fourney, Horvitz; CHI 2024)

"Reading Between the Lines: Modeling User Behavior and Costs in AI-Assisted Programming", [arXiv:2210.14306](https://arxiv.org/abs/2210.14306) v5 (2024-04-22). Read from the full text.

- **Design**: 21 programmers solved tasks with GitHub Copilot, then watched their own screen recording and labeled each telemetry segment with a CUPS state. Mean task time 12.23 min (max 20.80). 1,024 suggestions shown, 34.0% accepted (per-participant mean 36.5%, range 14.3%-60.7%). 3,137 labels.
- **States** (Table 1): Thinking/Verifying Suggestion; Not Thinking ("programmer away from keyboard"); Deferring Thought For Later ("accepts suggestion without completely verifying it, but plans to verify it after"); Thinking About New Code To Write; Waiting For Suggestion; Writing New Code; Editing Last Suggestion; Editing (Personally) Written Code; Prompt Crafting; Writing Documentation; Debugging/Testing Code; Looking up Documentation; Accepted; Rejected.
- **Time shares**: verifying suggestions was the largest state, "22.4% (sN = 12.97)" of session time; writing new functionality was second at 14.05%; waiting for suggestions 4.2%. The Copilot-specific states (verifying, deferring, waiting, prompt crafting, editing suggestion) together took "51.5 % (sN = 19.3) of the average session duration".
- **Transitions**: Prompt Crafting → Verifying (p = 0.54); Deferring Thought → Verifying (p = 0.54): "deference incurs verification debt, and this debt often 'catches up' with the programmer"; Writing New Functionality → Verifying (p = 0.59).
- **For pairtime**: in completion-style AI coding, *verification is the single biggest human activity*, bigger than writing code. A tracker that drops verification time drops a quarter of the real work. "Deferring thought" is the measurable form of skipping verification, and the paper shows it usually has to be paid back later.

#### Grounded Copilot (Barke, James, Polikarpova; 2022-2023)

"Grounded Copilot: How Programmers Interact with Code-Generating Models", [arXiv:2206.15000](https://arxiv.org/abs/2206.15000) v3 (2022-10-31). Published in PACMPL (OOPSLA) 2023 (venue from memory; the arXiv PDF still carries the ACM template placeholder). Read from the full text.

- **Design**: grounded theory from 20 participants on four tasks (Chat Server, Chat Client, Benford's Law, Advent of Code) in Python, Rust, Haskell and Java, plus coded livestreams.
- **Finding**: interactions are "bimodal". "In acceleration mode, the programmer already knows what they want to do next, and Copilot helps them get there quicker; interactions in this mode are fast and do not break programmer's flow. In exploration mode, the programmer is not sure how to proceed and uses Copilot to explore their options or get a starting point for the solution; interactions in this mode are slow and deliberate, and include explicit prompting and more extensive validation."
- **Acceleration**: happens after the programmer decomposes the task into "microtasks" (4.1.1); focuses on small logical units (4.1.2); "long, multi-line suggestions are at best dismissed out of hand and at worst distract the programmer away from their flow" (4.1.3); validation is visual "pattern matching" (4.1.4).
- **Exploration**: triggered by novel tasks or unexpected behavior (4.2.1); explicit prompting with comments (4.2.3); comparing multiple suggestions (4.2.4); explicit validation by "code examination, code execution (or testing), relying on IDE-integrated static analysis (e.g. a type checker), and looking up documentation" (4.2.5); willing to accept and then edit (4.2.6).
- **Time**: exploration took 248.6 participant-minutes vs 104.7 for acceleration. In exploration, validation leaned to comprehension (examination, documentation); in acceleration, to "rapid feedback on code correctness (execution)".
- **For pairtime**: both modes are productive struggle, but they look different in logs. Acceleration is short, frequent, low-latency accepts by someone who has already decomposed the problem; exploration is slower, with reading, doc lookups, edits and test runs. A credit rule must not mistake acceleration's speed for disengagement, or exploration's long pauses for idleness. Decomposition (the human splitting work into microtasks) is the skill that unlocks acceleration, and it shows up in agent sessions as specific, scoped prompts.

#### Anthropic: "Agentic coding and persistent returns to expertise" (2026-06-16)

Page title "How Claude Code is used in practice" ([link](https://www.anthropic.com/research/claude-code-expertise)). Hitzig, Massenkoff, Lyubich, Zhang, Heller, McCrory (Economics team).

- **Data**: "~400,000 interactive sessions from ~235,000 people between October 2025 and April 2026", CLI, Claude.ai and desktop; headless `claude -p` excluded. Classifiers are Claude Sonnet 4.6 on privacy-preserving pipelines; "more than 90% of sessions our classifier labeled as creating or modifying code showed code changes in the telemetry."
- **Expertise measure**: a task-specific 5-point rating from three cues: "how precisely the user frames their directions", "what they ask Claude to verify", and "whether the user tends to correct Claude or Claude tends to correct the user".
- **Results**: "The greater domain expertise a person brings to a session, the more work Claude does per instruction." Novice prompts set off "about five Claude actions and roughly 600 words of output"; expert prompts "12 actions" and "3,200 words". Controlled effect: "+9% actions and +13% output per expertise level". Verified success: novices 15%, intermediate and up 28-33%; partial success 77% vs 91-92%. "19% of sessions where the user appears to be a novice end abandoned, against 5-7% for everyone else." Pooled: about 4 turns per session, about 10 actions per prompt; "people make about 70% of the planning decisions but only 20% of the execution decisions."
- **Metrics it proposes**: per session, "the user's share of planning decisions and the user's share of execution decisions"; actions and output per prompt; a success-signal score whose hard signals are "git activity like commits and pull requests matching the work", "test suites passing", "explicit affirmation from the user"; a failure-signal score from errors, test failures, repeated attempts and user objections; "verified success" = judged successful plus at least one hard signal; "abandoned" = troubled, failed and zero lines written. Nine work modes: build, fix, test, orchestrate, operate, understand, plan, analyze, communicate.
- **For pairtime**: two warnings and one gift. Warning 1: *agent actions per prompt rise with expertise*, so "the agent did a lot per prompt" is a sign of skill, not of laziness. A rule that penalizes long agent runs punishes the students who steer best. Warning 2: the strongest markers of engaged use (precise framing, asking for verification, correcting the agent) are properties of prompt *content*, so they need local analysis of prompts that never leave the machine (R6). Gift: hard success signals (commits matching the work, tests passing) are cheap to detect locally and are exactly what a reviewer wants attached to submitted hours (R10).

#### Anthropic: "Measuring AI agent autonomy in practice" (2026-02-18)

[Link](https://www.anthropic.com/research/measuring-agent-autonomy). McCain, Millar, Huang, et al. (Societal Impacts).

- **Measures**: turn duration ("how much time has elapsed between when Claude starts working and when it stops"; a turn ends when Claude finishes, asks a question, or the user interrupts), auto-approve share, interrupt rate, Claude-initiated clarification stops.
- **Numbers**: "The median turn lasts around 45 seconds", stable between 40 and 55 s. The 99.9th percentile "nearly doubled, from under 25 minutes to over 45 minutes" from Oct 2025 to Jan 2026, then declined somewhat. Full auto-approve: "roughly 20%" of sessions for users with under 50 sessions, "over 40%" by 750 sessions. Interrupts: "New users (those with around 10 sessions) interrupt Claude in 5% of turns"; "more experienced users interrupt in around 9% of turns". "On the most complex tasks, Claude Code stops to ask for clarification more than twice as often as humans interrupt it." Internal: interventions per session fell from 5.4 to 3.3 (Aug-Dec 2025).
- **For pairtime**: (a) the median agent turn is about 45 s, so in most sessions the human is waiting less than a minute per turn and the interesting time is *between* turns. (b) Long turns are rare (the 99.9th percentile is 25-45 min), so a cap on credited agent time per turn affects few honest turns. (c) Experienced users *both* auto-approve more and interrupt more: they shift from approving each action to monitoring and stepping in when needed. Auto-approve is therefore not evidence of disengagement, but interrupts are evidence of engagement. (d) Agent-initiated clarification questions are common; a human's answer to one is a real decision even if it is one word (compare vibe-log's rubric, 1.5).

#### Anthropic: "How AI assistance impacts the formation of coding skills" (2026-01-29)

[Link](https://www.anthropic.com/research/AI-assistance-coding-skills); paper "How AI Impacts Skill Formation", arXiv 2601.20245 (Judy Hanwen Shen, Alex Tamkin). Randomized trial, 52 mostly junior engineers learning the Trio async library: 10 min warm-up, 35 min building two features, 25 min quiz. The treatment group had a sidebar assistant that "could at any time produce the correct code if asked" (design details from the earlier agent's fetch; results re-fetched 2026-11-19).

- **Result**: "the AI group averaged 50% on the quiz, compared to 67% in the hand-coding group" (Cohen's d = 0.738, p = 0.01). "The largest gap in scores between the two groups was on debugging questions." The AI group was about 2 minutes faster (about 23 vs 25 min), not significant (p = 0.391).
- **Interaction patterns** (alt text gives minutes and mean quiz score; n per pattern in parentheses):

| Pattern | n | Time | Quiz | What they did |
|---|---|---|---|---|
| AI delegation | 4 | 19.5 min | 39% | "wholly relied on AI to write code"; fastest, "encountered few or no errors" |
| Progressive AI reliance | 4 | 22 min | 35% | asked one or two questions, then "delegated all code writing" |
| Iterative AI debugging | 4 | 31 min | 24% | "relied on AI to debug or verify their code", slowest |
| Generation-then-comprehension | 2 | 24 min | 86% | generated code, then "asked the AI assistant follow-up questions to improve understanding" |
| Hybrid code-explanation | 3 | 24 min | 68% | asked for code "along with explanations" |
| Conceptual inquiry | 7 | 22 min | 65% | "only asked conceptual questions"; "encountered many errors, they also independently resolved them" |

- **Quotes that matter**: "Cognitive effort—and even getting painfully stuck—is likely important for fostering mastery." Several participants "took up to 11 minutes (30% of the total time allotted) composing up to 15 queries." The authors' caveat: the pattern analysis "does not draw a causal link".
- **For pairtime**: this is the most directly usable study. (1) *Time on task does not separate the groups*: the worst learners (iterative AI debugging, 24%) spent the *most* time, 31 min. So pairtime cannot use session length, or even prompt count, as a proxy for struggle. (2) What separates them is the *kind* of prompt: conceptual questions and requests for explanation went with high scores; delegation and "fix it for me" debugging went with low scores. "Iterative AI debugging" is the lab version of the re-prompting loop BOUNTY.md says shouldn't count. (3) Resolving errors oneself is the high-value activity; it shows up in logs as errors followed by human edits or human-authored fixes rather than another "fix it" prompt.

#### METR: experienced open-source developers (2025) and follow-ups (2026)

- **2025 RCT**: "Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity" ([arXiv:2507.09089](https://arxiv.org/abs/2507.09089), v2 2025-07-25; Becker, Rush, Barnes, Rein). "16 developers with moderate AI experience complete 246 tasks in mature projects", mainly with Cursor Pro and Claude 3.5/3.7 Sonnet. AI "increases completion time by 19%". Developers forecast a 24% reduction beforehand and estimated a 20% reduction afterward.
- **Late-2025 follow-up** ([METR blog, 2026-02-24](https://metr.org/blog/2026-02-24-uplift-update/)): 57 developers, 143 repos, 800+ tasks. Returning developers "-18% with a confidence interval between -38% and +9%"; new developers "-4%, with a confidence interval between -15% and +9%" (negative = faster). METR calls this "an unreliable signal" because developers refused to work without AI (30-50% of surveyed developers withheld some tasks; one said "I avoid issues like AI can finish things in just 2 hours, but I have to spend 20 hours"), and because "our measurements of time-spent on each task are unreliable" for "developers who use multiple AI agents concurrently". Developers "would often work an unrelated task while waiting for the agent to complete its work."
- **Self-report survey** ([METR, 2026-05-11](https://metr.org/blog/2026-05-11-ai-usage-survey/)): 349 technical workers, median self-reported 1.4-2x change in value of work and 3x in speed. METR: "survey results are not necessarily grounded in reality"; in its 2025 study "people overestimated AI's effect on their time spent on tasks by 40 percentage points on average."
- **Task substitution** ([METR, 2026-05-08](https://metr.org/blog/2026-05-08-task-substitution-and-uplift/); Cunningham, Whitfill): theory note. AI shifts people toward tasks it makes cheap, including "Cadillac Tasks" done "only because AI has made it cheap", so speedup on observed tasks can overstate value.
- **For pairtime**: (1) *People cannot estimate their own AI-assisted time*: a 39-43 point gap between perceived and measured speed. So self-declared hours are worthless as evidence and pairtime must measure (R9). (2) METR, with paid participants and screen recordings, could not get reliable task times once developers ran agents in parallel and did other work while waiting. Wall-clock per task is the wrong unit; pairtime has to attribute *human* minutes, deduplicated across concurrent sessions, which is what grit does (1.14). (3) "Waiting for the agent" while doing unrelated work is common and must not be credited to the project the agent is working on, but should be credited to whatever the human is actually doing (R4's "5 projects in an afternoon").

#### Anthropic Economic Index on Claude Code (2025-04-28) and "Learning curves" (2026-03-24)

- **Software development report** ([2025-04-28](https://www.anthropic.com/research/impact-software-development)): 500,000 coding interactions from April 6-13, 2025, split evenly between Claude Code (first-party API only) and Claude.ai Free/Pro. "79% of conversations on Claude Code were identified as 'automation'" vs "only 49% of Claude.ai conversations". Patterns: Directive ("Complete task delegation with minimal interaction") 43.8% on Claude Code vs 27.5% on Claude.ai; Feedback Loop ("Task completion guided by environmental feedback", where Claude acts autonomously "but with help of human validation", e.g. the user pasting errors back) 35.8% vs 21.3%. Augmentation patterns (Task Iteration, Learning, Validation) "were substantially lower on Claude Code". "AI-assisted coding currently requires a lot of human reviewing and iteration relative to non-coding tasks."
- **Learning curves** ([2026-03-24](https://www.anthropic.com/research/economic-index-march-2026-report), Claude.ai and API data from Feb 5-12, 2026): users who signed up 6+ months earlier "have a 10% higher success rate" (about 3-5 percentage points in regressions with task controls). "High tenure users are more likely to use Claude to iterate on their work" and "much less likely to delegate greater responsibility through directive use patterns." This "contradicts" Anthropic's earlier hypothesis that automation is typical of sophisticated users: "the most advanced users are more likely to iterate with Claude."
- **For pairtime**: the five-way classification (directive, feedback loop, task iteration, validation, learning) is a ready-made, published taxonomy for labeling *each human turn* locally. Directive turns are delegation; feedback-loop turns (pasting an error back) are borderline (they are the "iterative AI debugging" pattern from the skill study when repeated without human reasoning); task iteration, validation and learning turns are engagement. Experienced users iterate more, not less, so engagement markers rise with skill.

#### "Your Brain on ChatGPT" (Kosmyna et al., MIT Media Lab, 2025)

[arXiv:2506.08872](https://arxiv.org/abs/2506.08872) v2 (2025-12-31). 54 participants wrote essays in three groups (LLM, Search Engine, Brain-only) over three sessions; 18 did a fourth session with conditions swapped. EEG: Brain-only showed "the strongest, most distributed networks", "LLM users displayed the weakest connectivity", and "Cognitive activity scaled down in relation to external tool use." "Self-reported ownership of essays was the lowest in the LLM group", and "LLM users also struggled to accurately quote their own work." LLM-to-Brain participants "showed reduced alpha and beta connectivity, indicating under-engagement."

- **For pairtime**: essays, not code, and a small sample, so weak evidence for coding. The usable idea is the *ownership probe*: can the person explain or reproduce what they made? That is cheap to ask in a submission flow ("explain this function you shipped") and hard to fake at scale, and it gives reviewers a direct check (R10).

#### Microsoft Research survey on critical thinking (Lee et al., CHI 2025)

"The Impact of Generative AI on Critical Thinking: Self-Reported Reductions in Cognitive Effort and Confidence Effects From a Survey of Knowledge Workers" ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/the-impact-of-generative-ai-on-critical-thinking-self-reported-reductions-in-cognitive-effort-and-confidence-effects-from-a-survey-of-knowledge-workers/); CHI 2025, [doi:10.1145/3706598.3713778](https://doi.org/10.1145/3706598.3713778)). Lee, Sarkar, Tankelevitch, Drosos, Rintel, Banks, Wilson. The task brief calls it "Microsoft/CMU"; the first author was a CMU PhD student (from memory; the Microsoft page lists no affiliations). 319 knowledge workers, 936 examples. "Higher confidence in GenAI is associated with less critical thinking", "higher self-confidence is associated with more critical thinking", and "GenAI shifts the nature of critical thinking toward information verification, response integration, and task stewardship."

- **For pairtime**: the three named activities are the human's job in AI-assisted work, and they are a better definition of "productive struggle with AI" than "writing code": **verification** (checking output: reading diffs, running tests), **integration** (fitting output into the project: hand edits, resolving conflicts, wiring things together), and **stewardship** (owning the goal: planning, scoping, deciding, rejecting). Each has log signals (section 3).

#### Dark flow (Thomas 2026; Dixon et al. 2018)

- **Rachel Thomas**, "Breaking the Spell of Vibe Coding", [fast.ai, 2026-01-28](https://www.fast.ai/posts/2026-01-28-dark-flow/), the post Zach links. Vibe coding fails flow's preconditions: it "does not provide clear clues of how well one is performing"; "The match between challenge level and skill level is murky"; it gives "a false sense of control". Behaviors: generating code "with the intention that the code will not be read by humans", "excessively prompting the thing and wasting tokens" (quoting Armin Ronacher), building "a ton of tools I did not end up using much", taking agent activity and code volume as progress, and following the LLM's suggested next steps "down paths they wouldn't otherwise take". "Individuals are terrible judges of their own productivity."
- **Source**: Dixon, Stange, Larche, Graydon, Fugelsang, Harrigan, "Dark Flow, Depression and Multiline Slot Machine Play", *Journal of Gambling Studies* 2018, [doi:10.1007/s10899-017-9695-1](https://doi.org/10.1007/s10899-017-9695-1) (abstract via Europe PMC; PMC5846824). A *loss disguised as a win* is a spin that returns fewer credits than the wager; players respond to LDWs "as if they are wins"; LDWs create a "smoother" experience that promotes "a highly absorbing, flow-like state that we have called 'dark flow'"; dark flow correlated with problem-gambling severity and depression.
- **For pairtime**: the slot-machine analogy points at specific, loggable shapes. *Re-rolling*: the same or near-same prompt again after an unsatisfying result, with no human change in between. *LDW*: an agent turn that produces lots of output (files touched, lines changed) but no progress signal (tests still failing, the same error recurring, changes reverted later). *No reading*: next prompt arrives faster than the human could have read the output. *Menu-following*: the human's prompt just accepts the agent's offered next step ("yes, do option 2") over and over. None of these needs prompt content to leave the machine.

#### Teens and novices, including 2026 work

Abstracts read from arxiv.org on 2026-11-19.

- **Kazemitabaar et al., CHI 2023** ([arXiv:2302.07427](https://arxiv.org/abs/2302.07427)): the one controlled study with Hack Club's age group. "69 novices (ages 10-17)" did 45 Python authoring tasks, half with Codex, each followed by a manual code-modification task. Codex gave "1.15x increased completion rate and 1.8x higher scores" "while not decreasing performance on manual code-modification tasks". One-week retention was slightly better with Codex (not significant), and "learners with higher Scratch pre-test scores performed significantly better on retention post-tests, if they had prior access to Codex." **For pairtime**: AI help doesn't automatically block learning for teens. What matters is whether they still do the modification work themselves, which is the "hand edit after AI output" signal.
- **Rinja et al., AIED 2026** ([arXiv:2604.27134](https://arxiv.org/abs/2604.27134), 2026-04-29), "Unpacking Vibe Coding": 19,418 interaction turns from 110 undergraduates. "Top performers engaged in instrumental help-seeking -- inquiry and exploration", while "low performers relied on executive help-seeking, frequently delegating tasks and prompting the AI to assume an executor role focused on ready-made solutions." "Generative AI mirrors student intent (whether productive or passive)." **For pairtime**: this is a log-level replication of the Anthropic skill-study patterns with 5x the participants. The instrumental/executive split is classifiable per prompt.
- **Sankaranarayanan 2026** ([arXiv:2602.20206](https://arxiv.org/abs/2602.20206), v2 2026-03-31), "Mitigating 'Epistemic Debt'": N = 78, Cursor plugin with Claude 3.5 Sonnet, three conditions (manual, unrestricted AI, scaffolded AI with an "Explanation Gate", a teach-back check before generated code is integrated). Both AI groups beat manual on functional output (p < .001) and didn't differ from each other (p = .64), "yet unrestricted AI users suffered a 77% failure rate on a subsequent 30-minute AI-blackout maintenance task, vs. only 39% in the scaffolded group." "Successful vibe coders naturally self-scaffold, treating AI as a consultant rather than a contractor." **For pairtime**: shipped output doesn't distinguish engaged from passive builders, but an AI-free maintenance probe does, and teach-back prompts cut failure roughly in half. An optional "explain your change" step at submission is a cheap version of the probe (R10), and a "consultant vs contractor" framing is good language for the recap UI (R3).
- **Shakiba and Chaffey 2026** ([arXiv:2611.04783](https://arxiv.org/abs/2611.04783), 2026-11-03), "Who Is Doing the Thinking?": the Human Agency Depth Taxonomy (HADT), "a preliminary six-tier taxonomy that classifies the engineering contribution a student makes in a prompt, independent of the AI's output", on 962 prompts from 105 first-year students over ten weeks. "Most prompts (84.2%) carried some student contribution beyond delegation." Agency followed the project phase: architecture-discovery prompts were 48% of turns in the requirements phase and 5-12% from week 9, while prompts "analysing existing systems rose during build and verification (odds ratio 2.88)". "Two-thirds of the variance in tier lay within students, so agency depended more on the phase of work than on the student." "Explicitly specifying constraints on the AI's output was rare throughout." **For pairtime**: (1) classify *turns*, not *people*: the same student moves between delegation and deep engagement by phase, so a per-user "trust score" would be wrong two-thirds of the time; (2) what engaged prompts look like changes over a project (design questions early, analysis of existing code later), so a single keyword rule will misfire; (3) constraint-specification is rare and is a skill worth surfacing in recaps.
- **Anthropic Education Report** ([2025-04-08](https://www.anthropic.com/research/anthropic-education-report-how-university-students-use-claude); from the earlier agent's fetch, not re-fetched): 574,740 student conversations; "nearly half (~47%)" were Direct (resolve the query as quickly as possible) rather than Collaborative; the four Direct/Collaborative × Problem Solving/Output Creation patterns were each 23-29%.

### 2.3 What the research agrees on

| Finding | Evidence | Implication for the credit rule |
|---|---|---|
| Verification is the largest human activity in AI-assisted coding | CUPS: 22.4% of time verifying; Barke: examination dominates exploration | Credit reading and checking output, not just typing |
| Time on task does not separate learners from delegators | Skill study: lowest scorers spent the most time (31 min) | Session length, wall clock, prompt count can't be the measure |
| Prompt *kind* does separate them | Skill study, Rinja (instrumental vs executive), HADT, Economic Index patterns | Classify each human turn locally (inquiry, explanation request, constraint, verification, correction vs delegation, go-ahead, re-roll) |
| Engagement varies within a person by phase | HADT: two-thirds of variance within students | Score turns and sessions, not users |
| Expert steering makes the agent do *more* per prompt | Anthropic expertise study: 12 vs 5 actions per prompt | Never penalize long agent runs as such; credit the human's steering and review around them |
| Experienced users auto-approve more and interrupt more | Agent autonomy study | Interrupts and rejections are engagement; auto-approve is neutral |
| Self-report of AI-assisted time is wrong by about 40 points | METR 2025 and 2026 | Don't accept self-declared hours (R9) |
| Concurrent agents break wall-clock timing | METR 2026 | Attribute human minutes, deduplicate across sessions |
| Resolving errors yourself is where learning happens | Skill study ("getting painfully stuck"), Kapur, Bjork | Credit debugging done by the human; don't credit "fix it" loops |
| Output alone can't tell engaged from passive work | Epistemic debt study: equal output, 77% vs 39% maintenance failure | Use process evidence and optional teach-back probes, not output |

## 3. Signals that separate engaged from passive work

This section turns section 2 into things a local agent can measure. Exact payload formats per harness belong to the sibling doc `ai-harness-signals.md`; here, "source" names the kind of log. Claude Code examples are from the [hooks reference](https://code.claude.com/docs/en/hooks) (33 events as of 2026-11-19) and the [monitoring reference](https://code.claude.com/docs/en/monitoring-usage).

### 3.1 The unit of measurement

Count **human minutes**, not session time and not agent time. A minute is credited when there is evidence the human was present *and* doing one of the activities the research identifies as the human's job: steering (planning, prompting with intent, deciding), verifying (reading output, reviewing diffs, running and testing), integrating (editing by hand, fixing, wiring), or debugging. Each credited minute carries the rule that credited it, as in grit (1.14), so reviewers can audit it (R10).

The natural structure is the *turn*: human input, agent run, agent stops, human gap, next human input. Anthropic's autonomy study puts the median agent turn at about 45 s, so most of the human's time sits in the gaps between turns and in work outside the agent (editor, terminal, browser).

### 3.2 Engagement signals

"Local only" means computed on the machine; only the derived number or label syncs (R6).

| # | Signal | How to measure | Source | Evidence | Gaming risk |
|---|---|---|---|---|---|
| S1 | **Presence** | Seconds since last keyboard or mouse input, sampled every 5-15 s, stored as one bit per minute. Windows `GetLastInputInfo` + `GetTickCount`; macOS `CGEventSourceSecondsSinceLastEventType`; Linux X11 screensaver or GNOME `org.gnome.Mutter.IdleMonitor` (grit `internal/activity`). No key identity | OS | ActivityWatch AFK (180 s timeout), grit, Lookout auto-pause at 10 min | Mouse jigglers; needs S2 and S10 to back it |
| S2 | **Focus** | Frontmost app classified locally into editor / terminal / browser-docs / harness / other; only the category is kept | OS | Lookout records frontmost app and window focus per capture | Leaving the IDE focused while away (caught by S1) |
| S3 | **Human-typed prompt** | A prompt event with keyboard presence in the preceding minute(s) and composition time consistent with its length; a prompt with no input at all is not human | Harness hook or transcript + S1 | grit `no-input-prompts`; Claude Code `UserPromptSubmit` "also fires on turns Claude Code starts on its own" | Scripted prompts plus a jiggler; typing an LLM's text by hand (slow, so self-limiting) |
| S4 | **Prompt kind** | Local classifier per human turn: inquiry or conceptual question, request for explanation, constraint or acceptance criteria, verification request, correction of the agent, design decision, vs delegation, bare go-ahead, re-roll | Transcript, local model or rules | Skill study (conceptual inquiry 65%, generation-then-comprehension 86% vs delegation 39%); Rinja (instrumental vs executive help-seeking); HADT; Economic Index patterns; Anthropic expertise cues (precise framing, asking to verify, correcting Claude) | Writing "inquiry-shaped" prompts. Feeds credit only as a modest multiplier and as reviewer evidence |
| S5 | **Reading time** | Gap between agent stop and the next human action, with presence, compared with output length. Silent reading of English prose averages 238 wpm (most adults 175-300; [Brysbaert 2019](https://doi.org/10.1016/j.jml.2019.104047)); code is slower (unverified). Next prompt in under ~25% of minimum reading time = output not read | Transcript + S1 | CUPS: verification is 22.4% of time; dark flow: code "not read by humans" | Waiting before replying. Capped per turn, so cheap to fake but low payoff |
| S6 | **Review decisions** | Permission prompts answered (accept, reject, edit), decision latency; interrupts mid-turn | `PermissionRequest`, `PreToolUse`; transcript interrupt markers; Claude Code `code_edit_tool.decision` metric, `tool.blocked_on_user` span | Autonomy study: experienced users interrupt in about 9% of turns vs 5% for new users | Rubber-stamping accepts. Rejections and interrupts are the strong signal |
| S7 | **Hand edits** | Lines changed in the editor by the human (editor plugin, e.g. WakaTime's `human_line_changes`), or working-tree changes not attributable to an agent tool call | Editor plugin, file watcher, git-ai `h_` attestations and `overriden_lines` | Kazemitabaar (manual modification preserved learning); CUPS "Editing Last Suggestion"; Agent Trace `mixed` | Pasting AI output into the editor. Mitigated by paste-size heuristics in the plugin |
| S8 | **Run and test cycles** | Human-run commands in the terminal (shell integration) or agent-run tests the human asked for; result transitions (fail to pass), error recurrence | Terminal, harness tool results | Barke: execution is a main validation strategy; Anthropic: "test suites passing" is a hard success signal | Running tests in a loop. Only transitions count |
| S9 | **Human debugging** | An error appears, then the human reasons about it (hypothesis in the prompt, a hand edit, a doc lookup) before the fix | Transcript + S7 + S2 | Skill study: high scorers "encountered many errors, they also independently resolved them"; low scorers did "iterative AI debugging" | Hard to fake at scale |
| S10 | **Progress** | Something changed for the better: tests newly passing, a commit whose diff matches the session's files, an error that stops recurring, a feature the human confirms | git, test output, transcript | Anthropic "verified success"; Bjork's caveat that difficulty without progress isn't desirable | Commits of junk. Reviewers see the diff |
| S11 | **Ownership probe** | At submission, the student explains a change or answers a question about their own code; optional | Submission flow | MIT ownership finding; epistemic-debt teach-back (77% vs 39% maintenance failure) | Asking an LLM to explain. Live or timed probes resist this |

### 3.3 Anti-patterns and detectors

| Anti-pattern | What it looks like in logs | Detector | Evidence |
|---|---|---|---|
| **Walked away** | Agent turns continue (or one long turn runs) with no presence | S1 coverage during and after the turn; credit at most the first minute of an unsupervised run (grit) | Zach: Hackatime "just counts how active your AI agent is" |
| **Autopilot** | Agent-initiated turns, `/loop`, scheduled prompts, `/goal`-style self-continuation; bare "continue" prompts | Prompts without S3 evidence; share of go-aheads over a session (grit `autopilot`: at least 4 prompts, half low-effort); harness markers for agent-started turns where they exist | Karim: users can tell an agent to /goal or check something every 20 minutes |
| **Re-rolling** | Same or near-same prompt again after an unsatisfying result, with no human change in between | Normalized edit distance or local embedding similarity between consecutive prompts, with no S7 edit and no S5 reading between them | Dark flow (slot-machine re-spins); "excessively prompting the thing" |
| **Repetition** | One template sent many times, maybe with numbers changed | grit `repeated-prompts` (3 or more) | Zach: "doing the same thing over and over again" |
| **Regular timing** | Prompts at near-constant intervals | Coefficient of variation of inter-prompt spacing under 0.1 across 6+ prompts (grit `regular-timing`) | Scripts are periodic; humans aren't |
| **Loss disguised as a win** | Lots of files and lines touched, no S10 progress; churn (code added then reverted) | Lines changed per S10 event; git-ai notes show AI lines later overwritten or deleted | Dixon et al. LDWs; Thomas on "tools I did not end up using" |
| **Menu-following** | Human prompts only accept options the agent offered ("yes, option 2") | Short prompts that reference the agent's last message's enumerated options, repeated | Thomas: LLM choices lead "down paths they wouldn't otherwise take" |
| **Fix-it loop** | Error pasted back, "fix it", repeat, with no human reasoning | Error-bearing prompts with low added text and no S7 or S9 in between | Skill study: "iterative AI debugging" scored 24% |
| **One-shot** | A large output from very few human turns | Credit is human minutes, so a one-shot earns its few minutes and no more; flag for reviewers when lines shipped per credited minute is extreme | Zach's vision post: "one-shotting takes 2 minutes of productive struggle" |
| **Parallel farming** | Several agent sessions at once, possibly in several projects | Deduplicate human minutes across sessions; a minute goes to the project the human was focused on (S2 + last human input) | METR: concurrent agents made time-per-task "unreliable" |
| **LLM-driven agent** | Prompts written by another model, believable transcripts | No S3 evidence; implausible typing (characters per active second); pasted prompts; server witnessing of turn hashes at the time they happen (grit's chain) so transcripts can't be written after the fact | BOUNTY.md thread: "an LLM can drive the agent and produce believable transcripts" |

### 3.4 What passive logs cannot see

- **Thinking away from the keyboard** (whiteboard, a walk, reading on a phone). Real struggle, invisible to S1. The conservative answer, matching Hackatime's 2-minute cap and Lookout's 10-minute auto-pause, is to credit gaps only up to a cap (grit uses 10 minutes between an agent stop and the next human prompt) and let reviewers add time by hand with a reason. Over-crediting idle gaps is exactly what Stardance reviewers had to deflate (BOUNTY.md R9).
- **Reading the agent's output closely vs glancing.** S5 measures time available to read, not reading. Eye tracking would be invasive and isn't worth it. Combine with S6 and S7: someone who reads closely usually corrects, rejects or edits sometimes.
- **Learning that happens in chat outside the harness** (ChatGPT in a browser). Browser extensions or the AGENTS.md `track` route (BOUNTY.md, Karim) can capture prompt events, but credit should require S1 presence and S2 focus like any other source.
- **Whether a prompt is "struggle" in Hiebert and Grouws's sense** (effort toward something not yet understood). Only content shows it. That is the case for a local classifier (S4) whose output is a label, plus reviewer access to the prompt text for submitted hours only (R6, R10).

### 3.5 Calibrating, not hand-tuning

Every number above (10-minute gap cap, 90-second go-ahead cap, 8-minute supervised-run cap) is a guess until it is fitted to reviewer judgments. The R2 checklist item in BOUNTY.md already defines the test: "On a labeled set of real sessions, our hours match what human reviewers would approve." The cheapest labeled set is Hack Club's own review history: Stardance reviewers approved 27,600 of 123,400 submitted hours (R9), so per-project approved vs submitted hours exist for thousands of projects. If pairtime can replay the matching Hackatime heartbeats (and, for new users, transcripts), the credit rule can be fitted to approved hours rather than tuned by hand. That is a concrete accuracy advantage over grit's fixed constants.

## 4. Motivation for teens

R3 asks for a tool teens want to install "to self-improve, regardless of any You Ship, We Ship incentives." That's a product problem, not a measurement problem, but the two interact: whatever pairtime rewards, users will optimize.

### 4.1 What the reference products do

| Product | Mechanics | Evidence | Lesson |
|---|---|---|---|
| **Hackatime** (source, commit `43bde10`) | Streak = consecutive local days with at least `STREAK_DAY_SECONDS = 15.minutes` of activity (`heartbeatable.rb`); goals per day/week/month with presets 30 min, 1 h, 2 h, 4 h, max 5 (`app/models/goal.rb`); weekly summary email (`weekly_summary_user_email_job.rb`, opt-in via `subscribed?("weekly_summary")`); leaderboards with an admin shadowban tool (`leaderboard_shadowbans_controller.rb`); "currently hacking" presence; README badges; AI vs Human meter | Zach (R3): "it helps me track and feel motivated to work on personal projects I never submit" | Zero-effort tracking plus a small daily threshold works. Shadowbans show leaderboards attract gaming |
| **WakaTime** | Dashboards, goals, leaderboards, weekly reports, a yearly "wrapped" | Earlier agent's search hit "[Get ready for your yearly wrapped code stats](https://wakatime.com/blog/69-get-ready-for-your-yearly-wrapped-code-stats)" (not re-read) | A retrospective story of the year is shareable |
| **Strava** | Kudos, segments, yearly recap, privacy controls. **Local Legend** goes to "the athlete who completes a given segment the most over a rolling 90-day period", "regardless of pace or speed"; "Only activities visible to 'Everyone' will count" ([Strava Help](https://support.strava.com/en-us/articles/15401751-what-is-the-local-legend-achievement-on-strava)) | Local Legend exists beside KOM (fastest) to reward consistency | A consistency award over a rolling window is motivating to more people than a top-hours award, and is much less farmable |

Weekend activity decreased and days in which developers made a single contribution became less common." Some developers pursuing 100-day streaks abandoned them. Forgiveness (freezes) keeps streaks from becoming anxiety |

### 4.2 Theory: why "hours for prizes" is the dangerous part

- Deci, Koestner and Ryan's meta-analysis of 128 experiments ([*Psychological Bulletin* 1999, doi:10.1037/0033-2909.125.6.627](https://doi.org/10.1037/0033-2909.125.6.627)): "engagement-contingent, completion-contingent, and performance-contingent rewards significantly undermined free-choice intrinsic motivation (d = -0.40, -0.36, and -0.28, respectively)", "Positive feedback enhanced both free-choice behavior (d = 0.33) and self-reported interest (d = 0.31)", and "Tangible rewards tended to be more detrimental for children than college students."
- YSWS prizes paid per approved hour are an engagement-contingent tangible reward, the most undermining category, given to teenagers. pairtime can't remove the prizes, but it can make sure what the user sees day to day is *informational positive feedback* (what you did, what you got better at), not a running prize meter. That is the R3 requirement in research terms: the tool has to be worth using with the prize stripped away.
- Self-determination theory's three needs (competence, autonomy, relatedness; Deci and Ryan, general knowledge) map onto features: competence = skill recaps and progress; autonomy = the user controls what's shared and submitted; relatedness = public profiles, kudos, and a club context.

### 4.3 Making struggle time feel good

1. **Session recap, generated locally.** After a session: what you built, bugs you fixed yourself, questions you asked, agent edits you rejected or rewrote, tests you got passing. These are S4-S10 from section 3, shown as positive feedback rather than a score. The recap also teaches the behavior the research rewards (conceptual questions, verification, fixing by hand) without saying "you were lazy". Generated on the machine from local transcripts (R6); only the student decides whether it's posted.
2. **Skill growth.** Track concepts and error types the student has worked through (a first async bug, a first failing test made to pass). The skill study's high scorers asked conceptual questions and resolved their own errors; making those visible as growth gives a reason to keep doing it.
3. **Streaks that resist gaming.** A streak day should need credited *human* minutes (Hackatime's 15 minutes is a good start, but of credited time, not heartbeats). Allow freezes (Duolingo). Prefer rolling-window consistency awards ("built on 18 of the last 30 days", Local Legend style) over unbroken streaks and over hour totals, because GitHub's natural experiment shows bare streak counters produce token activity.
4. **Devlogs and project stories.** Draft a devlog entry from the week's recaps (local, editable, never auto-posted). Hack Club programs already ask for devlogs, so this saves the student work, and a devlog written from real session evidence doubles as audit material for reviewers (R10).
5. **Chess clock framing.** mod-crono's "your clock vs Claude's clock" (1.13) is an intuitive way to show human vs agent time without moralizing. Show it as information, not a target ratio.
6. **Public by default, generous privacy controls.** R5 requires public-by-default profiles. Strava shows the pattern: public activities feed the social features, and private ones still count for the owner. Profiles should show credited hours, projects and streaks, never prompts, file names or code.

### 4.4 Pitfalls

- **Feeling surveilled.** CDT's 2021 survey ([CDT, 2021-09-21](https://cdt.org/insights/cdt-original-research-examines-privacy-implications-of-school-issued-devices-and-student-activity-monitoring-software/)): 58% of students at schools using monitoring software agreed "I do not share my true thoughts or ideas because I know what I do online is being monitored." A tracker that feels like school monitoring will be uninstalled, or will make students hide the exploratory, messy prompts that are the struggle. Countermeasures: nothing leaves the machine except numbers until the user submits; `submit --dry-run` shows the exact bundle (as grit does); no screenshots or keystroke content by default; open source (R1) so the claims are checkable; easy local deletion.
- **Goodhart's law.** "When a measure becomes a target, it ceases to be a good measure" is Strathern's phrasing ([*European Review* 5(3):305-321, 1997](https://doi.org/10.1002/(sici)1234-981x(199707)5:3%3C305::aid-euro184%3E3.0.co;2-4)) of Goodhart's point. DX warns code-volume metrics are "particularly susceptible to gaming". Every signal in section 3 will be gamed once it earns prizes. Mitigations: (a) credit only what's costly to fake (presence plus progress), with caps; (b) keep anomaly flags separate from credit (grit's rule) so users can't tune against them without a reviewer seeing it; (c) put leaderboards on consistency, not hours; (d) publish the rules (R10 needs that) but calibrate them against reviewer outcomes so gaming one signal doesn't move the total much.
- **Tension between transparency and gaming.** Reviewers and students need to see *why* a minute counted (R10, R3), but a fully public rule is easier to game. Fraud Squad keeps its patterns secret ("We don't share the specific patterns we look for", [fraud.hackclub.com](https://fraud.hackclub.com/), from the sibling notes). A workable split: credit rules public and deterministic; fraud flags and their thresholds private to reviewers.
- **Shame.** A tracker that tells a student "only 35% of your session counted" reads as an accusation. Name the credited time positively ("steering time", "your time") and show the uncredited remainder as the agent's time, which it is.
- **Discouraging the right kind of AI use.** The Anthropic expertise study found experts make the agent do *more* per prompt. If pairtime's UI implies "less AI is better", it pushes teens away from learning to steer agents well, which is a skill Hack Club presumably wants them to build (Zach's vision post). The message should be "use AI, and stay in the loop", not "use less AI".
