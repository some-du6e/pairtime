## Summary

- **Runtime:** a single pure-Go binary (`CGO_ENABLED=0`) for the agent, the hook receiver and the CLI. Go, Rust and NativeAOT all start at 3 to 5 MB RSS; Node, Bun and Deno ship 80 to 115 MB runtimes and have no 32-bit Windows build; Python's interpreter startup and ActivityWatch's 268 MB, 1,543-file Windows bundle show the cost of that route (1). Go wins on cross-compiling everything from one Linux job and on cgo-free access to every OS API needed. Go 1.27+ drops macOS 12 (1.5).
- **Background:** the agent must run in the user's session, because idle time and focus are per-session (`GetLastInputInfo` is session-specific). Use the HKCU Run key, a LaunchAgent, or XDG autostart, none of which needs admin. Avoid Task Scheduler, whose defaults refuse to start on battery (2).
- **Watching:** sample idle time every 15 s, get focus changes from events, and tail only the harness log directories plus each repo's `.git`. Never watch working trees recursively on Linux, where inotify watches are per directory and the per-user limit is shared with VS Code. Avoid WMI and AppleScript, which cost ActivityWatch 5 to 30% CPU (3).
- **Hooks:** a native exec-form binary that talks to the agent over a Unix domain socket (supported on Windows 10 too) and falls back to an append-only spool; HTTP hooks to `127.0.0.1` with a bearer token where harnesses support them. Windows process creation alone is 10 to 30 ms, so interpreters and `npx` in hooks are out (6).
- **Distribution:** `curl | sh` and `irm | iex` scripts, winget, Scoop, a Homebrew tap, npm with per-platform packages, and the editor extension bundling the binary, as Claude Code does. Sign on Windows (Artifact Signing at about $9.99/month for a US organization, or SignPath, free for OSS projects that already have a release and some reputation), because unsigned files start from zero SmartScreen reputation on every release and Smart App Control blocks them. Notarize on macOS from Linux with quill (4).
- **Storage and UI:** a JSONL spool plus SQLite in WAL mode with `synchronous=NORMAL` and batched commits, and per-field encryption for any raw text kept locally. The dashboard is served by the agent and opened in the user's own browser; no webview stays resident, since any webview window costs about 100 MB (5).

## 1. Language and runtime

What the target machine imposes: about 4 GB of RAM, much of it already taken by Windows 10, a browser, an editor and an agent; a spinning disk, so every page fault and file open is slow; two cores, often a low-power Celeron or Pentium; and a battery. The background agent has to idle at roughly 0% CPU with a small resident set, and the hook binary that harnesses run on every prompt has to start in milliseconds. One codebase also has to ship to Windows (x64, possibly x86 and arm64), macOS (Intel and Apple Silicon) and Linux.

### 1.3 Idle CPU and wakeups

Idle CPU on a laptop is mostly a question of how often the process wakes, since each wakeup keeps the CPU out of deep C-states.

- **Go.** The runtime's monitor thread (`sysmon`, `src/runtime/proc.go` on master, Go 1.27.4 current) backs off from 20 µs to 10 ms sleeps, and once every P is idle it sleeps until the next timer or for `forcegcperiod / 2` (60 s, `forcegcperiod = 2 * 60 * 1e9`), whichever is sooner. An idle Go daemon whose own work is a 15 s ticker therefore wakes about once per 15 s, plus at least once every 60 s for the forced-GC check. On Windows, Go used to call `timeBeginPeriod(1)`, which raised the system timer rate to 1 kHz while the process ran and cost battery ([golang/go#8687](https://github.com/golang/go/issues/8687)). Current runtimes use `CreateWaitableTimerExW(..., CREATE_WAITABLE_TIMER_HIGH_RESOLUTION, ...)` when available, and `osRelax` is then a no-op ("there's no need to adjust the global clock frequency"); winmm's `timeBeginPeriod` is loaded only as a fallback on Windows versions without high-resolution timers (`src/runtime/os_windows.go`, master). Microsoft documents `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` as "supported in Windows 10, version 1803, and later" ([CreateWaitableTimerExW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createwaitabletimerexw)). On Windows 10 builds older than 1803 the fallback applies: Go calls `timeBeginPeriod(1)` at startup and drops back with `timeEndPeriod` only while every P is idle and sysmon's sleep is at least `osRelaxMinNS`, so a busy Go process on an unpatched 2016 install still raises the system timer rate (added in fact-check; same file, `osinit` and `sysmon`).
- **Rust.** No runtime threads beyond what the program creates. A tokio runtime with no pending timers parks its workers indefinitely.
- **NativeAOT.** Ships the .NET GC and a finalizer thread; the GC does not run periodically when nothing allocates (unverified).
- **Node, Bun, Python.** One event loop each, with few wakeups of their own when idle (unverified per runtime), but 15 to 40 MB more resident memory than the native options (1.2). ActivityWatch multiplies that by running one Python process per watcher.

The bigger idle cost is the program's own polling, not the runtime. ActivityWatch's window watcher polls once per second by default (`poll_time = 1.0` in `aw_watcher_window/config.py`, master `76b3f6f580`, 2026-11-10). How it fetched the foreground app mattered more than the language. Its Windows watcher once used WMI for the process name, which kept WMI Provider Host at 5 to 10% CPU ([activitywatch#654](https://github.com/ActivityWatch/activitywatch/issues/654), 2021) and up to 30% on one Windows 11 machine ([#829](https://github.com/ActivityWatch/activitywatch/issues/829), 2022), until [aw-watcher-window#83](https://github.com/ActivityWatch/aw-watcher-window/pull/83) moved it to `GetWindowThreadProcessId` plus `OpenProcess` and `GetModuleFileNameEx` (the current `windows.py`). Its macOS AppleScript path kept the System Events process at about 15% CPU on a 2015 MacBook Pro, rising with the number of open windows ([#472](https://github.com/ActivityWatch/activitywatch/issues/472), 2020); the default is now a Swift helper (`strategy_macos = "swift"`).

Notes on rows that decide the choice:

- **Footprint rules out the JS runtimes and Python for the resident agent.** A 100 MB executable and a 40 MB baseline RSS per process is 10 times the native options, on a machine where 4 GB is shared with a browser and an agent. Bun and Deno also have no 32-bit Windows build, and Node 26 has none either.
- **Hook cold start rules them out for the hook path.** A Node process costs about 42 ms before it does anything on a fast Linux box; Windows adds its own process-creation cost, and probably a Defender scan of the 100 MB image on first run (unverified) (6.1).
- **Go, Rust and NativeAOT all meet the footprint bar.** The tiebreakers are cross-compilation, OS API access, and the people who will maintain it. NativeAOT can't cross-compile between operating systems, so it needs three native build jobs and a Windows-hosted toolchain with the Visual Studio C++ workload. Zig is attractive for size, but it is still pre-1.0, where breaking changes between 0.x releases are expected, and it lacks mature libraries for SQLite, tray icons and macOS frameworks.

### 1.5 Cross-compilation and CI cost

GitHub Actions is "free for standard GitHub-hosted runners in public repositories" ([billing docs](https://docs.github.com/en/actions/concepts/billing-and-usage), read 2026-11-19), so pairtime pays nothing for CI on any OS. The standard runners available to public repos ([runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), read 2026-11-19):

| OS and architecture | Labels | CPU / RAM |
|---|---|---|
| Linux x64 | `ubuntu-latest` (24.04), `ubuntu-24.04`, `ubuntu-22.04`, `ubuntu-26.04`; `ubuntu-slim` (1 CPU / 5 GB container, 15-minute job limit) | 4 / 16 GB |
| Linux arm64 | `ubuntu-24.04-arm`, `ubuntu-22.04-arm`, `ubuntu-26.04-arm` | 4 / 16 GB |
| Windows x64 | `windows-latest` (Server 2025 with VS 2026), `windows-2025`, `windows-2025-vs2026`, `windows-2022` | 4 / 16 GB |
| Windows arm64 | `windows-11-arm`, `windows-11-vs2026-arm` | 4 / 16 GB |
| macOS Intel | `macos-15-intel`, `macos-26-intel` | 4 / 14 GB |
| macOS arm64 (M1) | `macos-latest` (26), `macos-15`, `macos-26`, `xcode-27` | 3 / 7 GB |

The Intel macOS runners are ending. GitHub introduced `macos-15-intel` on 2025-09-19 as "the last available x86_64 image from Actions", available "until August 2027", after which "the x86_64 architecture will not be supported on GitHub Actions" ([runner-images#13045](https://github.com/actions/runner-images/issues/13045)). A `macos-26-intel` label has appeared since (runner page above), but the end date stands. After August 2027, Intel Mac builds must be cross-compiled from Apple Silicon, which Go and Rust both do natively (`GOARCH=amd64`; `--target x86_64-apple-darwin`), and tested on real hardware or not at all.

What each language costs in CI:

- **Go, pure.** One `ubuntu-latest` job builds every target (`GOOS`/`GOARCH` matrix) in well under a minute for a project of this size. Test jobs still need each OS to exercise platform code. GoReleaser (section 4) does builds, archives, checksums, signing and package manifests from one config.
- **Go with cgo** (for example `mattn/go-sqlite3` or a cgo tray library on macOS). Needs a C cross-toolchain per target, or a native runner per OS. This is the main reason to stay cgo-free.
- **Rust.** Native runners per OS are the practical route (macOS can't be linked from Linux without the Apple SDK). Release builds take minutes rather than seconds; free on public repos either way.
- **NativeAOT.** Three native runners, by design.

**Old Macs and the Go toolchain.** Macs that top out at macOS 12 Monterey (roughly models from 2015 to 2016; Ventura needs 2017 or later, unverified) can't run binaries from Go 1.27 or later. Go 1.26 still supports them and gets security fixes until February 2027 ([golang/go#75836](https://github.com/golang/go/issues/75836), which also says about 0.8% of opt-in `cmd/go` telemetry reports came from macOS 12 as of 2025-10-09). If those Macs matter, ship the macOS build from Go 1.26 until then, or accept dropping them. Rust targets macOS 10.12 and later.

### 1.6 Verdict

**Go, pure (`CGO_ENABLED=0`), for both the agent and the hook binary.** Reasons, in order of weight:

1. It meets the footprint bar (3.6 MB baseline RSS, about 2 MB hello-world binary, sysmon sleeping up to 60 s when idle, no timer-resolution change on current Windows) with a much simpler toolchain story than Rust: every target, including darwin/arm64 with ad-hoc signing (4.4), builds from one Linux job in seconds.
2. Every OS API pairtime needs is reachable without cgo: Win32 through `golang.org/x/sys/windows`; Apple frameworks through `purego` (grit already does this for idle time); D-Bus through `godbus/dbus`; SQLite through `modernc.org/sqlite` or `ncruces/go-sqlite3` (5.1); keychains through `go-keyring` (5.2).
3. The two closest pieces of prior art are Go: wakatime-cli (whose BSD-3 parsers pairtime may reuse, per ai-harness-signals.md) and grit (the competing bounty entry). Contributors from Hack Club and the Hackatime ecosystem can read it.
4. It runs on 32-bit Windows 10 if that matters (`windows/386`), which the JavaScript runtimes don't.

Costs to accept: fsnotify has no FSEvents backend and no recursive watching (fine for the narrow watch set in 3.2); a macOS tray icon needs cgo (5.3), so it goes in a separate helper or waits; Go 1.27+ drops macOS 12 (1.5); and Go binaries draw more antivirus false positives on Windows (Go FAQ), which signing (4.3) and staying away from keyboard hooks (3.3) mitigate.

Rust is the strong alternative if the team prefers it: smaller binaries, a better file watcher (`notify` with FSEvents), macOS 10.12+ support. It costs native CI runners per OS and slower builds. NativeAOT, Zig, Node/Bun/Deno and Python don't fit, for the reasons in 1.4.

## 2. Running in the background on each OS

The agent has to run in the user's own interactive session, because the signals it needs belong to that session. On Windows, `GetLastInputInfo` "provides session-specific user input information for only the session that invoked the function" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getlastinputinfo), Remarks), and a service runs in session 0. On macOS, idle time and frontmost-app notifications need the user's GUI (Aqua) session. On Linux, X11 and Wayland idle protocols need `DISPLAY` or `WAYLAND_DISPLAY`. That rules out system services and daemons on all three OSes, and all the per-user mechanisms below need no admin rights.

| Linux | systemd user unit in `~/.config/systemd/user/pairtime.service`, `systemctl --user enable --now` | no | `WantedBy=default.target` starts it with the user manager (first login); X11/Wayland-only services should use `PartOf=graphical-session.target` so they stop with the session ([systemd.special(7)](https://www.freedesktop.org/software/systemd/man/latest/systemd.special.html), systemd 262) | yes / yes | `Restart=on-failure` | `systemctl --user status`; invisible to non-technical users | The service doesn't inherit `DISPLAY`/`WAYLAND_DISPLAY` unless the desktop imports them into the user manager (GNOME and KDE do; minimal window managers may not) (unverified per desktop). | Linux | XDG autostart `~/.config/autostart/pairtime.desktop` | no | "automatically launched during startup of the user's desktop environment after the user has logged in" ([autostart spec](http://specifications.freedesktop.org/autostart/latest/) 0.5) | yes / yes | no | Desktop "Startup Applications" settings; `Hidden=true` disables | Works on non-systemd distributions and inherits the session environment. Recommendation for pairtime: the HKCU Run key on Windows (one registry write, no COM, no admin, shows up where users expect startup apps), a LaunchAgent plist on macOS, and on Linux an XDG autostart entry by default, with a systemd user unit as an opt-in for people who want restart-on-crash. Each is written by `pairtime install` and removed by `pairtime uninstall`. The agent also needs a single-instance lock (a named mutex on Windows, an `flock` on the socket's lock file elsewhere), because Run-key starts, a user double-clicking the binary, and a hook starting the agent on demand will all race.

### 2.2 Sleep, standby and battery

| Situation | What happens to the agent | What pairtime must do |
|---|---|---|
| Windows S3 sleep or hibernate (typical of 2016 laptops; unverified) | All processes freeze; on resume, timers that were due fire at once | Treat any gap between consecutive samples longer than twice the sample interval as "machine asleep", never as idle-but-present. Use wall-clock timestamps for records, and detect suspend explicitly (below) |
| Windows Modern Standby (connected standby, newer laptops) | The Desktop Activity Moderator puts processes "created in an interactive session" in a job object "subject to suspension": "all their threads suspended ... app state (process memory) is maintained". It's like S3 to the app, with "inconsistencies in uptime / runtime vs. wall clock time" ([DAM, Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/w8cookbook/desktop-activity-moderator)). The page is a Windows 8 cookbook entry: "The DAM is present only on Windows 8 client machines that support connected standby", and the suspend `WM_POWERBROADCAST` goes only to processes that opted in; that it behaves the same under Windows 10/11 Modern Standby is (unverified) | Register with `PowerRegisterSuspendResumeNotification(DEVICE_NOTIFY_CALLBACK, ...)` (no window needed) or `RegisterSuspendResumeNotification` with an HWND, and handle `WM_POWERBROADCAST` `PBT_APMSUSPEND` / `PBT_APMRESUME` (same page). Flush the event store on suspend |
| Windows on battery | The Run-key agent keeps running. Windows schedules windowless background processes by heuristics; a process can opt into EcoQoS with `SetProcessInformation(ProcessPowerThrottling)` and `PROCESS_POWER_THROTTLING_EXECUTION_SPEED`, which "always selects most efficient CPU frequency and schedules to efficient cores" (Eco level: Windows 11; Low/Utility levels from 1709 and 22H2) ([Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service), 2025-07-14) | Opt into EcoQoS at startup. It costs nothing on a 2-core laptop with no efficiency cores and helps on newer ones. Avoid Task Scheduler, whose defaults stop tasks on battery (2.1) |
| macOS sleep | Processes freeze. A process without AppKit gets sleep and wake through IOKit: `IORegisterForSystemPower`, messages `kIOMessageSystemWillSleep` (must acknowledge with `IOAllowPowerChange`, or "sleep will be delayed by 30 seconds") and `kIOMessageSystemHasPoweredOn`. AppKit apps can observe `NSWorkspaceWillSleepNotification` / `NSWorkspaceDidWakeNotification` on NSWorkspace's own notification center ([QA1340](https://developer.apple.com/library/archive/qa/qa1340/_index.html), 2014) | Use the IOKit route from the agent, acknowledge promptly, flush on will-sleep. QA1340's sample delivers these messages through a CFRunLoop source (`IONotificationPortGetRunLoopSource`), so a Go agent needs one OS-locked thread running a CFRunLoop through `purego`, the same thread that can carry `NSWorkspace` notifications (added in fact-check) |
| macOS on battery, App Nap | App Nap targets hidden apps with UI (unverified for launchd agents); a launchd agent's throttling comes from `ProcessType` (2.1) | Leave `ProcessType` unset or `Background`; pairtime's work is tiny |
| Linux sleep | systemd-logind sends `PrepareForSleep(b start)` on `org.freedesktop.login1.Manager` "right before (with the argument 'true') or after (with the argument 'false')" suspend or hibernate. A client takes a lock with `Inhibit(in s what, in s who, in s why, in s mode, out h pipe_fd)` using `mode = "delay"`, flushes, then closes the fd; the delay is capped by `InhibitDelayMaxUSec` (from logind.conf; default not stated on that page) ([org.freedesktop.login1](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.login1.html), systemd 262) | Subscribe over D-Bus where logind exists; otherwise rely on the sample-gap rule |
| Clock behavior across sleep | Monotonic clocks differ by OS, and Go's `time.Since` inherits the difference (added in fact-check). Linux: Go's `nanotime` uses `CLOCK_MONOTONIC` (`sys_linux_amd64.s`), which "does not count time that the system is suspended"; `CLOCK_BOOTTIME` does ([clock_gettime(2)](https://man7.org/linux/man-pages/man2/clock_gettime.2.html)). macOS: Go uses `mach_absolute_time` (`sys_darwin.go`), and Apple says "this clock does not increment while the system is asleep". Windows: Go master uses `QueryInterruptTimePrecise` (`os_windows.go`, `sys_windows_amd64.s`), the biased interrupt time; Microsoft says the unbiased count "does not include time the system spends in sleep or hibernation" and that biased time is used so timers due during sleep fire on wake ([QueryUnbiasedInterruptTime](https://learn.microsoft.com/en-us/windows/win32/api/realtimeapiset/nf-realtimeapiset-queryunbiasedinterrupttime)), so on Windows the Go monotonic clock keeps counting through sleep (by implication; not tested) | Never compute an "active duration" as a monotonic difference across a possible suspend: the same Go code gives a gap that includes the sleep on Windows and excludes it on Linux and macOS. Store wall-clock UTC per sample, and split intervals at suspend and resume events |

The sample-gap rule is the safety net on every OS: if the agent samples idle state every 15 s and two samples are 10 minutes apart, the machine was asleep or the agent was frozen, and that span counts as nothing.

A Go trap for this rule (added in fact-check): when two `time.Time` values both carry monotonic readings, "t.Sub(u) [is] carried out using the monotonic clock readings alone", and "On some systems the monotonic clock will stop if the computer goes to sleep" (`src/time/time.go`, master). On Linux and macOS, `time.Since(lastSample)` therefore misses a suspend entirely. Compute the gap from wall-clock values (strip the monotonic reading with `t.Round(0)`, or compare `UnixNano()`), and keep the monotonic difference only as a second signal: wall gap minus monotonic gap approximates time asleep on Linux and macOS, and is about zero on Windows.

## 3. Watching for activity cheaply

The agent's inputs, in rough order of cost: idle-time samples (a syscall), foreground-app changes (an event or a cheap query), harness hook events (pushed to us, section 6), harness transcript and log files (file notifications plus reads), and the user's repos (the expensive one). The API names per OS are in ai-harness-signals.md 13.4; this section is about what each costs and how to keep it near zero.

### 3.1 File-change notification APIs

| | Windows `ReadDirectoryChangesW` | macOS FSEvents | macOS kqueue | Linux inotify |
|---|---|---|---|---|
| Recursive | yes, one handle per tree (`bWatchSubtree = TRUE`) | yes, a stream covers "a large tree of files" | no, one fd per watched file or directory | no: "to monitor subdirectories under a directory, additional watches must be created" ([inotify(7)](https://man7.org/linux/man-pages/man7/inotify.7.html), man-pages 6.19) |
| Granularity | per file, with action codes | per directory by default ("tells you *only* that something in the directory has changed"); per file with `kFSEventStreamCreateFlagFileEvents` (10.7+) ([FSEvents guide](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/TechnologyOverview/TechnologyOverview.html), 2012) | per fd | per file, with event masks |
| Overflow | the kernel buffer is fixed when first allocated; on overflow the call "will still return true, but the entire contents of the buffer are discarded" and `lpBytesReturned` is 0, or it fails with `ERROR_NOTIFY_ENUM_DIR`; either way "compute the changes by enumerating the directory or subtree" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)) | coalesced; history is kept in a per-volume database | n/a | "Events in excess of this limit are dropped, but an IN_Q_OVERFLOW event is always generated" (`max_queued_events`) |

The limit is per real user ID, so it is shared with VS Code's own watcher. The same file sets `max_queued_events` to 16384 and `max_user_instances` to 128 per user, and every fsnotify `Watcher` is one instance (added in fact-check) |
| Replay after downtime | no (use the NTFS change journal, which needs admin, or rescan) | yes: the database records changes "even while your application was not running" | no | no |
| Gotchas | `FILE_NOTIFY_CHANGE_SIZE` and `_LAST_WRITE`: "detects a change ... only when the file is written to the disk. Library support, checked 2026-11-19:

- **Go, [fsnotify](https://github.com/fsnotify/fsnotify) v1.10.1 (2026-05-04, BSD-3-Clause).** Backends: inotify, kqueue (BSD and macOS), `ReadDirectoryChangesW`, FEN. FSEvents is listed as "Needs support in x/sys/unix". "Are subdirectories watched? No" (recursive watching is still issue #18). On macOS, "kqueue requires opening a file descriptor for every file that's being watched". No polling fallback for network filesystems (issue #9). Fine for pairtime's narrow watch set (3.2), wrong for watching a whole repo on macOS.
- **Rust, [notify](https://github.com/notify-rs/notify) 9.0.0-rc.9 (2026-11-15); latest stable 8.2.2 (2026-11-08, crates.io); the `notify` crate is CC0-1.0, its debouncers MIT or Apache-2.0.** inotify on Linux, FSEvents by default on macOS (kqueue optional), `ReadDirectoryChangesW` on Windows, and a polling backend everywhere. Comes with debouncers.

### 3.2 What pairtime should watch

**Harness transcript and log directories, not repos.** These trees are small: one directory per project for Claude Code, date-nested folders for Codex, one folder per session for Copilot CLI (paths in ai-harness-signals.md). The tailer should:

1. Watch each harness root non-recursively plus only the subdirectories that are active (today's Codex date folder; Copilot session folders touched in the last day). That keeps the inotify count in the tens and the macOS kqueue fd count in the tens.
2. Keep a cursor per file: (volume and file ID or inode, size, byte offset, hash of the last complete line). On a change event, `stat` the file, read from the offset to EOF, and buffer any partial last line until the next newline. If the file shrank or its ID changed, it was truncated or replaced, so restart from 0 and dedupe by line hash.
3. Back up the notifications with a slow poll of only the files that are "hot" (written in the last 10 minutes): one `stat` every 5 to 10 s while a session is active, backing off to 60 s, then stopping. This covers Windows' delayed size notifications, network homes, WSL paths (`\\wsl.localhost\...`, where change notification is unreliable; unverified), and editors or harnesses that write through `mmap`.
4. On startup, do one catch-up scan (lookback) from the saved cursors, which is how wakatime-cli reads transcripts too (hackatime-and-hack-club.md 2.2). On macOS, FSEvents can replay changes since the last event ID; elsewhere a scan of the few harness roots by modification time is cheap.
5. For SQLite-backed harness state (Cursor's `state.vscdb`, which can be gigabytes per ai-harness-signals.md), watch the `-wal` file, open the database read-only, and query incrementally by rowid, rate-limited to once per 30 to 60 s. On a spinning disk this is the most expensive read in the whole client.

**Repos: watch `.git`, not the working tree.** A non-recursive watch on `<repo>/.git` sees `HEAD`, `index` and `ORIG_HEAD` change, plus `.git/logs/HEAD` appends, which covers commits, checkouts, resets, rebases and staging for every repo pairtime knows about (worktrees and submodules point `.git` to elsewhere, so resolve with `git rev-parse --git-dir` once). Working-tree edits come from the editor extension and from harness hooks (`PostToolUse` paths), which already say who made the edit. A recursive working-tree watch costs the most on exactly the hardware we care about: a JavaScript project's `node_modules` can hold tens of thousands of directories, each an inotify watch pinning an inode on Linux, and every `npm install` floods the queue. If pairtime ever needs it (say, to see hand edits made in an editor without an extension), use it only on Windows and macOS, where one handle covers the tree, and never on Linux by default.

### 3.3 Idle, input and focus: cost per sample

| Signal | Call | Cost | Sample rate |
|---|---|---|---|
| Idle time, Windows | `GetLastInputInfo` + `GetTickCount` | one user32 call; no permission. The tick "is not guaranteed to be incremental" (it can go backwards, for example after `SendInput`), so clamp negative idle to 0 | every 5 to 15 s. ActivityWatch's AFK watcher polls every 5 s with a 180 s timeout (`aw_watcher_afk/config.py`: `timeout = 180`, `poll_time = 5`); grit samples every 15 s |
| Idle time, macOS | `CGEventSourceSecondsSinceLastEventType(kCGEventSourceStateHIDSystemState, kCGAnyInputEventType)` | one CoreGraphics call; no permission | same |
| Idle time, Linux | X11 `XScreenSaverQueryInfo`; GNOME `org.gnome.Mutter.IdleMonitor` (event-driven watches); `ext-idle-notify-v1` on wlroots, KDE and others | a D-Bus or X round trip | same, or event-driven where the watch API exists |
| Foreground app, Windows | `SetWinEventHook(EVENT_SYSTEM_FOREGROUND, ..., WINEVENT_OUTOFCONTEXT)` on a thread with a message loop, then `GetWindowThreadProcessId` → `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` → `QueryFullProcessImageNameW` | event-driven: zero cost between focus changes. | Foreground app, Linux | X11: `PropertyNotify` on the root window's `_NET_ACTIVE_WINDOW`; Wayland: no standard protocol | event-driven on X11; on GNOME Wayland it needs a Shell extension | on event |
| Keystroke and click counts | Windows Raw Input (`RIDEV_INPUTSINK`) or low-level hooks; macOS `CGEventTap` (Input Monitoring permission) | hooks add latency to every keystroke system-wide if the hook thread stalls; low-level hooks are "silently removed" after a timeout on Windows 7+ (ai-harness-signals.md 13.4). A program that installs a global keyboard hook and uploads data looks like a keylogger to antivirus heuristics and to privacy-minded users | leave out of v1; idle time plus harness and editor events carry the presence signal. If added later, count keys without recording them, opt-in only |

On a 2-core laptop, the whole sampling loop (idle sample every 15 s, foreground on event, hot-file `stat` every 10 s during a session) should wake the CPU about 10 times a minute and use well under 0.1% CPU (estimate; measure on target hardware before quoting it).

## 4. Installing, updating and code signing

### 4.1 Precedent: how Claude Code ships (read 2026-11-19)

Claude Code is among the most-used harnesses (share among Hack Clubbers unverified; open question 2), and its install story is the bar to match ([setup docs](https://code.claude.com/docs/en/setup.md)):

- **Native installer, no admin:** `curl -fsSL https://claude.ai/install.sh | bash` (macOS, Linux, WSL); `irm https://claude.ai/install.ps1 | iex` (PowerShell); `curl -fsSL https://claude.ai/install.cmd -o install.cmd && install.cmd && del install.cmd` (CMD). Installs `~/.local/bin/claude` as a symlink into `~/.local/share/claude/versions/` (Windows: `%USERPROFILE%\.local\bin\claude.exe`). Native installs auto-update in the background, keep the two newest versions, and take effect on next start.
- **Package managers:** Homebrew casks `claude-code` (stable) and `claude-code@latest`; `winget install Anthropic.ClaudeCode`; signed apt, dnf and apk repositories. None of these auto-update by default. `CLAUDE_CODE_PACKAGE_MANAGER_AUTO_UPDATE=1` makes Claude Code run the Homebrew or WinGet upgrade itself; apt, dnf and apk "continue to require a manual upgrade because those commands need elevated privileges". "On WinGet the upgrade may fail while Claude Code is running because Windows locks the executable".
- **npm:** `npm install -g @anthropic-ai/claude-code@latest` (Node 22+) pulls "a per-platform optional dependency such as `@anthropic-ai/claude-code-darwin-arm64`, and a postinstall step links it into place. The installed `claude` binary does not itself invoke Node." Platforms: `darwin-arm64`, `darwin-x64`, `linux-x64`, `linux-arm64`, `linux-x64-musl`, `linux-arm64-musl`, `win32-x64`, `win32-arm64`.
- **Integrity:** each release publishes a GPG-signed `manifest.json` with SHA-256 per platform; macOS binaries are signed by "Anthropic PBC" and notarized; Windows binaries are Authenticode-signed; Linux binaries rely on the signed manifest or repository keys.
- **Requirements:** "macOS 13.0+", "Windows 10 1809+", "4 GB+ RAM, x64 or ARM64 processor". No 32-bit Windows, no macOS 12.

That last line bounds pairtime's own requirements for its Claude Code users: a machine that can't run the harness doesn't need pairtime's harness integration. 32-bit Windows and macOS 12 matter only for other harnesses and for editor-only tracking (unverified which popular harnesses still support them).

### 4.3 Windows: SmartScreen, Smart App Control, and what signing costs

From Microsoft's [SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation) page (2026-05-04):

- SmartScreen weighs "Publisher reputation" and "File hash reputation". Unsigned: "Windows protected your PC", and the user "must choose 'Run anyway'". Enterprise policy can remove that option.
- "When a file is not signed, SmartScreen reputation must build for each new version of your files, starting with zero reputation." Signed files can inherit reputation from the certificate; reputation "can take several weeks and hundreds of clean installs from a wide audience".
- "EV certificates no longer bypass SmartScreen." The bypass "was removed in 2024".
- "On Windows 11 devices, the Smart App Control feature may supersede SmartScreen ... Smart App Control will block execution of unsigned files unless the file has a positive reputation. Smart App Control signature checks apply to all executable files, not just those downloaded from the Internet." So on a Windows 11 machine with Smart App Control on, an unsigned pairtime binary may not run however it was installed.

Terms ([signpath.org/terms](https://signpath.org/terms), marked draft, read 2026-11-19): "an OSI-approved Open Source license without commercial dual-licensing for all components" (AGPL-3.0 qualifies); no proprietary components; "Binary artifacts must be built from source code in a verifiable way"; "The project must already be released in the form that should be signed"; for downloadable executables "we require a certain verifiable reputation"; acceptance is discretionary | Microsoft's own page lists it as the open-source route; "The code signing certificate is issued to SignPath Foundation", so the Foundation, not pairtime, is the publisher Windows shows; keys stay in SignPath's HSM, signing runs from CI. Conditions that bind pairtime's design (added in fact-check): "Every release needs manual approval for signing"; MFA for all team members; a "Code signing policy" section on the home and download pages; sending data to destinations the user didn't choose needs a privacy statement at setup plus an opt-out; "Software must not modify the user's system configuration without proper warnings", which covers writing the Run key and harness hook configs; uninstall tooling is required. A brand-new project may not meet the reputation bar on day one, so plan for a first release that is unsigned or signed another way |
| Microsoft Store MSIX | free | anyone | covered above |

Hack Club is a US nonprofit, so as an organization it should qualify for Artifact Signing (open question 1). SignPath is the free route if signing under the project's own name doesn't matter.

### 4.4 macOS: Gatekeeper and notarization

- Since macOS 15 Sequoia, "users will no longer be able to Control-click to override Gatekeeper when opening software that isn't signed correctly or notarized. They'll need to visit System Settings > Privacy & Security" ([Apple Developer News](https://developer.apple.com/news/?id=saqachfa), 2024-08-06). Apple's current user steps: try to open it, then System Settings > Privacy & Security > Open Anyway, confirm, and the app "is now saved as an exception" ([support 102445](https://support.apple.com/en-us/102445), 2026-05-27).
- Apple Silicon won't run native arm64 code without a valid signature (ad-hoc is enough); Homebrew's issue cites Apple's Rosetta page for this ([brew#20755](https://github.com/Homebrew/brew/issues/20755)). The Go toolchain ad-hoc signs Mach-O output itself: `src/cmd/internal/codesign` ("ad-hoc code signing of Mach-O files ... the same ad-hoc signing algorithm as the Darwin linker"), so a pure-Go `GOOS=darwin GOARCH=arm64` build made on Linux runs on Apple Silicon (wakatime-cli ships such a `darwin-arm64` build). Rust gets the same from Apple's linker on a macOS runner.
- Developer ID signing and notarization need an Apple Developer Program membership (US$99/year; fee waivers exist for some nonprofits, unverified for Developer ID-only use). Both can run on a Linux CI runner: GoReleaser's `notarize.macos` uses [anchore/quill](https://github.com/anchore/quill) ("works on any operating system"; inputs: `.p12` certificate and password, App Store Connect `issuer_id`, `key_id` and `.p8` key; binaries only, not app bundles) ([GoReleaser docs](https://goreleaser.com/customization/notarize/)). The same page warns "Do not use this method if you create App Bundles", because "App Bundles in which only the binary is signed/notarized are deemed damaged by macOS"; GoReleaser's bundle-capable `notarize.macos_native` mode runs only on macOS and "is exclusively available with GoReleaser Pro" (added in fact-check). So a future menu-bar `.app` needs a macOS runner with `codesign`/`notarytool`, GoReleaser Pro, or rcodesign. [rcodesign](https://gregoryszorc.com/docs/apple-codesign/main/) can "sign, notarize, and release Apple software from non-Apple operating systems", including stapling for bundles, pkgs and DMGs.
- In practice: a CLI installed by `curl | sh`, a Homebrew formula or an editor extension avoids Gatekeeper even unsigned (unverified for the extension case); a downloadable `.app` or a Homebrew cask needs Developer ID plus notarization.

### 4.5 Linux

No signing requirement. Ship static binaries in tarballs, `.deb`/`.rpm`/`.apk` via nFPM (GoReleaser), and a signed checksum file. Avoid Snap and Flatpak for the agent: their sandboxes are designed to block reading `~/.claude`, `~/.codex` and other apps' files, which is the agent's whole job (unverified per-sandbox details; both allow broad `home` access only with extra permissions).

### 4.6 Self-update

| Step | Detail |
|---|---|
| Check | at most once a day, plus on agent start; fetch a small signed manifest (version, per-platform URL, SHA-256, minimum supported version) from GitHub Releases |
| Verify | the manifest signature with an Ed25519 public key compiled into the binary (minisign format or plain Ed25519; GPG as Claude Code does works too but needs gpg tooling), then the SHA-256 of the download. ## 5. Local storage and UI

### 5.1 The local event store

pairtime writes little: an idle sample every 15 s, a few hook events per prompt, transcript-derived turn records, focus changes. That's on the order of 10,000 small rows per active day (estimate). The store's real jobs are durability across crashes and sleep, cheap range queries for the local dashboard, and an append-only shape that later supports the audit chain (R10).

Recommended layout:

| File | Format | Why |
|---|---|---|
| `spool/<yyyy-mm-dd>.jsonl` | append-only JSON Lines, one record per line, written by the agent (file kept open, flushed in batches) and by hooks only when the agent is unreachable (6.2) | a hook can always fall back to one `O_APPEND` write and exit; crash-safe; human-readable for the user and a reviewer; trivial to hash-chain |
| `pairtime.db` | SQLite in WAL mode | the agent's index: sessions, minutes, projects, derived credit, upload state. Rebuildable from the spool plus harness logs, so `synchronous=NORMAL` is acceptable |
| `config.toml` | TOML | user settings, project mappings, privacy rules |

SQLite settings: `journal_mode=WAL`, `synchronous=NORMAL`. SQLite's docs: "WAL mode is safe from corruption with synchronous=NORMAL", "A transaction committed in WAL mode with synchronous=NORMAL might roll back following a power loss or system crash", and "Transactions are durable across application crashes regardless of the synchronous setting or journal mode"; in WAL+NORMAL "no sync operations occur during most transactions". Auto-checkpoint defaults to 1,000 pages ([PRAGMA docs](https://www.sqlite.org/pragma.html)). On a spinning disk, fsync is the expensive part (tens of milliseconds each, estimate), so batch writes: the agent commits once every 15 to 60 s or on suspend, not per event. The spool is where per-event durability lives.

Go drivers (benchmark on an i7-1165G7, NVMe, Go 1.26.0, run 2026-03-23, [cvilsmeier/go-sqlite-bench](https://github.com/cvilsmeier/go-sqlite-bench), Unlicense): inserting 1 million rows in one transaction took 1,480 ms with `mattn/go-sqlite3` (cgo, MIT), 2,419 ms with `modernc.org/sqlite` (C transpiled to Go, no cgo, BSD-3-Clause) and 2,719 ms with `ncruces/go-sqlite3` (SQLite compiled to WASM and run by wazero, no cgo, MIT). The author's summary: "SQLite without CGO is possible nowadays." At pairtime's write rate, all three are far faster than needed, so the cgo-free drivers win on cross-compilation (1.5). `modernc.org/sqlite` adds several megabytes to the binary (unverified size). Rust's `rusqlite` with the `bundled` feature compiles SQLite's C in the build.

Alternatives considered: bbolt (what wakatime-cli uses for its offline queue, `~/.wakatime/offline_heartbeats.bdb`; hackatime-and-hack-club.md) is a fine key-value queue but has no SQL for dashboard queries; plain JSONL alone makes "minutes per project this week" a full scan; DuckDB is far too large for the footprint target.

### 5.2 Encryption at rest

| Approach | Protects against | Doesn't protect against | Cost |
|---|---|---|---|
| Rely on full-disk encryption (BitLocker, FileVault, LUKS) | stolen laptop | anything running as the user | none; but Windows 10 Home has no BitLocker, only "Device Encryption" on some hardware (unverified for 2016 laptops) |
| Encrypt sensitive fields only (raw prompt text, transcript excerpts) with XChaCha20-Poly1305 (`golang.org/x/crypto`), key in the OS credential store | other local users, backups and cloud sync of the home folder, casual reading of the files, accidental upload | malware or a script running as the same user, which can ask the credential store for the key | small; one key lookup at agent start |
| SQLCipher for the whole DB | same as above, for every field | same as above | needs cgo in Go, reintroducing the cross-compile cost |

Key storage without cgo: [zalando/go-keyring](https://github.com/zalando/go-keyring) (MIT, pushed 2026-11-17) uses Windows Credential Manager, the `/usr/bin/security` binary on macOS ("It should be available by default"), and the Secret Service D-Bus API on Linux. Secret Service is missing on minimal window managers and headless boxes, so fall back to a key file with mode `0600` and say so in the UI. On Windows, DPAPI (`CryptProtectData`, per-user) is an alternative with no prompt.

Recommendation: store only what's needed (hashes, lengths, timestamps and derived features by default; raw prompt text only if the user turns on local history), and encrypt that raw text per field. Be honest in the privacy page that this guards against other users and accidental sharing, not against malware on the same account (R6).

### 5.3 UI: tray, menu bar, or a local web dashboard

On a 4 GB machine, a webview window costs about 100 MB whichever framework draws it, so the rule is: nothing with a webview stays resident. The local dashboard in the user's existing browser costs nothing extra while closed, and a browser is already open on almost every teen's laptop. A tray or menu-bar icon is worth adding for R3 (today's time at a glance, pause tracking, open dashboard), but as a thin layer: on Windows and Linux it can live in the agent; on macOS a tray needs cgo and an app bundle, so ship it as a small separate menu-bar helper or defer it.

## 6. Hooks calling the client: cold start and IPC

Harness hooks are the main event source (ai-harness-signals.md), and several fire on every prompt and many times per turn. Claude Code's `UserPromptSubmit` hooks have a 30 s default timeout, and the model waits until the hook returns ([hooks docs](https://code.claude.com/docs/en/hooks.md)). The default for `command`, `http` and `mcp_tool` hooks on most other events is 600 s, but `SessionEnd` hooks "share a 1.5-second budget" (raised only by a per-hook `timeout`, up to 60 s, or `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS`), so a session-end hook must hand its record to the agent or the spool and exit without doing any work itself (added in fact-check; same page). A hook that costs 300 ms is a visible lag on every prompt, and on a 2-core laptop it competes with the agent and the editor.

### 6.1 What a hook invocation costs

| Path | Startup cost | Source |
|---|---|---|
| Process creation on Windows | "10-30ms to spawn" each new process on Windows, versus under 10 ms for `fork`+`exec` on Linux | [Szorc, "Surprisingly Slow"](https://gregoryszorc.com/blog/2021/04/06/surprisingly-slow/), 2021 |
| Same, relative | Linux launches programs ">20x faster" than Windows; a Raspberry Pi 3 beat stock Windows 10 Pro with Defender on a Ryzen 1800X | [bitsnbites](https://www.bitsnbites.eu/benchmarking-os-primitives/), 2017 (updated 2024) |
| Defender on file close | `CloseHandle` on a newly written file "1-10+ milliseconds", because Defender's filter driver scans on close | Szorc, same post |
| Native binary runtime init (Go, Rust) | 0.41 ms (Go), 0.51 ms (Rust) on an i5-2400S; about 4 ms on a Raspberry Pi 3 | [bdrung/startup-time](https://github.com/bdrung/startup-time), 2018 |
| Interpreter init | Python 3: 25.84 ms on the i5, 197.79 ms on the Pi 3; Node.js 41.70 ms and Deno 14.53 ms in a separate undated sample | bdrung; [chocolateboy/startup-time](https://github.com/chocolateboy/startup-time) |
| `npx pairtime ...` | Node startup plus npm's package resolution on every call (several hundred ms or more on an old laptop; unverified, measure) | |
| Shell-form hook on Windows | Claude Code runs shell-form hooks through Git Bash ("Git Bash on Windows, or PowerShell when Git Bash isn't installed"), adding a shell's startup before pairtime's; exec form ("`command` + `args`") spawns the executable directly but "requires `command` to resolve to a real executable such as a `.exe`" | [hooks docs](https://code.claude.com/docs/en/hooks.md), read 2026-11-19 |
| HTTP hook (Claude Code `type: "http"`; Copilot with `COPILOT_HOOK_ALLOW_LOCALHOST=1`) | no process at all: one POST to the agent; "Connection failure: non-blocking error" | hooks docs; ai-harness-signals.md section 14 |

So on the target laptop, a native hook binary in exec form costs roughly the Windows spawn (tens of ms) plus milliseconds of its own work; an interpreter adds 25 to 200+ ms on top; `npx` adds more. HTTP hooks remove the spawn but aren't available everywhere: Claude Code's `SessionStart` accepts only `command` or `mcp_tool`, and Cursor's loader runs only `command` and `prompt` types for Claude-format hooks (ai-harness-signals.md, fact-check notes). The client therefore needs both: a native hook binary and a local HTTP endpoint.

### 6.2 What the hook binary should do

`pairtime hook --harness <name> --event <event>`, registered in exec form:

1. Read stdin (the event JSON) with a size cap. Parse only the fields it needs: session ID, event name, timestamps, cwd, and the prompt for prompt events.
2. Apply the local privacy policy right there: compute the prompt's length, SHA-256 and any features; keep raw text only if the user enabled local history (R6).
3. Send one framed message to the agent over the local IPC endpoint (6.3) with a short connect-and-ack timeout (50 to 100 ms).
4. If the agent doesn't answer: append one line to the spool file (5.1), start the agent detached, and exit. The agent drains the spool when it comes up, so nothing is lost when the agent is down, asleep or updating.
5. Exit 0 and print nothing, or exactly the JSON the harness expects. Claude Code parses a hook's stdout as JSON for decisions, and exit code 2 blocks the action, so a tracking hook must never fail closed.

The IPC path is preferred over writing the spool every time because on Windows each new file and each close of a written file can cost milliseconds under Defender (6.1), while a write to an open pipe or socket doesn't touch the file system. The agent keeps its own spool file open and flushes it in batches.

### 6.3 IPC options

| | Unix domain socket | Windows named pipe | Localhost TCP/HTTP |
|---|---|---|---|
| Availability | macOS, Linux; Windows since Insider build 17063 ("Build 17063 brings native support for the unix socket to Windows"; build 17063 was an RS4 preview and RS4 shipped as Windows 10 1803, so public from 1803 by inference, unverified), `SOCK_STREAM` only (no `SOCK_DGRAM` or `SOCK_SEQPACKET`, no `socketpair`, no autobind), "no support for ancillary data" ([Microsoft devblog](https://devblogs.microsoft.com/commandline/af_unix-comes-to-windows/), 2017-12-19). Go: "The Unix socket (AF_UNIX) address family is now supported for compatible versions of Windows" ([Go 1.12 notes](https://go.dev/doc/go1.12)); `src/net/unixsock_posix.go` builds for `windows` | Windows only. Go: `github.com/Microsoft/go-winio` (MIT) `ListenPipe(path string, c *PipeConfig) (net.Listener, error)`, where `PipeConfig.SecurityDescriptor` takes SDDL; "The pipe must not already exist" (`pipe.go`, main, checked in fact-check) | everywhere; the only option for the browser dashboard and for HTTP hooks |
| Who can connect | anyone with write permission on the socket file: "for connecting to a stream socket, the connecting process should have write permission on the socket" (same devblog); put it in a directory only the user can open | by default, "full control to the LocalSystem account, administrators, and the creator owner" and "read access to members of the Everyone group and the anonymous account" ([Named pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)), so always pass an explicit DACL; "To prevent remote users or users on a different terminal services session from accessing a named pipe, use the logon SID on the DACL" | any process of any user on the machine, and any web page the user opens (subject to browser protections) |
| Peer identity | Linux `SO_PEERCRED`; macOS `getpeereid` / `LOCAL_PEERCRED` (and `LOCAL_PEERPID`, xnu `bsd/sys/un.h`); Windows AF_UNIX `SIO_AF_UNIX_GETPEERPID` (`_WSAIOR(IOC_VENDOR, 256)` in `afunix.h`, as mirrored in mingw-w64's headers) | `GetNamedPipeClientProcessId`, `GetNamedPipeServerProcessId`; `FILE_FLAG_FIRST_PIPE_INSTANCE` detects a squatter that created the pipe first; `PIPE_REJECT_REMOTE_CLIENTS` (unverified flag behavior on old builds) | none; needs a bearer token |
| Path rules | `sun_path` is 108 bytes on Linux (unix(7)) and Windows (`UNIX_PATH_MAX 108` in `afunix.h`) and 104 on macOS (xnu `bsd/sys/un.h`), so use a short path: `$XDG_RUNTIME_DIR/pairtime/agent.sock` on Linux, `$TMPDIR/pairtime/agent.sock` on macOS (per-user), `%LOCALAPPDATA%\pairtime\agent.sock` on Windows. A stale socket file must be deleted before `bind` (on Windows it's "a custom NTFS reparse point") | `\\.\pipe\pairtime-<user SID>` | port in a user-only file |
| Reachable from WSL2 | no | no | only via the host IP in NAT mode, which Windows treats as a LAN connection; `localhost` works both ways only in mirrored mode, "Windows 11 22H2 and higher" ([WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking)) |

Recommendation:

- **Hooks and CLI → agent:** a Unix domain socket on all three OSes, in a per-user directory (on Windows, `%LOCALAPPDATA%` already has a user-only ACL; set it explicitly anyway). One code path in Go, and access is controlled by file permissions. Fall back to a named pipe with an owner-only DACL only if AF_UNIX turns out to be unreliable on some Windows 10 builds (test 1809 and 21H2 specifically).
- **HTTP endpoint for HTTP hooks and the dashboard:** bind `127.0.0.1` only, never `0.0.0.0`, even though that's what reaching the agent from WSL's NAT mode would take (6.4). Use a default port with fallback, and write `{port, token}` to a user-only file. Hook endpoints require `Authorization: Bearer <token>` (Claude Code HTTP hooks support `headers`, with env interpolation only for names in `allowedEnvVars`, so the installer writes the literal header value into the hook config). Every request must carry a `Host` of `127.0.0.1:<port>` or `localhost:<port>`, which blocks DNS rebinding. Any request with an `Origin` other than the dashboard's own is rejected (CSRF). The dashboard gets a session cookie (`SameSite=Strict`, `HttpOnly`) through a one-time URL that `pairtime dashboard` opens. Several users share family laptops, so the token is per user, not per machine.

### 6.4 WSL

Some Windows users run their harness inside WSL2 (Claude Code documents WSL 2 as supported and WSL 1 as "Not supported", per its setup docs; how many Hack Clubbers do is unknown, open question 2), where hooks are Linux processes and transcripts live in the Linux file system. Neither the Unix socket nor `127.0.0.1` on the Windows side is reachable from there on Windows 10 (6.3). Options: (a) run a Linux pairtime agent inside WSL that tails the Linux-side logs and handles hooks, and have it hand records to the Windows agent through a spool directory under `/mnt/c/Users/<user>/AppData/Local/pairtime/` (DrvFs writes are real NTFS writes, so the Windows agent's watcher should see them; unverified); idle and focus come from the Windows agent, since WSL has no input devices. (b) Have the Windows agent read `\\wsl.localhost\<distro>\home\<user>\.claude` over 9P, which is slow and whose change notifications are unreliable (unverified). Option (a) is more robust. `pairtime install` run inside WSL should detect WSL (`/proc/sys/fs/binfmt_misc/WSLInterop` or `WSL_DISTRO_NAME`) and set this up.

## 7. Recommended client stack

One Go binary, `pairtime` (`pairtime.exe`), with subcommands. Same binary for every role so there's one thing to sign, ship and update.

| Role | Command | Runs as | Notes |
|---|---|---|---|
| Agent | `pairtime agent` | one per user session, started at login (2.1), single-instance lock | idle sampler (15 s), foreground-app events, harness log tailer (3.2), `.git` watchers, spool drain, SQLite index, local HTTP and socket endpoints, uploader for submitted data, self-update check |
| Hook receiver | `pairtime hook --harness <h> --event <e>` | spawned by harnesses, exec form | 6.2: parse, apply privacy policy, send over the socket, spool fallback, exit 0 |
| Explicit tracking | `pairtime track ...` | run by the coding agent, following the AGENTS.md entry (Karim's universal fallback, R7) | same path as `hook`; the model passes the stripped prompt |
| Setup | `pairtime install` / `uninstall` / `doctor` | the user, once | writes autostart (2.1) and harness hook configs (merging with existing entries such as git-ai's, per ai-harness-signals.md), picks paths, runs a self-test that reports idle detection, hook latency and watcher status |
| Dashboard | `pairtime dashboard` | the user | opens `http://127.0.0.1:<port>/` with a one-time token (5.3, 6.3) |
| Tray / menu bar | in the agent on Windows and Linux; a small separate helper on macOS, or later | | today's total, pause, open dashboard (R3) |

Libraries (all cgo-free): `golang.org/x/sys` (Win32, Unix), `ebitengine/purego` (macOS frameworks), `godbus/dbus/v5` (Linux idle, logind, SNI tray), `fsnotify/fsnotify` (watching, 3.1), `modernc.org/sqlite` or `ncruces/go-sqlite3` (5.1), `zalando/go-keyring` (5.2), `golang.org/x/crypto` (XChaCha20-Poly1305, Ed25519 for update signatures). Release pipeline: GoReleaser OSS in GitHub Actions on `ubuntu-latest` builds `windows/{amd64,386,arm64}`, `darwin/{amd64,arm64}`, `linux/{amd64,arm64}`; produces archives, `checksums.txt` and a signed update manifest; Authenticode-signs Windows binaries through SignPath or Artifact Signing; signs and notarizes macOS binaries with quill once an Apple Developer ID exists; publishes the Scoop bucket, Homebrew tap and winget manifest; and builds platform-specific VSIX packages for the editor extension. Test jobs run on `windows-latest`, `macos-latest`, `macos-15-intel` (until August 2027) and `ubuntu-latest`, all free for a public repo (1.5).

Footprint targets to verify on real hardware before launch (estimates, not measurements): agent binary under 15 MB; agent RSS under 25 MB on Windows; idle CPU under 0.1% averaged over an hour with about 10 wakeups a minute; hook round trip under 50 ms warm on a 2016 dual-core with a hard drive; disk use under 50 MB per month of tracking excluding opt-in raw prompt history.

## 9. Design implications

1. **Write the client in pure Go (`CGO_ENABLED=0`) as one binary with `agent`, `hook`, `track`, `install`, `doctor` and `dashboard` subcommands.** One artifact per OS and architecture to sign, ship and update; cross-compiled from one Linux job; reaches Win32, Apple frameworks (via `purego`), D-Bus and SQLite without cgo. Ship `windows/amd64`, `windows/arm64`, `darwin/amd64`, `darwin/arm64`, `linux/amd64`, `linux/arm64`, plus `windows/386` if open question 2 says 32-bit machines exist. (R8, R7)
2. **Set footprint budgets and make them release gates:** agent RSS under 25 MB on Windows, idle CPU under 0.1% averaged over an hour, about 10 wakeups a minute, hook round trip under 50 ms warm, binary under 15 MB. Measure them on a real 2016-era 4 GB laptop with a hard drive, since GitHub's runners (4 CPU, 16 GB, SSD) aren't representative. (R8)
3. **Run the agent in the user's session, started by the HKCU Run key (Windows), a LaunchAgent (macOS) or XDG autostart (Linux, with an opt-in systemd user unit).** No admin rights, no service. Don't use Task Scheduler, whose defaults stop on battery. Enforce a single instance. Show the user where autostart lives, and make `pairtime uninstall` remove every trace. (R4, R6, R8)
4. **Treat sleep explicitly:** subscribe to suspend and resume (`PowerRegisterSuspendResumeNotification`, IOKit `IORegisterForSystemPower`, logind `PrepareForSleep`), flush on suspend, store wall-clock UTC per sample, and treat any gap over twice the sample interval as "machine off". Never derive active time from monotonic differences across a possible suspend; in Go that means computing sample gaps from wall-clock values (`t.Round(0)` or `UnixNano()`), because `time.Since` uses the monotonic clock, which stops during sleep on Linux and macOS and keeps running on Windows (2.2). (R2, R9, R10)
5. **Presence comes from OS idle time sampled every 15 s, plus focus-change events, plus harness and editor events.** No global keyboard or mouse hooks in v1: they look like a keylogger to antivirus engines, to winget's multi-engine scan and to privacy-minded users, and idle time already covers presence. If keystroke counts are added later, they're opt-in and count-only. (R6, R8, R9)
6. **Get the foreground app from events (`SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`, `NSWorkspace` notifications, X11 `_NET_ACTIVE_WINDOW`), never from WMI or AppleScript polling.** App name by default; window titles only with opt-in, since titles leak file names and page titles. (R6, R8, R4)
7. **Watch narrowly:** harness log roots non-recursively plus active subfolders, with per-file cursors and a slow `stat` poll of hot files as backup; each known repo's `.git` directory for commits and checkouts; no recursive working-tree watch on Linux. This keeps inotify watches in the tens and leaves VS Code's watcher budget alone. (R8, R4, R5 git integration)
8. **The hook path is a native exec-form binary that sends one message over a per-user Unix domain socket, falls back to an append-only spool, always exits 0 and prints nothing unexpected.** Register hooks as `command` + `args` pointing at the absolute binary path, never through `npx`, a shell or an interpreter. (R7, R8, R4)
9. **Expose a `127.0.0.1`-only HTTP endpoint** for harnesses that support HTTP hooks (Claude Code, Copilot) and for the dashboard, guarded by a per-user bearer token, `Host` validation against DNS rebinding, and `Origin` checks against CSRF. (R6, R7, R3)
10. **Store events as a daily JSONL spool (append-only, hash-chainable for audit) plus a SQLite index in WAL mode with `synchronous=NORMAL` and batched commits.** The index can be rebuilt from the spool and harness logs. Keep raw prompt text out by default; if the user enables local history, encrypt it per field with a key from the OS credential store. (R6, R10, R8)
11. **The UI is a local web dashboard served by the agent and opened in the user's browser, plus a thin tray icon on Windows and Linux.** Nothing with a webview stays resident; reuse the server dashboard's components so the local and public views match. Defer the macOS menu-bar helper until there's an Apple Developer ID. (R3, R8, R5)
12. **Distribute through every channel teens already use, all no-admin:** `curl -fsSL .../install.sh | sh`, `irm .../install.ps1 | iex`, winget, Scoop, a Homebrew tap, npm with per-platform optional dependencies (for `npx pairtime install`, not for hooks), and platform-specific VSIX builds of the editor extension that bundle the binary. GoReleaser OSS produces nearly all of it. (R8, R7, adoption)
13. **Sign on Windows as early as an identity allows** (Azure Artifact Signing under Hack Club as a US organization, which can start as soon as identity validation clears in 1 to 30 business days; or SignPath Foundation, free, but it wants a released project with "a certain verifiable reputation", manual approval of every signing request, and a published code signing policy, so it may not be available for the first release), because unsigned files restart SmartScreen reputation with every release and Smart App Control blocks them. **Notarize on macOS** with quill from Linux once a Developer ID exists. Sign the update manifest with an embedded Ed25519 key, and verify every download. (R9, R6, R8)
14. **Self-update daily from a signed manifest,** with a rename-swap on Windows. Don't self-update binaries owned by winget, Scoop or Homebrew. Keep the hook path stable across updates. (R8, R9)
15. **Ship a WSL mode:** `pairtime install` inside WSL sets up a Linux agent for the Linux-side logs and hooks, which hands records to the Windows agent through a spool on `/mnt/c`. Presence still comes from the Windows side. (R7, R8)
16. **Decide the macOS toolchain floor explicitly:** build the macOS binaries with Go 1.26 until February 2027 if pre-2017 Macs on macOS 12 matter, then move to the current Go and require macOS 13 (Claude Code already does). (R8)
17. **Opt the agent into EcoQoS on Windows and leave `ProcessType` at Background or unset on macOS,** so the OS can schedule it on the most efficient cores and frequencies. (R8)
18. **Make `pairtime doctor` the support tool:** it reports idle-detection status, hook round-trip time, watcher health, autostart state and signing status, and exports a redacted report. Hack Club's support channel will see many old, odd machines. (R8, R3)

## 10. Open questions

1. **Who holds the signing identities?** Can Hack Club, as a US nonprofit, own an Azure Artifact Signing account and an Apple Developer ID (and is Apple's nonprofit fee waiver available for Developer ID-only distribution)? Or should pairtime use SignPath Foundation, which signs under the Foundation's name, wants a released project with some verifiable reputation before it signs downloadable executables, and needs a team member to approve every signing request? If SignPath, is shipping the first releases unsigned (or Store-only) acceptable while reputation builds? Who controls the keys if the project changes hands? (Karim, Hack Club staff)
2. **What hardware and OS do Hack Clubbers actually run?** Hackatime's heartbeat user agents include OS, architecture and editor. Can Hack Club share aggregate counts of Windows 10 vs 11, 32-bit Windows, macOS versions (especially 12 and older), Linux distributions, WSL and ChromeOS? This decides `windows/386`, the Go 1.26 pin for macOS and the priority of WSL mode. (Hack Club staff)
3. **Is ChromeOS in scope?** R8 names Windows, macOS and Linux, but many students have school Chromebooks, where the Linux container (Crostini) sees no host input or focus. (Hack Club staff)
4. **School-managed and S-mode laptops:** should pairtime support machines where users can't run unsigned or non-Store software? That requires an MSIX build in the Microsoft Store, with the sandbox limits that implies for reading other apps' files. (Hack Club staff, Karim)
5. **Is a resident agent acceptable for the privacy bar?** R4 practically requires one (idle time, lookback), but some privacy-minded users may prefer hooks-only mode with no daemon. Should hooks-only be a supported, clearly weaker mode? (Karim)
6. **Karim's `npx` examples:** is it acceptable for the AGENTS.md entry and hooks to call an installed `pairtime` binary instead of `npx`, given that `npx` adds Node and npm startup to every prompt? (Karim)
7. **Local raw-prompt history: default on or off?** On helps R3 (reflection, self-improvement); off is the stronger privacy default for R6. (Karim)
8. **Language choice:** Go is recommended here; does the team's skill set or a preference for Rust change that? (Karim)
9. **Field telemetry for R8:** may the client report anonymous footprint metrics (agent RSS, CPU, hook latency, OS version) to the server so the old-laptop claim can be shown with data? (Karim, Hack Club staff)
10. **Test hardware:** can Hack Club lend or source a few real 2015 to 2017 Windows laptops (4 GB, hard drive) and an old Intel Mac for footprint testing, or recruit testers who own them? (Hack Club staff)
